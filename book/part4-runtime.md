# 第四部分：核心運行時期與對話引擎

在前一部分中，我們對 Claw Code 的整體系統架構進行了全面的剖析，從 Cargo Workspace 的組織結構到九個 crate 的分層設計，再到核心引擎 runtime crate 中三十五個以上子模組的功能分群。讀者至此應當已經建立了對系統全貌的清晰認識。然而，架構圖只是靜態的骨架，要真正理解 Claw Code 如何運作，我們需要追蹤資料在系統中的流動路徑，觀察各個元件在運行時期的協作方式。

本部分將聚焦於 Claw Code 最核心的運行時期行為：對話引擎的工作機制、工作階段的完整生命週期，以及設定系統的合併與驗證邏輯。這三個方面分別對應了系統的「動態行為」、「狀態管理」和「靜態配置」三個維度，共同決定了使用者在每一次互動中所體驗到的系統行為。

## 第十章：對話迴圈深度解析

### 10.1 啟動流程

當使用者在終端機中輸入 claw 命令並按下 Enter 鍵的那一刻，一個精密的啟動序列便開始運作。理解這個啟動序列對於排除問題和最佳化使用體驗至關重要。

啟動的第一步是 CLI 參數解析。rusty-claude-cli 的 main.rs 模組使用 Rust 的命令列參數處理機制解析使用者提供的所有參數。系統需要判斷使用者選擇了哪種運作模式：如果使用者提供了 prompt 子命令和提示詞文字，系統將進入一次性提示模式；如果使用者只輸入了 claw 而沒有其他參數，系統將進入互動式 REPL 模式；如果使用者輸入了 doctor、status、init 等子命令，系統將執行對應的子命令邏輯後退出。

第二步是共用初始化流程，這是一次性模式和 REPL 模式共享的啟動路徑。首先，ConfigLoader 的 discover 方法會按照前述的五層優先級順序掃描所有可能的設定檔案路徑，讀取存在的設定檔案內容，然後進行深度合併，產生最終的 RuntimeConfig。接著，系統解析要使用的模型名稱，解析邏輯遵循四級優先序：命令列旗標最優先，其次是環境變數 ANTHROPIC_MODEL 或 CLAW_MODEL，再次是設定檔中的 model 欄位，最後是系統預設值 claude-opus-4-6。ModelProvenance 結構會記錄最終的模型名稱以及它的來源，方便後續的除錯和日誌記錄。然後，系統解析認證資訊，依序檢查 API 金鑰環境變數、OAuth token 檔案和 Bearer token 環境變數。

第三步是載入外掛。PluginManager 的 load_plugins 方法會掃描設定中指定的外掛目錄，讀取每個外掛的 plugin.json 清單檔，驗證外掛的元資料和權限需求，初始化符合條件的外掛，並註冊它們提供的工具和勾子。

第四步是 MCP 伺服器啟動。如果設定中包含 mcpServers 區段，系統會為每個配置的 MCP 伺服器執行完整的生命週期啟動序列：從 ConfigLoad 到 ServerRegistration、SpawnConnect、InitializeHandshake、ToolDiscovery、ResourceDiscovery，直到所有伺服器達到 Ready 狀態或部分伺服器進入降級模式。

第五步是系統提示詞組裝。SystemPromptBuilder 收集各種上下文資訊——Git 分支名稱和最近提交記錄、專案目錄結構、設定檔中的自訂指令、已載入的工具清單和工具描述——然後將所有這些資訊整合成一個完整的系統提示詞字串。這個系統提示詞將在每次 API 請求中被包含，指導 AI 模型理解當前的工作環境和可用的操作能力。

第六步是工作階段初始化。如果使用者提供了 --resume 參數，系統會從磁碟上載入指定的歷史工作階段，恢復完整的訊息歷史；否則，系統會創建一個全新的工作階段，生成唯一的 session_id，記錄工作區路徑和模型名稱。

第七步是權限模式設定。系統根據命令列旗標、環境變數或設定檔中的指定，設定 PermissionPolicy 的運作模式和規則。至此，整個系統進入就緒狀態，準備接收使用者的輸入。

### 10.2 單回合對話流程

當系統進入就緒狀態後，每一次使用者與 AI 的互動都遵循一個精確的回合（turn）流程。理解這個流程的每一個步驟，有助於開發者預測系統行為、診斷問題以及最佳化使用策略。

回合開始於使用者輸入。在 REPL 模式中，系統透過 rustyline 函式庫顯示提示符號（prompt），等待使用者輸入文字。使用者可以輸入自然語言指令、斜線命令，或者透過快捷鍵觸發特殊操作。如果輸入以斜線開頭，系統會將其路由到 commands crate 進行斜線命令處理，不進入 AI 對話流程。否則，使用者的輸入被封裝為一則 User 角色的 ConversationMessage，添加到工作階段的訊息歷史中。

接下來，ConversationRuntime 呼叫 build_api_request 方法建構 API 請求。這個方法將系統提示詞、工作階段中的所有歷史訊息（包括之前的使用者訊息、助手回應和工具結果）、以及所有可用工具的定義（包括內建工具、MCP 工具和外掛工具）組合成一個 MessageRequest 結構。這個結構還包含模型名稱、最大輸出 token 數量、串流設定等參數。

然後，系統透過 ApiClient 的串流介面發送請求到 AI 提供商。提供商的伺服器開始處理請求，並透過 SSE 連線逐步推送回應事件。在 SSE 事件迴圈中，系統需要處理三類主要事件。

第一類是文字增量事件（TextDelta）。每當收到一小段文字增量時，系統將其傳遞到 CLI 層的 TerminalRenderer，TerminalRenderer 將增量的 Markdown 文字即時轉換為 ANSI 格式並輸出到終端。使用者因此能夠看到 AI 的回應正在逐字逐句地生成，獲得一種流暢的互動體驗。

第二類是工具呼叫事件（ToolUse）。當 AI 模型決定需要使用某個工具來完成任務時，它會在回應中包含一個工具呼叫請求，指定工具名稱和輸入參數。系統收到這個請求後，需要經過一個多步驟的處理流程。首先，HookRunner 檢查是否有已註冊的 pre_tool_use 勾子，如果有，則執行這些勾子腳本並收集它們的回傳結果。勾子可以回傳 Allow（強制允許）、Deny（強制拒絕）或 Ask（要求詢問使用者）。如果沒有勾子覆蓋，系統會透過 PermissionPolicy 進行標準的權限評估——先檢查工具是否在 deny 清單中，再檢查是否在 allow 清單中，再檢查是否在 ask 清單中，最後根據工具所需的權限級別和當前的權限模式進行比較。如果權限允許，系統透過 ToolExecutor 執行工具呼叫。工具執行完成後，如果有 post_tool_use 勾子，系統會執行這些勾子腳本。工具的執行結果（或權限拒絕的錯誤訊息）被封裝為一則 Tool 角色的 ConversationMessage，添加到訊息歷史中。然後，系統會自動發起新一輪的 API 請求，將工具結果包含在內，讓 AI 模型能夠基於工具的輸出繼續回應。這個工具呼叫到結果回饋的循環可能會連續執行多次，直到 AI 模型認為任務已完成。

第三類是訊息結束事件（MessageStop）。當收到這個事件時，表示 AI 的本輪回應已經完成。系統會從事件中提取停止原因（end_turn 表示正常結束，tool_use 表示需要等待工具結果）和 token 用量資訊，更新 UsageTracker。

回合結束後的收尾工作包括：檢查工作階段的 token 總量是否超過壓縮閾值（預設十萬個 token），如果超過，觸發自動壓縮流程；將更新後的工作階段儲存到磁碟上的 JSONL 檔案；生成 TurnSummary（回合摘要）回傳給 CLI 層。

### 10.3 多回合對話與上下文管理

一個典型的 Claw Code 使用場景往往涉及多個連續的對話回合。使用者可能先要求 AI 分析某個檔案的結構，然後基於分析結果要求修改特定的功能，接著要求執行測試來驗證修改，最後要求進行程式碼清理。在這整個過程中，每一個回合都建立在前一個回合的基礎上——AI 需要記住之前讀取過的檔案內容、之前做過的修改、之前測試的結果。

這種跨回合的上下文維護是透過工作階段的訊息歷史實現的。每一條使用者輸入、每一段 AI 回應、每一次工具呼叫和結果，都作為獨立的 ConversationMessage 被追加到工作階段中。在每個新的回合開始時，build_api_request 方法會將完整的訊息歷史包含在 API 請求中，讓 AI 模型能夠「看到」之前所有的互動記錄。

然而，這種方式面臨一個實際的限制：隨著對話的進行，訊息歷史會越來越長，最終超過 AI 模型的上下文視窗大小。即使在上下文視窗非常大（如 Claude Opus 的兩百萬 token）的模型上，長時間的開發工作階段也可能產生大量的 token。更重要的是，即使上下文視窗足夠大，過長的訊息歷史也會顯著增加 API 呼叫的延遲和成本。

Claw Code 透過壓縮機制來解決這個問題。CompactionConfig 定義了壓縮的觸發閾值（預設十萬個 token）和保留策略（預設保留最近四則訊息）。當工作階段的 token 總量超過閾值時，compact_session 方法會被觸發。壓縮的過程是：首先，系統計算需要移除多少舊訊息才能將 token 總量降到閾值以下；然後，被移除的訊息會被摘要為一段簡短的文字，記錄在 SessionCompaction 結構中；最後，壓縮後的工作階段只包含摘要和最近的四則訊息。這種設計在保持上下文連續性（摘要提供了歷史概覽）和控制成本（只保留最相關的近期訊息）之間取得了平衡。

## 第十一章：工作階段管理

### 11.1 工作階段的資料模型

Session 是 Claw Code 中管理對話狀態的核心資料結構。每一個 Session 包含以下關鍵欄位：session_id 是一個唯一的字串標識符，由系統在創建工作階段時自動生成；created_at_ms 和 updated_at_ms 分別記錄創建時間和最後更新時間的毫秒時間戳記；workspace_root 記錄工作區的根目錄路徑，用於建立工作階段與特定專案之間的關聯；model 記錄當前使用的模型名稱。

Session 內部包含一個有序的 ConversationMessage 列表，代表對話的完整歷史。每則 ConversationMessage 有一個 MessageRole 欄位（System、User、Assistant 或 Tool），以及一個 ContentBlock 列表。ContentBlock 是一個有三種變體的列舉型別：Text 變體包含純文字內容；ToolUse 變體包含工具呼叫的 ID、名稱和輸入參數；ToolResult 變體包含工具呼叫 ID、工具名稱、輸出內容和是否為錯誤的旗標。

此外，Session 可能包含一個 SessionCompaction 記錄（如果進行過壓縮）、一個 SessionFork 記錄（如果是從另一個工作階段分支出來的）、以及一個 SessionPromptEntry 列表（記錄使用者的所有提示歷史）。每則訊息還可能附帶 TokenUsage 資訊，記錄輸入 token 數量、輸出 token 數量、快取創建 token 數量和快取讀取 token 數量。

### 11.2 JSONL 持久化

Claw Code 選擇了 JSONL（JSON Lines）格式來持久化工作階段資料。在 JSONL 格式中，每一行是一個獨立的 JSON 物件，行與行之間以換行符號分隔。這種格式相較於傳統的單一 JSON 檔案有幾個顯著優勢。

首先是追加寫入的友好性。在對話過程中，每當有新的訊息產生（使用者輸入、AI 回應、工具結果），系統只需要將新訊息序列化為一行 JSON 並追加到檔案末尾，不需要重新序列化和寫入整個工作階段。這不僅提高了寫入效能，也降低了資料損壞的風險——即使程式在寫入過程中意外終止，已經寫入的行仍然是完整的，最多只會損失最後一行不完整的資料。

其次是串流讀取的友好性。當恢復一個歷史工作階段時，系統可以逐行讀取 JSONL 檔案，每讀取一行就解析一則訊息並添加到工作階段中。這種方式的記憶體效率比一次性載入整個 JSON 檔案要高得多，特別是對於長時間的工作階段。

Claw Code 還實作了工作階段檔案的旋轉機制。當一個工作階段檔案的大小超過兩百五十六 KB 時，系統會創建一個新的檔案繼續寫入，同時保留最新的三個檔案。這種旋轉策略在保留足夠的歷史記錄和控制磁碟空間消耗之間取得了平衡。

工作階段檔案存儲在專案根目錄下的 .claw/sessions/ 目錄中，檔案名稱格式為 <session_id>.jsonl。系統還維護了一個「latest」參考，指向最近使用的工作階段。當使用者執行 claw --resume latest 時，系統會透過這個參考找到並恢復最近的工作階段。

### 11.3 工作階段的分支與分叉

Session 支援分支（fork）操作，允許使用者從一個現有的工作階段中創建一個新的分支，保留完整的歷史記錄但在新分支上繼續不同的對話路徑。這個功能類似於 Git 的分支概念——主分支上的修改不會影響新分支，新分支上的修改也不會影響主分支。

分支操作透過 SessionFork 結構來記錄：parent_session_id 指向父工作階段的 ID，branch_name 記錄分支的名稱。分支操作在實作上是創建一個新的 Session，複製父工作階段的完整訊息歷史，然後獨立地進行後續的操作。這種設計讓開發者能夠在不確定的情況下安全地探索不同的解決方案——如果新分支上的嘗試失敗了，可以切回原來的工作階段繼續。

## 第十二章：設定系統深度解析

### 12.1 設定合併機制

Claw Code 的設定系統被設計為支援多層次的配置需求，從個人偏好到團隊標準、從全域預設到專案特定。這種多層設定架構的核心挑戰在於如何正確地合併來自不同來源的設定值。

ConfigLoader 的 discover 方法是設定合併的入口點。它會按照優先級從低到高的順序依次嘗試讀取五個設定檔案路徑。對於每個存在的檔案，ConfigLoader 會讀取其 JSON 內容並解析為一個鍵值對的樹狀結構。然後，所有讀取到的設定會按照優先級順序進行深度合併。

深度合併的規則是：對於同名的鍵，如果兩邊的值都是物件（JSON Object），則遞迴地合併兩個物件；如果兩邊的值類型不同，或者都是非物件類型（字串、數字、陣列、布林值），則高優先級的值直接覆蓋低優先級的值。這意味著使用者可以在全域設定中定義一個完整的 mcpServers 物件，然後在專案設定中只覆蓋特定的伺服器設定，而不會丟失全域設定中的其他伺服器。

特別值得注意的是 .claw/settings.local.json 這個最高優先級的設定檔案。它的設計意圖是用於存放個人偏好和敏感資訊（如 API 金鑰路徑），應該被加入 .gitignore 中以避免被提交到版本控制系統。這確保了團隊成員可以共享專案設定（透過 .claw.json 和 .claw/settings.json），同時每個人還能保有自己的個人配置。

### 12.2 RuntimeFeatureConfig 結構

合併後的原始 JSON 設定會被解析為 RuntimeFeatureConfig 結構，這是 Claw Code 在運行時期使用的型別安全的設定表示。RuntimeFeatureConfig 包含以下主要欄位和子結構：

model 欄位是可選的模型名稱覆蓋。aliases 是一個有序映射，定義了自訂的模型別名。permission_mode 是可選的權限模式覆蓋。trusted_roots 是信任的檔案系統根路徑列表。

RuntimeHookConfig 子結構定義了三種勾子的命令列表：pre_tool_use 在工具執行前觸發、post_tool_use 在工具執行後觸發、post_tool_use_failure 在工具執行失敗後觸發。每個勾子是一個 Shell 命令字串，系統會在觸發時透過 Shell 執行它。

RuntimePluginConfig 子結構定義了外掛系統的設定：enabled_plugins 是一個映射，指定哪些外掛應該被啟用；external_directories 列出了額外的外掛搜尋目錄；install_root 和 registry_path 分別指定外掛的安裝根目錄和註冊表路徑。

McpConfigCollection 子結構包含所有 MCP 伺服器的設定。每個伺服器的設定被包裝在 ScopedMcpServerConfig 中，内部的 McpServerConfig 指定了傳輸方式（Stdio、SSE、HTTP、WebSocket、SDK 或 ManagedProxy）及其對應的連接參數。

SandboxConfig 子結構控制沙箱的行為：enabled 旗標控制是否啟用沙箱；namespace_restrictions 控制是否啟用命名空間限制；network_isolation 控制是否隔離網路；filesystem_mode 指定檔案系統隔離模式（Off、WorkspaceOnly 或 AllowList）；allowed_mounts 列出了在 AllowList 模式下允許的掛載點。

RuntimePermissionRuleConfig 子結構定義了細粒度的權限規則，包含三個列表：allow 列出了應該自動允許的工具名稱、deny 列出了應該自動拒絕的工具名稱、ask 列出了每次使用時都應該詢問使用者的工具名稱。

ProviderFallbackConfig 子結構定義了模型提供商的回退策略：primary 指定主要提供商、fallbacks 列出了回退提供商的清單。當主要提供商不可用時，系統會依序嘗試回退提供商。

### 12.3 設定驗證

config_validate 模組負責對合併後的設定進行全面的驗證。驗證結果以 ConfigDiagnostic 列表的形式回傳，每個診斷項包含一個 DiagnosticKind（診斷類型）和一段人類可讀的描述訊息。

驗證涵蓋的檢查項目包括：模型名稱的有效性（是否能被解析為已知的提供商）、MCP 伺服器設定的完整性（Stdio 類型是否指定了 command，SSE 類型是否指定了 url）、權限規則的一致性（同一個工具不應該同時出現在 allow 和 deny 清單中）、沙箱設定的合理性（AllowList 模式是否指定了至少一個 allowed_mount）、以及檔案路徑的存在性（外掛目錄是否存在）。

驗證結果會在系統啟動時呈現給使用者，警告類型的診斷不會阻止啟動，錯誤類型的診斷則會導致啟動失敗並提示使用者修正設定。這種啟動時驗證的策略能夠盡早地發現設定問題，避免在使用過程中才遇到因設定錯誤導致的意外行為。

### 10.4 提示詞工程的系統化方法

SystemPromptBuilder 是 Claw Code 中負責組裝系統提示詞的核心元件。系統提示詞的品質直接影響 AI 模型的行為品質——一個好的系統提示詞能夠讓模型更準確地理解工作環境、更恰當地選擇工具、更安全地執行操作。

SystemPromptBuilder 組裝系統提示詞時會整合多種上下文資訊。首先是專案上下文（ProjectContext），包括專案的目錄結構（重要的檔案和目錄列表）、程式語言和框架的偵測結果、README 或 CLAUDE.md 等專案說明文件的內容。這些資訊幫助 AI 模型理解它正在工作的專案是什麼類型、使用了什麼技術棧、有什麼特殊的約定。

其次是 Git 上下文，由 git_context.rs 提供。GitContext 包含當前分支名稱、最近的提交歷史（通常是最近幾次提交的訊息和作者）、以及暫存區的狀態（是否有未提交的變更）。這些資訊讓 AI 模型了解當前的開發狀態——是否在功能分支上工作、最近做了什麼變更、是否有需要提交的修改。

再次是工具定義列表。系統提示詞中包含所有可用工具的名稱、描述和輸入 Schema，讓 AI 模型知道它可以使用哪些工具、每個工具需要什麼參數。這個列表是動態生成的，會根據當前載入的外掛和 MCP 伺服器而變化。

最後是使用者自訂的指令。使用者可以在設定檔或 CLAUDE.md 文件中添加自訂指令，這些指令會被注入到系統提示詞中。例如，使用者可能指定「永遠使用 TypeScript 而不是 JavaScript」或「在修改程式碼前先執行測試」等偏好。

ContextFile 型別代表被納入系統提示詞的上下文檔案。每個 ContextFile 包含檔案路徑和內容，系統會將所有上下文檔案的內容拼接到系統提示詞的適當位置。上下文檔案的來源包括：設定中指定的固定檔案（如 .claw/context.md）、自動偵測的專案說明文件（如 README.md、CLAUDE.md）以及使用者在對話中明確要求加入的檔案。

### 10.5 串流事件處理的細節

AssistantEvent 列舉型別定義了 ConversationRuntime 在處理 AI 回應時可能遇到的所有事件類型。TextDelta 事件攜帶增量的文字內容，是最頻繁出現的事件類型。在一次典型的 AI 回應中，可能會收到數十甚至數百個 TextDelta 事件，每個事件攜帶幾個到幾十個字元的增量文字。ConversationRuntime 收到 TextDelta 事件後，會立即將增量文字轉發到 CLI 層的 TerminalRenderer。

TerminalRenderer 負責將增量的 Markdown 文字即時轉換為終端輸出。這個轉換過程需要處理多種複雜情況：當收到程式碼區塊的開始標記時，需要切換到語法高亮渲染模式；當收到列表項目時，需要處理縮排和符號；當收到標題時，需要添加格式化效果。增量渲染的挑戰在於，Markdown 的語法結構可能跨越多個 TextDelta 事件——例如，一個程式碼區塊的開始標記 ``` 可能出現在一個事件中，而語言標籤 rust 出現在下一個事件中。TerminalRenderer 需要維護一個解析狀態機來處理這些跨事件的語法結構。

Spinner 動畫是另一個重要的終端渲染元素。當 AI 正在思考（收到 TextDelta 之前）或正在執行工具呼叫時，終端會顯示一個旋轉的動畫效果，讓使用者知道系統正在工作。Spinner 使用 crossterm 函式庫的游標控制功能實現——每隔一段時間（通常是一百毫秒），Spinner 會將游標移回到動畫的位置，擦除舊的字元，寫入新的字元，產生旋轉的視覺效果。

ToolUse 事件包含三個關鍵欄位：id（工具呼叫的唯一標識符，後續的 ToolResult 會引用這個 ID）、name（工具名稱）和 input（工具輸入參數的 JSON 物件）。收到 ToolUse 事件後，系統會在終端顯示一個工具呼叫的摘要資訊（工具名稱和關鍵參數），然後啟動工具呼叫流程。

ThinkingDelta 事件攜帶 AI 模型的思考過程文字。這是 Anthropic 的 extended thinking 功能提供的能力，讓 AI 模型可以在生成正式回應之前進行一段內部推理。思考過程的文字通常不會直接顯示給使用者，但會被記錄在工作階段中供後續分析。SignatureDelta 事件攜帶思考過程的簽章，用於驗證思考內容的完整性。

### 10.6 自動壓縮的觸發機制

自動壓縮是 Claw Code 管理長時間對話的關鍵機制。CompactionConfig 結構定義了壓縮的配置參數：token_threshold 是觸發壓縮的 token 總量閾值（預設為十萬個 token），retain_recent_count 是壓縮時保留的最近訊息數量（預設為四則）。

壓縮的觸發邏輯嵌入在每個對話回合的結尾。當 ConversationRuntime 完成一個回合（收到 message_stop 事件並更新 UsageTracker）後，它會計算當前工作階段中所有訊息的 token 總量。如果總量超過 token_threshold，系統會自動觸發壓縮流程。

壓縮流程的第一步是確定需要移除多少訊息。系統從最舊的訊息開始計算，累加每則訊息的 token 數量，直到移除足夠的訊息使得剩餘訊息的 token 總量降到閾值以下。但無論如何，最近的 retain_recent_count 則訊息永遠不會被移除。

第二步是產生壓縮摘要。系統會將要移除的訊息發送給 AI 模型，要求它產生一段簡短的摘要，概述這些訊息中的關鍵資訊。這個摘要會被儲存在 SessionCompaction 結構中，包含壓縮次數（count）、移除的訊息數量（removed_message_count）和摘要文字（summary）。

第三步是重建工作階段。壓縮後的工作階段包含三個部分：壓縮摘要（作為系統提示詞的一部分注入）、一個分隔標記（說明以下內容是壓縮後保留的近期對話）、以及最近的 retain_recent_count 則訊息。這樣，AI 模型在後續的對話中仍然能夠透過摘要了解之前的上下文，但不需要處理所有的歷史訊息。

summary_compression.rs 模組負責控制摘要文字的長度。SummaryCompressionBudget 定義了摘要的上限——最多一千二百個字元或二十四行。如果自動產生的摘要超過這個限制，系統會進一步壓縮摘要文字，確保它不會佔用過多的 token 預算。

## 第十一章：工作階段管理（擴展）

### 11.4 工作區指紋與工作階段關聯

session_control.rs 實現了 SessionStore，負責管理工作階段的存儲和檢索。SessionStore 使用工作區指紋（workspace fingerprint）來建立工作階段與特定專案之間的關聯。工作區指紋是基於工作區根目錄的絕對路徑計算的雜湊值，確保不同的專案有不同的指紋，即使它們的目錄名稱相同。

當使用者執行 --resume latest 時，系統會首先計算當前工作區的指紋，然後在 .claw/sessions/ 目錄中搜尋與該指紋關聯的最新工作階段。這確保了恢復的工作階段與當前的專案相對應，避免了在不同專案之間混淆工作階段的問題。

SessionStore 還負責工作階段的清理工作。長時間使用後，sessions 目錄中可能積累大量的工作階段檔案。SessionStore 提供了清理方法，可以刪除超過指定天數的舊工作階段，釋放磁碟空間。

### 11.5 JSONL 格式的邊緣情況處理

雖然 JSONL 格式在大多數情況下運作良好，但在某些邊緣情況下需要特殊處理。

第一個邊緣情況是不完整的最後一行。如果程式在寫入一行 JSON 的過程中意外終止（例如被作業系統的 OOM killer 終止），JSONL 檔案的最後一行可能是不完整的 JSON。工作階段載入邏輯需要能夠偵測和跳過這種不完整的行，而不是因為解析錯誤而拒絕載入整個工作階段。

第二個邊緣情況是 Unicode 字元的處理。在某些語言環境中，使用者的輸入或 AI 的回應可能包含各種 Unicode 字元，包括多位元組字元、表情符號、以及從右到左書寫的文字。JSONL 的序列化和反序列化需要正確地處理這些字元，確保資料的完整性。serde_json 函式庫已經內建了完整的 Unicode 支援，但在計算字串長度和 token 數量時，需要注意區分位元組數量和字元數量。

第三個邊緣情況是同時寫入的衝突。雖然 Claw Code 通常是單一程序運行的，但在某些場景下（如透過 MCP 伺服器觸發的遠端操作），可能存在多個程序嘗試寫入同一個工作階段檔案的情況。JSONL 的追加寫入模式在大多數檔案系統上是原子的（每次 write 系統呼叫寫入的資料不會與其他 write 呼叫交錯），但為了更高的可靠性，Claw Code 在寫入時使用檔案鎖（file lock）來確保互斥。

## 第十二章：設定系統深度解析（擴展）

### 12.4 環境變數覆蓋

除了設定檔之外，Claw Code 的許多設定還可以透過環境變數進行覆蓋。環境變數的優先級高於所有設定檔，因為它們通常代表的是部署時期的動態配置需求。

ANTHROPIC_API_KEY 是最重要的環境變數，提供 Anthropic API 的認證金鑰。ANTHROPIC_AUTH_TOKEN 提供 OAuth Bearer Token。ANTHROPIC_MODEL 覆蓋設定檔中指定的模型名稱。CLAW_MODEL 是 ANTHROPIC_MODEL 的別名。CLAW_SANDBOX_ENABLED 強制啟用或停用沙箱。CLAW_PERMISSION_MODE 覆蓋設定檔中指定的權限模式。

HTTP 代理相關的環境變數也被自動偵測：HTTP_PROXY 和 http_proxy 設定 HTTP 代理 URL；HTTPS_PROXY 和 https_proxy 設定 HTTPS 代理 URL；NO_PROXY 和 no_proxy 設定代理排除清單。系統同時支援大寫和小寫的環境變數名稱，以相容不同作業系統的慣例。

對於 OpenAI 相容的提供商，OPENAI_API_KEY 提供 API 金鑰，OPENAI_BASE_URL 覆蓋預設的 API 端點 URL（例如設定為 Ollama 的本地地址 http://localhost:11434/v1）。對於 xAI，XAI_API_KEY 提供 API 金鑰。對於 DashScope，DASHSCOPE_API_KEY 提供 API 金鑰。

### 12.5 設定診斷報告

config_validate.rs 模組在驗證設定時會產生 ConfigDiagnostic 列表。每個診斷項包含三個欄位：kind（診斷類型，可以是 Warning 或 Error）、path（設定項的路徑，如 mcpServers.github.command）、以及 message（人類可讀的描述訊息）。

Warning 類型的診斷表示設定可能有問題但不會阻止系統運行。例如：模型名稱不在已知列表中（可能是使用者指定了一個新發布的模型）、外掛目錄不存在（可能外掛還沒有安裝）、MCP 伺服器的命令包含空格（可能需要引號）。

Error 類型的診斷表示設定有嚴重問題，會阻止系統正常運行。例如：沒有提供任何認證資訊（API 金鑰和 OAuth token 都沒有設定）、MCP 伺服器的 type 欄位值不在支援的列表中、權限規則中的同一個工具同時出現在 allow 和 deny 清單中。

診斷報告在系統啟動時被生成和呈現。對於 Warning 類型的診斷，系統會在終端顯示黃色的警告訊息但繼續啟動。對於 Error 類型的診斷，系統會在終端顯示紅色的錯誤訊息並退出。這種策略確保了設定問題能夠被盡早發現，同時不會因為可以忽略的警告而阻止使用者的正常使用。

### 12.6 設定的動態重載

在 REPL 模式下，使用者可以透過 /config 斜線命令查看當前的設定值。更重要的是，某些設定可以在運行時動態修改。例如，/model 命令可以切換使用的模型，/permissions 命令可以變更權限模式，/sandbox 命令可以查看和修改沙箱設定。

動態設定修改的實作需要特別注意執行緒安全性。由於 ConversationRuntime 可能在非同步的 tokio 任務中運行，而 REPL 的輸入處理在另一個任務中運行，設定的修改需要透過適當的同步機制（如 RwLock 或 watch channel）來確保一致性。Claw Code 使用了 tokio 的 watch channel 來廣播設定變更——當使用者透過斜線命令修改設定時，新的設定值會被發送到 watch channel，ConversationRuntime 在每個回合開始時會檢查 watch channel 中是否有新的設定值。

### 10.7 REPL 模式的互動細節

REPL（Read-Eval-Print Loop）模式是 Claw Code 最常用的互動方式。讓我們深入了解 REPL 迴圈的每一個步驟以及它提供的豐富互動功能。

REPL 迴圈的核心是一個無限迴圈。每一次迭代中，系統首先透過 rustyline 顯示提示符號（通常是 claw> 或包含當前模型名稱的自訂提示）。rustyline 提供了類似 GNU readline 的編輯體驗——使用者可以使用方向鍵在行內移動游標、使用 Ctrl+A 和 Ctrl+E 跳到行首和行尾、使用 Ctrl+W 刪除一個詞、使用 Ctrl+K 刪除到行尾。

歷史記錄功能讓使用者可以用上下方向鍵瀏覽之前輸入的命令。歷史記錄被持久化存儲，即使退出程式再重新進入，之前的輸入歷史仍然可用。SlashCommandHelper 提供了斜線命令的 Tab 補全——當使用者輸入 / 然後按 Tab 鍵時，系統會列出所有匹配的斜線命令。

使用者的輸入被分為三類處理。如果輸入以 / 開頭，它被視為斜線命令，路由到 commands crate 進行處理。commands crate 會解析命令名稱（可能是別名）和參數，找到對應的命令處理器並執行。如果輸入為空（使用者直接按 Enter），系統會顯示一個提示訊息並等待新的輸入。其他所有輸入都被視為自然語言提示詞，交給 ConversationRuntime 進行對話處理。

ReadOutcome 列舉型別定義了 REPL 輸入讀取的所有可能結果：Line（使用者輸入了一行文字）、Interrupted（使用者按了 Ctrl+C）、Eof（使用者按了 Ctrl+D 或輸入流結束）以及 Error（讀取過程中發生錯誤）。Interrupted 的處理邏輯取決於當前狀態——如果系統正在等待使用者輸入，Ctrl+C 會清除當前輸入行；如果系統正在執行 AI 對話或工具呼叫，Ctrl+C 會嘗試中斷當前的操作。Eof 通常觸發程式退出。

### 10.8 一次性模式的工作機制

一次性提示模式適合腳本化和自動化場景。在這種模式下，使用者透過命令列參數提供提示詞，Claw Code 處理完一輪對話後自動退出。

一次性模式的典型使用方式是 claw prompt 文字，其中文字是使用者的提示詞。如果提示詞較長或包含特殊字元，可以用引號包裹。一次性模式還支援從標準輸入讀取提示詞，這讓管道操作成為可能——例如，可以將一個檔案的內容透過管道傳遞給 Claw Code 進行分析。

在一次性模式中，AI 的回應會被輸出到標準輸出，這讓 Claw Code 可以被整合進更大的自動化工作流程中。例如，可以在 CI 管線中使用 Claw Code 來自動化程式碼審查、產生文件摘要或分析測試失敗的原因。退出碼反映了處理結果——正常完成返回零，發生錯誤返回非零值。

一次性模式也支援工具呼叫。如果 AI 模型在處理提示詞時決定需要使用工具（例如讀取檔案或執行命令），工具呼叫會被正常執行，結果會被回饋給模型，模型會繼續生成回應。整個過程是自動化的，不需要使用者的額外輸入（除非在 Prompt 權限模式下，某些操作需要使用者確認）。

### 11.6 工作階段的生命週期事件

工作階段的生命週期可以從一個狀態機的角度來理解。工作階段從 Created 狀態開始——當 Session 物件被建立時，它包含一個唯一的 session_id、當前時間的建立時間戳記、工作區路徑和模型名稱，但還沒有任何訊息。

當第一則訊息（通常是使用者輸入）被添加到工作階段時，它進入 Active 狀態。在 Active 狀態下，工作階段持續接收新的訊息——使用者輸入、AI 回應、工具呼叫、工具結果——每則訊息都被追加到訊息歷史中。

當工作階段的 token 總量超過壓縮閾值時，compact_session 方法會被呼叫，工作階段進入短暫的 Compacted 狀態。壓縮過程中，舊訊息被移除並產生摘要，然後工作階段回到 Active 狀態繼續接收新訊息。SessionCompaction 結構中的 count 欄位記錄了工作階段被壓縮的總次數。

每次新訊息被添加或壓縮完成後，工作階段會被 Saved 到磁碟。儲存操作是追加寫入——新訊息被序列化為一行 JSON 並追加到 JSONL 檔案末尾。如果檔案大小超過旋轉閾值（二百五十六 KB），系統會建立新檔案並歸檔舊檔案。

已儲存的工作階段可以被 Resumed（恢復）。當使用者執行 --resume latest 或 /resume 命令時，系統從 JSONL 檔案中逐行讀取並重建工作階段的訊息歷史。恢復後的工作階段進入 Active 狀態，可以繼續接收新訊息。

Fork（分支）操作建立一個新的工作階段，複製父工作階段的完整訊息歷史。新的工作階段有自己的 session_id 和 JSONL 檔案，但 SessionFork 結構記錄了它的父工作階段 ID 和分支名稱。

最終，當使用者退出程式或發出 /clear 命令時，工作階段結束。退出前的最後一次儲存確保了所有資料都被持久化。

### 12.7 OAuthConfig 與 OAuth 認證流程

oauth.rs 實現的 PKCE S256 OAuth 認證流程是 Claw Code 支援的認證方式之一。PKCE（Proof Key for Code Exchange）是 OAuth 2.0 的一個安全擴充，專門設計用於無法安全存儲客戶端密鑰的公開客戶端（如命令列工具）。

S256 是 PKCE 的一種程式碼挑戰方法。在認證流程開始時，系統生成一個隨機的 code_verifier 字串，然後計算它的 SHA-256 雜湊值作為 code_challenge。code_challenge 被包含在授權請求中，而 code_verifier 被保留在本地。當授權伺服器回傳授權碼後，系統使用 code_verifier 來交換存取 token。授權伺服器會驗證 code_verifier 的雜湊值是否與之前收到的 code_challenge 匹配，確保 token 交換請求確實來自發起授權的同一個客戶端。

PkceCodePair 結構包含 code_verifier 和 code_challenge 兩個字串。OAuthTokenSet 結構包含存取 token（access_token）、重新整理 token（refresh_token）和過期時間（expires_at）。系統會在 token 即將過期時自動使用 refresh_token 來獲取新的 access_token，確保認證狀態的連續性。

OAuth 認證流程在互動式模式下的體驗是：系統在終端顯示一個授權 URL，使用者在瀏覽器中開啟該 URL 並完成授權（通常涉及登入和同意畫面），授權完成後瀏覽器會被重導向到一個本地的回調 URL。Claw Code 會啟動一個臨時的 HTTP 伺服器來接收回調，從回調的查詢參數中提取授權碼，然後使用授權碼和 code_verifier 交換 token。

### 12.8 ProviderFallbackConfig 與多提供商回退

ProviderFallbackConfig 結構定義了模型提供商的回退策略。primary 欄位指定主要的模型名稱或提供商，fallbacks 欄位列出一個或多個回退選項。

回退機制的工作方式是：系統首先嘗試使用 primary 指定的模型。如果因為 API 呼叫失敗（例如服務暫時不可用、速率限制、或者模型不存在），系統會依序嘗試 fallbacks 列表中的每一個選項。回退嘗試使用相同的請求內容，只改變模型名稱和對應的提供商設定。

這種回退機制在企業環境中非常有用。例如，一個團隊可能將 Claude Opus 設定為主要模型（提供最好的推理能力），將 Claude Sonnet 設定為第一回退選項（在 Opus 不可用時提供較好的能力），將 Claude Haiku 設定為第二回退選項（確保基本功能的可用性）。甚至可以跨提供商設定回退——例如，將 Anthropic 的 Claude 設定為主要選項，將 OpenAI 的 GPT 設定為回退選項。

回退的觸發條件包括：HTTP 5xx 伺服器錯誤、429 速率限制（如果重試次數已耗盡）、網路連線錯誤和認證失敗。不觸發回退的情況包括：API 請求格式錯誤（4xx 客戶端錯誤，除了 429）和正常的工具呼叫流程。


### 12.9 aliases 與自訂命令別名

RuntimeFeatureConfig 中的 aliases 欄位是一個 BTreeMap，將自訂的命令別名映射到完整的命令或模型名稱。使用者可以在設定檔中定義自己的別名，簡化常用操作的輸入。

例如，使用者可以定義 fast 別名指向 claude-haiku-4-5-20251213（成本最低的模型），定義 smart 別名指向 claude-opus-4-6（能力最強的模型），定義 balanced 別名指向 claude-sonnet-4-6（能力和成本的平衡）。然後在使用時，只需要輸入 claw --model fast 就能快速切換到最便宜的模型。

別名的解析優先於系統內建的別名。這意味著使用者可以覆蓋系統預設的別名——例如，將 opus 重新定義為指向不同的模型。別名的解析是遞迴的——一個別名可以指向另一個別名，但系統會偵測並拒絕循環引用。

### 12.10 trusted_roots 的安全意義

RuntimeFeatureConfig 中的 trusted_roots 欄位列出了被信任的檔案系統根路徑。這個設定主要用於多工作區的場景——當 Claw Code 需要存取工作區之外的路徑時（例如共享的函式庫目錄），使用者可以將這些路徑加入 trusted_roots，讓系統允許讀取這些目錄中的檔案。

trusted_roots 只擴充了讀取權限的邊界，不影響寫入權限。即使一個路徑被加入 trusted_roots，工作區寫入模式下的寫入操作仍然被限制在工作區根目錄內。這種設計確保了 trusted_roots 不會成為安全漏洞——它只讓 AI 模型能夠「看到」更多的檔案，而不能「修改」更多的檔案。

trusted_roots 的使用需要謹慎。將一個包含敏感資訊的目錄（如 ~/.ssh/ 或 ~/.gnupg/）加入 trusted_roots 是不推薦的，因為這會讓 AI 模型能夠讀取其中的金鑰和憑證。一般建議只將專案相關的共享資源目錄加入 trusted_roots。

### 10.9 子命令模式的實作

除了 REPL 模式和一次性模式之外，Claw Code 還支援多種子命令。每個子命令是一個獨立的功能單元，執行完特定的任務後退出。

claw init 子命令在當前目錄初始化 Claw Code 的設定。它會建立 .claw.json 設定檔（包含基本的預設設定）和 .gitignore 檔案中的相關規則（確保敏感的本地設定檔和工作階段資料不被提交到版本控制）。init 子命令還會偵測專案的類型（Rust、JavaScript、Python 等）並產生適當的預設設定。InitStatus 列舉記錄了初始化的結果——Created（成功建立新設定）、AlreadyExists（設定已存在，跳過）或 Error（初始化過程中發生錯誤）。InitReport 結構提供了初始化的詳細報告，包括建立了哪些檔案、跳過了哪些檔案。

claw doctor 子命令執行系統健康檢查。它會依序檢查：Rust 工具鏈是否安裝（嘗試執行 rustc --version）、Git 是否可用（嘗試執行 git --version）、API 認證是否配置（檢查環境變數和 OAuth token）、沙箱是否可用（嘗試執行 unshare --help）、設定檔是否存在且語法正確（嘗試載入和解析設定檔）。每個檢查項目會被標記為通過、警告或失敗，最終產生一個健康報告。

claw status 子命令顯示當前工作區的狀態資訊，包括 Claw Code 的版本、當前的設定來源、已配置的模型和提供商、權限模式、沙箱狀態、以及最近的工作階段資訊。

### 11.7 工作階段的效能最佳化

對於長時間的工作階段（可能包含數百甚至數千則訊息），工作階段的載入和儲存效能變得重要。Claw Code 採用了幾種最佳化策略來確保工作階段操作的高效性。

追加寫入最佳化：每次新增訊息時，只需要將一行 JSON 追加到檔案末尾。這是一個 O(1) 的操作，不受工作階段大小的影響。相比之下，如果使用單一 JSON 檔案格式，每次修改都需要重新序列化和寫入整個檔案，是 O(n) 的操作。

懶序列化：ContentBlock 的序列化被推遲到實際寫入時才執行。在對話過程中，ContentBlock 以 Rust 原生型別的形式存在於記憶體中，享受 Rust 高效的記憶體管理。只有在需要持久化時，才會執行 JSON 序列化。

選擇性載入：當恢復工作階段時，如果工作階段有多個旋轉檔案，系統會先載入最新的檔案。只有在需要更早的歷史記錄時（例如壓縮時需要計算總 token 量），才會載入較舊的檔案。

Buffer 寫入：系統不是對每則訊息都執行一次 fsync 系統呼叫，而是使用 BufWriter 進行緩衝寫入。多則訊息會被批量寫入磁碟，減少 I/O 系統呼叫的次數。在回合結束時才執行 fsync，確保資料的持久性。


### 10.10 ColorTheme 與終端渲染的細節

TerminalRenderer 使用 ColorTheme 結構來定義終端輸出的顏色方案。不同類型的內容使用不同的顏色——AI 的文字回應使用預設的終端前景色、工具呼叫的提示使用青色、錯誤訊息使用紅色、警告使用黃色、系統資訊使用灰色。

Markdown 渲染是 TerminalRenderer 最複雜的功能之一。pulldown-cmark 函式庫將 Markdown 文字解析為一系列事件——標題開始、段落開始、程式碼區塊開始、行內程式碼、粗體、斜體等。TerminalRenderer 逐一處理這些事件，將它們轉換為對應的 ANSI 格式化序列。

對於程式碼區塊，syntect 函式庫提供了語法高亮功能。syntect 內建了數百種程式語言的語法定義，能夠正確地高亮顯示 Rust、Python、JavaScript、Go、Java 等幾乎所有主流程式語言的程式碼。程式碼區塊的語言標籤（如 rust 或 python）被用於選擇正確的語法定義。如果沒有提供語言標籤，syntect 會嘗試自動偵測語言。

增量渲染的挑戰在於 Markdown 的語法結構可能跨越多個 SSE 事件。例如，一個包含程式碼區塊的回應可能以這樣的順序到達：第一個 TextDelta 包含一段文字和 ``` 的前兩個字元、第二個 TextDelta 包含第三個 ` 和語言標籤、後續的 TextDelta 包含程式碼內容。TerminalRenderer 需要維護一個解析狀態來處理這些跨事件的語法邊界。

### 11.8 Session 的序列化格式

Session 的 JSONL 序列化格式值得詳細了解，因為它直接影響了工作階段的可攜性和長期可維護性。

每行 JSON 代表一個「事件」，有以下幾種類型：session_start（標記工作階段的開始，包含 session_id、model、workspace_root 等元資料）、message（一則對話訊息，包含 role 和 content 欄位）、compaction（壓縮事件，包含壓縮摘要和移除的訊息數量）、以及 metadata_update（元資料更新，如模型切換或權限模式變更）。

這種事件化的序列化格式有一個重要的優勢：它是追加式的——新事件只需要追加到檔案末尾，不需要修改已寫入的內容。這意味著 JSONL 檔案天然地形成了一個事件日誌（event log），記錄了工作階段的完整歷史。即使工作階段被壓縮，壓縮事件也被記錄在日誌中，保留了壓縮的審計追蹤。

在載入工作階段時，系統逐行讀取 JSONL 檔案，根據事件類型進行不同的處理：session_start 事件初始化 Session 結構的元資料；message 事件添加訊息到歷史記錄中；compaction 事件清除被壓縮的訊息並設定壓縮摘要；metadata_update 事件更新對應的元資料欄位。

這種格式的另一個優勢是工具友好性。使用者可以用標準的文字處理工具（如 grep、jq）來檢查和分析工作階段的內容。例如，用 jq 過濾出所有工具呼叫事件，可以了解 AI 模型在工作階段中執行了哪些操作。

### 12.11 設定的繼承與覆蓋語意

Claw Code 的五層設定合併遵循一套精確的繼承與覆蓋語意。理解這些語意對於正確地組織設定檔案至關重要。

對於簡單型別的欄位（字串、數字、布林值），覆蓋語意非常直接：高優先級的值完全取代低優先級的值。例如，如果全域設定指定 model 為 claude-sonnet-4-6，而專案設定指定 model 為 claude-haiku-4-5-20251213，最終使用的模型就是 claude-haiku-4-5-20251213。

對於物件型別的欄位（JSON Object），覆蓋語意是深度合併：兩個物件的鍵會被合併，相同鍵的值遵循上述規則遞迴處理。例如，如果全域設定的 mcpServers 包含 server_a 和 server_b 的配置，而專案設定的 mcpServers 只包含 server_c 的配置，最終的 mcpServers 會包含三個伺服器的配置。如果專案設定也包含 server_a 但使用不同的設定值，server_a 的設定會被專案設定覆蓋。

對於陣列型別的欄位（JSON Array），覆蓋語意是完全替換：高優先級的陣列完全取代低優先級的陣列，不進行元素級別的合併。例如，如果全域設定的 permissions.allow 列表包含 read_file 和 glob_search，而專案設定的 permissions.allow 列表包含 bash，最終的 allow 列表只包含 bash。這種設計的原因是陣列的元素通常沒有穩定的鍵來進行匹配和合併。

null 值（JSON null）有特殊的語意——在高優先級的設定中將一個欄位設定為 null，表示「明確地清除這個欄位」。例如，如果全域設定指定了 model，而專案設定將 model 設定為 null，最終的效果是沒有模型覆蓋，系統會使用預設值。

.claw/settings.local.json 的特殊地位在於它的預期用途——存放個人化的覆蓋和敏感資訊。這個檔案應該被加入 .gitignore，確保它不會被提交到版本控制系統。典型的 .claw/settings.local.json 內容可能包括：個人偏好的模型名稱、自訂的模型別名、個人的權限規則偏好、以及 API 金鑰的路徑或值。


### 10.11 錯誤恢復的使用者體驗

在對話過程中，各種錯誤都可能發生——網路中斷、API 服務暫時不可用、工具執行逾時、權限被拒絕。Claw Code 對每種錯誤都設計了特定的恢復策略，確保使用者能夠以最小的干擾繼續工作。

網路相關的錯誤（如連線被拒、DNS 解析失敗、TLS 握手失敗）會觸發自動重試。系統會在終端顯示一個簡短的提示（如「網路錯誤，正在重試...」），然後等待一段時間後重新發送請求。重試使用指數退避策略——第一次等待兩秒，第二次等待四秒，第三次等待八秒。如果連續三次重試都失敗，系統會顯示完整的錯誤訊息並讓使用者決定下一步行動。

API 速率限制（HTTP 429）的處理更加精細。Anthropic 的 429 回應通常包含 Retry-After 標頭，指定需要等待的秒數。系統會遵循這個指示，在終端顯示倒計時，然後在指定時間後重試。這確保了系統不會因為過於頻繁的重試而加重速率限制。

工具執行錯誤（如 Bash 命令逾時、檔案不存在、權限不足）不會中斷對話流程。錯誤會被封裝為 ToolResult（is_error 設定為 true），回傳給 AI 模型。模型通常能夠根據錯誤訊息調整策略——例如，如果讀取檔案失敗是因為路徑錯誤，模型可能會先使用 glob_search 找到正確的路徑，然後重新嘗試讀取。

權限被拒絕的工具呼叫也不會中斷對話。拒絕的原因會被清楚地傳遞給 AI 模型，模型可能會嘗試使用替代的方法（例如，如果 bash 被拒絕，模型可能會改用 read_file 和 write_file 來完成相同的操作）。

### 11.9 工作階段的容量規劃

對於長時間使用 Claw Code 的團隊，了解工作階段的儲存消耗並進行容量規劃是重要的。

一個典型的對話回合會在 JSONL 檔案中產生兩到四行 JSON——一行使用者輸入、一行 AI 回應（可能包含多個內容區塊和工具呼叫）、一行或多行工具結果。每行 JSON 的大小取決於內容的長度——一個簡短的文字回應可能只有幾百位元組，而一個包含大量程式碼的回應可能有幾十 KB。

根據典型的使用模式，一個小時的互動式開發工作階段大約會產生五十到二百個對話回合，對應的 JSONL 檔案大小約為一到十 MB。考慮到旋轉機制（每個檔案最大二百五十六 KB，保留三個檔案），磁碟消耗通常不會成為問題。

然而，在自動化場景中（如 CI 管線中的長時間任務），情況可能不同。一個自動化任務可能在幾分鐘內產生數百個工具呼叫，每個呼叫的結果可能包含大量的文字（如完整的建構日誌或測試輸出）。在這種場景下，建議配置更積極的壓縮策略（降低 token 閾值和保留的訊息數量），以及更頻繁的檔案旋轉。

SessionStore 提供了清理舊工作階段的功能。建議在 CI 環境中配置自動清理策略——例如，刪除超過七天的工作階段。這可以透過在 CI 管線的清理步驟中執行相應的命令來實現。


### 12.12 設定檔案的安全考量

設定檔案可能包含敏感資訊（如 API 金鑰、OAuth token、代理伺服器的認證資訊），因此需要特別的安全考量。

Claw Code 在設定系統中採用了幾種安全措施。首先，.claw/settings.local.json 被設計為存放敏感資訊的專用檔案，claw init 命令會自動將它加入 .gitignore。其次，設定檔案的讀取遵循嚴格的路徑——只讀取五個預定義路徑的設定檔案，不會讀取任意路徑的檔案，防止路徑注入攻擊。第三，設定檔案的解析使用 serde_json 的安全解析器，不執行任何使用者提供的程式碼。

對於 API 金鑰，建議使用環境變數而不是設定檔案來傳遞。環境變數的優勢是不會被意外地提交到版本控制系統，而且在程序退出後就會消失。如果必須在設定檔案中存儲敏感資訊，建議只放在 .claw/settings.local.json 中，並確保這個檔案已被正確地加入 .gitignore。

在企業環境中，可能需要使用機密管理服務（如 HashiCorp Vault、AWS Secrets Manager）來管理 API 金鑰。在這種情況下，建議使用勾子腳本在 Claw Code 啟動時從機密管理服務中獲取金鑰，並透過環境變數傳遞給系統。


### 10.12 Ctrl+C 中斷處理的精細控制

在互動式 REPL 模式中，Ctrl+C（SIGINT 信號）的處理需要精細的控制，因為使用者按 Ctrl+C 的意圖取決於當前的系統狀態。

如果系統正在等待使用者輸入（顯示提示符號時），Ctrl+C 應該清除當前的輸入行並顯示新的提示，而不是退出程式。這與傳統的 Shell 行為一致——在 Bash 中按 Ctrl+C 也只是取消當前行的輸入。

如果系統正在接收 AI 的 SSE 回應（AI 正在生成文字時），Ctrl+C 應該中斷當前的 API 呼叫，丟棄已接收但尚未完成的回應，並回到提示符號等待新的輸入。這讓使用者能夠在 AI 產生不需要的回應時快速中斷。

如果系統正在執行工具呼叫（如 Bash 命令或檔案操作時），Ctrl+C 應該嘗試終止正在執行的工具操作，但不應該丟棄之前的對話歷史。工具的中斷會被記錄為工具呼叫的結果（interrupted: true），回傳給 AI 模型讓它知道操作被中斷了。

這種精細的 Ctrl+C 處理透過 crossterm 的信號處理和 tokio 的取消機制協同實現。crossterm 的 enable_raw_mode 讓程式能夠攔截 Ctrl+C 而不是讓作業系統直接終止程序。tokio 的 CancellationToken 讓非同步任務能夠感知到取消請求並優雅地清理資源。

### 12.13 多環境設定策略

在實際的開發工作流程中，開發者通常需要在多個環境之間切換——本地開發、測試環境、預生產環境等。Claw Code 的設定系統支援透過環境變數和設定檔案的組合來管理多環境配置。

一種常見的策略是使用環境變數來選擇設定檔案組。例如，定義一個 CLAW_ENV 環境變數，值為 dev、test 或 prod。然後在 .claw/ 目錄中為每個環境建立單獨的設定檔案——settings.dev.json、settings.test.json 和 settings.prod.json。雖然 Claw Code 目前不原生支援環境選擇器，但可以透過勾子腳本實現——pre_tool_use 勾子可以根據 CLAW_ENV 的值載入對應的額外設定。

另一種策略是使用全域設定作為基礎，專案設定作為環境特定的覆蓋。例如，全域設定指定基本的模型和權限配置，每個專案的 .claw.json 指定專案特定的 MCP 伺服器和工具配置，而 .claw/settings.local.json 指定環境特定的 API 端點和認證資訊。

### 11.10 工作階段的可攜性

JSONL 格式的一個隱含優勢是工作階段的可攜性。使用者可以將 .claw/sessions/ 目錄中的 JSONL 檔案複製到另一台機器上，然後使用 --resume 參數恢復工作階段。只要目標機器上安裝了相同版本的 Claw Code，工作階段就能被正確地載入和使用。

這種可攜性在幾個場景中很有用：開發者在不同的機器之間切換工作（如從辦公室到家中）、將工作階段分享給團隊成員以展示操作歷史、或者將工作階段保存到雲端存儲作為備份。

工作階段的可攜性也讓「工作階段審查」成為可能——團隊負責人可以要求開發者分享他們的工作階段檔案，審查 AI 在開發過程中做了哪些操作、使用了哪些工具、產生了哪些修改。這在需要嚴格的程式碼審查流程的團隊中特別有價值。


### 10.13 Token 預算管理的實用策略

在實際使用中，token 預算管理是影響成本和效能的關鍵因素。理解 token 的消耗模式有助於最佳化使用策略。

一個典型的對話回合中，token 消耗的分布大致如下：系統提示詞佔輸入 token 的百分之三十到五十（包含專案上下文、工具定義和自訂指令）；訊息歷史佔輸入 token 的百分之三十到五十（包含之前的所有對話記錄）；當前的使用者輸入佔輸入 token 的百分之五到十；AI 的回應佔輸出 token 的全部。

基於這種分布，最佳化的策略包括：精簡系統提示詞（只包含真正需要的上下文資訊，避免將整個專案的所有檔案都包含在上下文中）；適當設定壓縮閾值（太高的閾值會導致過長的訊息歷史增加成本，太低的閾值會導致頻繁的壓縮損失上下文）；選擇合適的模型（簡單的任務使用 Haiku 而不是 Opus，可以節省大量成本）。

使用提示詞快取是另一個重要的成本最佳化手段。如前所述，快取讀取的成本只有正常輸入的十分之一。在長時間的工作階段中，系統提示詞在每個回合都會被重複發送——如果啟用了快取，從第二個回合開始就可以享受十倍的成本節省。

/cost 命令的輸出可以作為調整策略的依據。如果發現快取讀取的比例很低，可能需要檢查快取是否正確啟用。如果發現輸出 token 的成本佔比很高，可能是因為 AI 模型產生了過於詳細的回應——可以在系統提示詞中添加「簡潔回應」的指令來改善。

### 12.14 ConfigLoader 的實作細節

ConfigLoader 的 discover 方法實作了完整的設定發現和合併邏輯。讓我們追蹤這個方法的執行流程。

第一步是確定五個設定檔案的路徑。家目錄的路徑透過環境變數 HOME 獲取（在 macOS 上也檢查 HOME 環境變數，在 WSL 上則使用 Linux 的 HOME）。使用者設定目錄的路徑是 $HOME/.config/claw/。專案根目錄的路徑透過向上遍歷目錄樹來查找——從當前工作目錄開始，逐層向上查找包含 .claw.json 或 .claw/ 目錄的目錄，直到找到或到達檔案系統的根目錄。

第二步是按順序讀取每個路徑的設定檔案。對於每個路徑，ConfigLoader 首先檢查檔案是否存在。如果存在，讀取其 JSON 內容並解析為 serde_json::Value 型別。如果讀取或解析失敗，錯誤會被記錄但不會阻止後續檔案的處理——一個損壞的低優先級設定檔案不應該阻止系統從高優先級的設定檔案中載入設定。

第三步是深度合併。merge_json_values 遞迴函數接受兩個 Value 參數（base 和 override），根據前述的合併規則產生合併後的 Value。合併從最低優先級的設定開始，逐步覆蓋高優先級的設定值。

第四步是將合併後的 JSON Value 反序列化為 RuntimeFeatureConfig 結構。serde_json::from_value 函數負責這個轉換，它會驗證 JSON 的結構是否符合 RuntimeFeatureConfig 的定義。如果反序列化失敗（例如設定中包含了不認識的欄位類型），系統會回傳詳細的錯誤訊息，指出具體是哪個欄位出了問題。

第五步是設定驗證。config_validate::validate 函數對 RuntimeFeatureConfig 進行語意層面的驗證（而不僅僅是結構層面的驗證），產生 ConfigDiagnostic 列表。

最後，discover 方法回傳一個 DiscoveredConfig 結構，包含合併後的 RuntimeFeatureConfig、設定的來源追蹤資訊（哪些檔案被讀取了、哪些被跳過了）以及驗證診斷列表。


### 12.15 McpServerConfig 在 RuntimeFeatureConfig 中的位置

RuntimeFeatureConfig 中的 McpConfigCollection 是設定系統中最複雜的子結構之一。讓我們深入了解它的完整結構和配置語意。

McpConfigCollection 本質上是一個從伺服器名稱（字串）到 ScopedMcpServerConfig 的有序映射（BTreeMap）。使用 BTreeMap 而不是 HashMap 確保了伺服器的列舉順序是確定性的（按照名稱的字典序），這在日誌和狀態顯示中提供了一致的體驗。

ScopedMcpServerConfig 包裝了 McpServerConfig，並添加了作用域欄位（scope）。作用域記錄了這個伺服器設定來自哪個設定層級——是全域設定、使用者設定、專案設定還是本地設定。這個資訊在合併過程中用於確定優先序，在顯示設定來源時也很有用。

當設定合併引擎處理 mcpServers 區段時，它遵循物件型別的深度合併規則：如果全域設定定義了伺服器 A 和 B，專案設定定義了伺服器 B 和 C，最終的結果包含三個伺服器——A 來自全域設定、B 來自專案設定（覆蓋了全域的 B）、C 來自專案設定。每個伺服器的 ScopedMcpServerConfig 會記錄其最終的作用域來源。


### 10.14 模型選擇的策略建議

在實際使用中，模型的選擇對工作效率和成本有著巨大的影響。Claw Code 支援透過命令列旗標、環境變數或設定檔隨時切換模型，讓使用者能夠根據任務的性質選擇最合適的模型。

對於需要深度推理的複雜任務（如大規模重構、架構設計分析、複雜 bug 的診斷），推薦使用 Claude Opus 或同等級的模型。Opus 的推理能力最強，能夠處理涉及多個檔案和複雜邏輯的任務。代價是成本較高（每百萬輸入 token 十五美元，每百萬輸出 token 七十五美元）且延遲較長。

對於日常的程式碼修改和常規開發任務，推薦使用 Claude Sonnet 或同等級的模型。Sonnet 在能力和成本之間取得了良好的平衡，對於大多數的檔案編輯、測試修復和程式碼生成任務都能勝任。成本約為 Opus 的五分之一。

對於簡單的查詢和瀏覽操作（如搜尋檔案、查看文件、執行簡單的命令），推薦使用 Claude Haiku 或同等級的模型。Haiku 的成本最低（每百萬輸入 token 零點二五美元），回應速度最快，非常適合快速的互動式瀏覽。

在工作流程引擎的場景中，可以為不同的 Worker 配置不同的模型——負責核心邏輯修改的 Worker 使用 Opus，負責格式化和清理的 Worker 使用 Haiku。ProviderFallbackConfig 還允許設定回退策略，確保即使主要模型不可用時系統仍然能夠繼續工作。


### 12.16 設定系統的未來演進

Claw Code 的設定系統雖然已經相當完善，但仍有一些可能的改進方向。

環境選擇器是一個常見的需求——讓使用者能夠透過一個環境變數或命令列參數選擇不同的設定組。例如 claw --env staging 會自動載入 .claw/settings.staging.json。這種功能在需要頻繁切換環境的場景中（如在開發、測試和生產環境之間切換）非常有用。

設定的即時驗證是另一個改進方向。目前的驗證只在系統啟動時進行一次。未來可能引入在設定檔案被修改時自動重新驗證的功能（透過檔案系統監控），讓使用者在編輯設定時就能即時收到驗證反饋。

設定的圖形化介面也是一個可能的方向。雖然 Claw Code 是命令列工具，但設定的編輯可以透過 Web 界面或 TUI（Terminal User Interface）來進行，提供更直觀的設定體驗——如下拉選單選擇模型、滑桿調整壓縮閾值、樹狀視圖管理 MCP 伺服器等。


### 12.17 設定遷移的處理

當 Claw Code 的新版本改變了設定檔案的結構時，需要處理舊版本設定的遷移。ConfigLoader 在載入設定時會檢查設定的版本標記（如果存在），根據版本差異執行必要的遷移邏輯。

遷移邏輯的典型操作包括：重命名欄位（如將舊版的 sandboxEnabled 重命名為 sandbox.enabled）、調整結構（如將扁平的設定層級轉換為巢狀結構）、設定預設值（如為新增的欄位提供合理的預設值）。

遷移是自動且無損的——系統會產生一個遷移後的新設定，同時保留原始設定檔的備份（以 .bak 後綴儲存）。如果遷移失敗，系統會使用原始設定繼續啟動，並向使用者顯示遷移失敗的提示和建議。這確保了新版本的 Claw Code 不會因為設定遷移的問題而無法啟動。


這種事件驅動的設計讓 ConversationRuntime 能夠在不修改核心迴圈邏輯的情況下支援新的事件類型和處理邏輯。每個新功能的添加只需要在事件處理器中添加對應的分支，而不需要改變迴圈的基本結構。
