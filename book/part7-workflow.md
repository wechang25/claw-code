# 第七部分：工作流程引擎與進階主題

在前面的章節中，我們已經深入探討了 Claw Code 的核心對話引擎、工具系統、安全模型以及外部整合能力。這些功能構成了 Claw Code 作為一個互動式 AI 代理人的基礎。然而，Claw Code 的野心遠不止於此——它還包含一個完整的工作流程引擎，旨在支援 CI/CD 自動化、多代理人協作和大規模的程式碼修改任務。

本部分將剖析工作流程引擎的核心元件，包括 Lane 事件系統、Worker 生命週期、策略引擎、錯誤復原機制，以及其他進階主題。

---

## 第十九章：Lane 工作流程系統

### 19.1 Lane 事件驅動模型

lane_events.rs 是 Claw Code 工作流程引擎的事件基礎設施。Lane 是一個抽象概念，代表一條從任務開始到完成（或失敗）的完整工作流程路徑。每個 Lane 的執行過程會產生一系列事件（LaneEvent），這些事件記錄了工作流程的每一個狀態轉換。

LaneEventName 列舉型別定義了二十個以上的事件類型，涵蓋了工作流程的完整生命週期：Started（工作流程開始）、Ready（準備就緒）、Running（正在執行）、Green（所有測試通過）、Red（測試失敗）、Blocked（被阻塞）、CommitCreated（提交建立）、PrOpened（Pull Request 開啟）、MergeReady（準備合併）、ShipPrepared（準備部署）、ShipMerged（合併完成）、Finished（工作流程結束）、Failed（工作流程失敗）、Recovery（進入復原模式）等。

LaneFailureClass 列舉型別定義了十二種失敗分類，幫助系統精確地識別失敗的根因，以便選擇適當的復原策略。每個 LaneEvent 除了事件名稱外，還包含事件狀態、事件來源（EventProvenance）和毫秒級的時間戳記，形成了完整的審計追蹤。

### 19.2 Worker 生命週期

worker_boot.rs 定義了 Worker 的完整生命週期狀態機。Worker 是 Claw Code 中執行獨立任務的基本單位，每個 Worker 在自己的執行上下文中運行，擁有獨立的工作階段和資源。

Worker 的生命週期經歷以下狀態：Spawning（啟動中）→ TrustRequired（需要信任驗證，如果 TrustResolver 判定需要人工核准）→ ReadyForPrompt（等待接收提示詞）→ Running（正在執行）→ Finished（完成）或 Failed（失敗）。失敗的 Worker 可以重新進入 Spawning 狀態進行重試。

WorkerRegistry 是管理所有活躍 Worker 的全域單例。它維護一個從 worker_id 到 Worker 實例的映射，提供建立、查詢、停止和清理 Worker 的方法。每個 Worker 的狀態變化都會被記錄，方便監控和除錯。

信任機制是 Worker 生命週期中的一個重要環節。trust_resolver.rs 定義了三種信任策略：AutoTrust 對信任清單中的 Worker 自動放行；RequireApproval 要求使用者手動核准；Deny 直接拒絕。這種信任閘門確保了只有經過授權的 Worker 才能存取系統資源。

### 19.3 策略引擎

policy_engine.rs 實現了一個靈活的策略評估引擎，用於控制 Lane 工作流程的行為。策略引擎使用規則—條件—動作的三元組模型：每個 PolicyRule 包含一組 PolicyCondition（觸發條件）和一個 PolicyAction（當條件滿足時執行的動作）。

PolicyCondition 可以基於多種因素：事件類型（如「當測試失敗時」）、失敗分類（如「當編譯錯誤時」）、時間限制（如「當超過三十分鐘時」）、重試次數（如「當第三次重試時」）等。PolicyAction 定義了系統應該採取的動作：繼續執行、暫停等待、觸發復原、通知使用者或終止工作流程。

策略引擎在每個 Lane 事件產生時被觸發。它會遍歷所有已註冊的規則，找到匹配的條件，然後執行對應的動作。這種事件驅動的策略評估模型使得工作流程的行為可以被靈活地定制，而不需要修改核心程式碼。

### 19.4 錯誤復原

recovery_recipes.rs 定義了七種常見失敗場景的自動化復原方案（RecoveryRecipe）。每個復原方案包含一個 FailureScenario（失敗場景描述）和一系列 RecoveryStep（復原步驟）。

七種失敗場景涵蓋了最常見的 CI/CD 問題：編譯錯誤（系統會嘗試修復語法錯誤或缺少的依賴）、測試失敗（系統會分析失敗的測試並嘗試修復）、lint 警告（系統會自動套用 lint 修正）、合併衝突（系統會嘗試自動解決衝突）、權限不足（系統會升級權限模式後重試）、逾時（系統會增加逾時時間後重試）和資源不足（系統會釋放資源後重試）。

每個 RecoveryStep 是一個具體的動作，如「重新執行 cargo build」、「讀取失敗的測試輸出」、「編輯相關的原始碼」等。復原方案的執行是自動的——系統偵測到特定的失敗場景後，會自動選擇對應的復原方案並依序執行復原步驟。

## 第二十章：分支管理與品質閘門

### 20.1 分支新鮮度偵測

在多人協作的開發環境中，分支的新鮮度是一個重要的品質指標。一個太舊的分支可能包含過時的程式碼，合併時可能產生衝突。stale_branch.rs 模組定義了 BranchFreshness 型別來表示分支的新鮮度，以及 StaleBranchPolicy 來定義針對過期分支的處理策略。

StaleBranchAction 定義了系統可以採取的行動：警告使用者（Warn）、自動 rebase（Rebase）、阻止合併（Block）或忽略（Ignore）。stale_base.rs 則從另一個角度處理類似的問題——它追蹤基底提交的新鮮度，確保 Worker 工作在最新的程式碼基礎上。

### 20.2 分支鎖定

branch_lock.rs 模組實現了分支鎖定機制，防止多個 Worker 同時修改同一個分支。BranchLockIntent 結構表示一個鎖定意圖，包含要鎖定的分支名稱和請求鎖定的 Worker ID。BranchLockCollision 結構表示鎖定衝突，包含衝突的分支名稱和持有鎖的 Worker ID。

當 Worker 嘗試在一個已被其他 Worker 鎖定的分支上工作時，系統會檢測到衝突並通知 Worker。Worker 可以選擇等待鎖被釋放、切換到另一個分支，或者請求強制取得鎖。

### 20.3 綠燈契約

green_contract.rs 定義了四級測試品質閘門——GreenLevel。這四個級別從低到高分別代表不同的測試覆蓋度和通過要求：最低級別可能只要求編譯成功；較高級別要求核心測試通過；更高級別要求所有測試通過；最高級別要求所有測試通過且沒有 lint 警告。

GreenContract 結構將特定的 GreenLevel 與 Lane 工作流程的階段關聯起來。例如，可以配置為在 PrOpened 階段要求至少達到第二級別，在 MergeReady 階段要求達到最高級別。這種分級的品質閘門使得工作流程能夠在開發早期快速迭代（較低的品質要求），而在接近合併時確保嚴格的品質標準。

## 第二十一章：任務封包與團隊協作

### 21.1 任務封包系統

task_packet.rs 定義了 TaskPacket 結構，這是 Worker 之間傳遞任務資訊的標準格式。每個 TaskPacket 包含：objective（任務目標的文字描述）、scope（TaskScope 列舉，指定任務的範圍——如單一檔案、目錄、模組或整個儲存庫）、scope_path（可選的範圍路徑）、repo（可選的儲存庫 URL）和 worktree（可選的工作樹路徑）。

TaskPacket 的設計理念是提供足夠的上下文資訊，讓接收任務的 Worker 能夠獨立地理解和執行任務，而不需要額外的溝通。scope 的存在特別重要——它告訴 Worker 任務的影響範圍，幫助 Worker 聚焦在相關的程式碼區域，避免不必要的修改。

### 21.2 團隊協作模型

team_cron_registry.rs 實現了團隊和排程管理。TeamRegistry 管理團隊的建立和刪除，每個 Team 有一個唯一的 team_id、名稱和狀態（Created、Running、Completed、Deleted）。一個團隊可以包含多個任務，形成一種邏輯分組——團隊中的任務可以並行執行，團隊的狀態取決於其中所有任務的狀態。

CronRegistry 管理排程任務。每個 CronTask 有一個唯一的 cron_id、名稱、排程表達式和狀態。排程表達式遵循標準的 cron 格式，指定任務的執行時間。排程系統讓使用者能夠設定定期執行的自動化任務，如每日的程式碼品質檢查、每週的依賴更新掃描等。

### 21.3 子代理人架構

Agent 工具允許 AI 模型啟動子代理人來處理特定的子任務。子代理人架構的核心理念是「分治法」——將一個複雜的大任務分解為多個可獨立執行的子任務，每個子任務由一個獨立的代理人處理。

子代理人繼承了父代理人的大部分設定（權限模式、沙箱配置等），但擁有獨立的工作階段和上下文。這意味著子代理人的對話歷史不會污染父代理人的上下文，子代理人的 token 消耗也會被獨立追蹤。子代理人完成任務後，會將結果摘要回報給父代理人，父代理人再基於這些結果繼續後續的工作。

### 21.4 摘要壓縮在工作流程中的角色

summary_compression.rs 模組在工作流程引擎中扮演著重要的角色。當一個長時間運行的 Worker 產生大量的對話歷史時，摘要壓縮能夠有效地控制 token 消耗，同時保留足夠的上下文資訊供 Worker 繼續工作。

SummaryCompressionBudget 結構定義了摘要的預算限制：最多一千二百個字元和二十四行。這個限制確保了壓縮摘要在被注入到系統提示詞中時，不會佔用過多的 token 空間。SummaryCompressionResult 結構記錄了壓縮的結果：原始文字長度、壓縮後文字長度、壓縮比率以及是否觸發了截斷。

在工作流程場景中，壓縮的觸發頻率通常比互動式 REPL 高得多。一個自動化的 CI 任務可能在短時間內執行大量的工具呼叫——讀取多個檔案、執行測試、分析結果、編輯程式碼、再次執行測試。每次工具呼叫都會在對話歷史中添加兩則訊息（工具呼叫和工具結果），使得 token 總量快速增長。自動壓縮機制確保了即使在長時間的自動化任務中，token 消耗也能被控制在合理的範圍內。

### 21.5 bootstrap.rs 與啟動計畫

bootstrap.rs 模組管理系統的啟動計畫。BootstrapPhase 列舉型別定義了啟動計畫的各個階段，BootstrapPlan 結構定義了完整的啟動計畫。啟動計畫指定了系統在啟動時應該自動執行的操作序列——例如，自動讀取特定的設定檔案、自動掃描專案目錄結構、自動執行健康檢查等。

啟動計畫在工作流程場景中特別有用。當一個 Worker 被啟動時，它的啟動計畫可以指定 Worker 在接收提示詞之前應該自動完成的準備工作——例如，拉取最新的程式碼、安裝依賴、建構專案。這確保了 Worker 在開始工作時已經處於一個已知的良好狀態。

### 21.6 remote.rs 與遠端會話

remote.rs 模組實現了遠端會話功能，允許 Claw Code 在遠端伺服器上運行，而使用者透過本地的客戶端進行互動。RemoteSessionContext 結構包含遠端會話的上下文資訊。UpstreamProxyBootstrap 結構定義了上游代理的啟動配置。

遠端會話功能在企業環境中特別有價值。開發者可以在強大的雲端伺服器上運行 Claw Code，利用伺服器的計算資源和網路頻寬，同時在自己的筆記型電腦上透過輕量級的客戶端進行操作。這種架構還有安全上的優勢——原始碼和 API 金鑰都保存在受控的伺服器環境中，不需要分發到開發者的個人設備上。

### 21.7 深度規劃模式

EnterPlanMode 和 ExitPlanMode 工具以及 /ultraplan 斜線命令共同實現了 Claw Code 的深度規劃功能。在規劃模式中，AI 模型不會直接執行操作，而是先制定一個詳細的行動計畫，列出要修改的檔案、要執行的命令以及預期的結果。使用者審查計畫後，可以選擇執行整個計畫、修改部分步驟，或者完全拒絕計畫。

這種規劃模式在執行大規模的程式碼修改時特別有用。例如，當需要重構一個跨越多個檔案的 API 介面時，讓 AI 先制定計畫能夠確保修改的完整性和一致性。使用者可以在計畫階段就發現潛在的問題，而不需要等到修改完成後才發現遺漏。

/ultraplan 命令是規劃模式的增強版本，它會讓 AI 模型進行更加深入的分析——不僅列出要修改的檔案，還會分析每個修改的影響範圍、潛在的風險以及回滾策略。這種深度規劃對於關鍵系統的修改特別重要。


### 21.8 斜線命令的詳細功能

commands crate 定義的二十四個以上斜線命令為 REPL 模式提供了豐富的管理功能。讓我們詳細了解每個命令的功能和使用場景。

/help（別名 /h）顯示所有可用的斜線命令及其簡短說明。這是新使用者最先接觸的命令，也是在記不清命令名稱時的參考。

/status（別名 /s）顯示系統的全面狀態資訊，包括：當前使用的模型和其來源（ModelProvenance）、權限模式、沙箱狀態（啟用/停用，如果啟用則顯示隔離模式）、已載入的外掛數量和名稱、已連線的 MCP 伺服器數量和狀態、當前工作階段的訊息數量和 token 用量、以及 Git 分支資訊。

/sandbox 顯示沙箱的詳細狀態，包括沙箱是否啟用、啟用的原因或停用的原因、PID 命名空間隔離是否啟用、網路隔離是否啟用、檔案系統隔離模式、以及容器環境偵測結果。

/compact 手動觸發工作階段壓縮。雖然系統會在 token 總量超過閾值時自動壓縮，但使用者也可以在任何時候手動觸發壓縮，例如在完成一個子任務後希望清理上下文時。

/model 切換當前使用的模型。使用者可以指定模型名稱或別名，系統會自動偵測對應的提供商。模型切換即時生效，下一輪對話就會使用新模型。

/permissions（別名 /perm）顯示和修改權限模式。不帶參數時顯示當前的權限設定；帶參數時切換到指定的模式。例如 /permissions read-only 切換到唯讀模式，/permissions workspace-write 切換到工作區寫入模式。

/agents 列出所有活躍的子代理人，包括每個代理人的 ID、當前狀態和任務描述。這個命令在使用子代理人架構時非常有用，讓使用者能夠監控多個代理人的工作進度。

/mcp 列出所有配置的 MCP 伺服器及其狀態。對於每個伺服器，顯示名稱、傳輸方式、連線狀態（健康/失敗/降級）、提供的工具數量和資源數量。

/plugins（別名 /marketplace）列出所有已載入的外掛及其狀態。顯示每個外掛的名稱、版本、類型（內建/隨附/外部）、狀態和提供的工具數量。

/skills 列出所有已註冊的技能。技能是預定義的操作序列，可以被 AI 模型透過 Skill 工具呼叫。

/doctor 執行系統健康檢查，診斷可能的問題。它會檢查：Rust 工具鏈是否安裝正確、API 金鑰是否有效（透過一個輕量級的 API 呼叫測試）、沙箱是否可用、已配置的 MCP 伺服器是否可連線、以及設定檔是否有語法錯誤。

/resume 恢復之前的工作階段。不帶參數時恢復最近的工作階段（等同於 --resume latest），帶參數時恢復指定 ID 的工作階段。

/clear 清除當前的對話上下文，重新開始一個新的對話。與退出程式再重新啟動不同，/clear 保持所有的設定和連線狀態不變，只清除對話歷史。

/quit（別名 /exit）退出程式。退出前會自動儲存當前的工作階段，關閉所有 MCP 伺服器連線，關閉外掛。

/cost 顯示當前工作階段的累計 token 用量和成本估算。分別顯示輸入 token、輸出 token、快取創建 token 和快取讀取 token 的數量，以及基於模型定價表計算的成本。

/config 顯示當前的設定值，包括所有來源的設定檔路徑和合併後的最終設定。

/session 顯示當前工作階段的詳細資訊，包括 session_id、建立時間、訊息數量、token 總量、壓縮歷史和儲存路徑。

/diff 顯示工作區中的 Git 差異。等同於 git diff 命令，但輸出會被 Markdown 格式化以便閱讀。

/commit 在工作區中建立 Git 提交。AI 模型可以被要求根據變更內容自動產生提交訊息。

/pr 建立 Pull Request。系統會根據當前分支的變更自動產生 PR 的標題和描述。

/review 觸發程式碼審查模式。AI 模型會分析工作區中的變更，指出潛在的問題和改進建議。

/subagent 管理子代理人——列出、停止或查看子代理人的輸出。

/ultraplan 進入深度規劃模式，AI 模型會制定一個詳細的行動計畫供使用者審查。

/teleport 跳轉到指定的檔案或符號位置。如果配置了 LSP，可以利用 LSP 的符號查找功能精確定位。

/bughunter 啟動 bug 掃描模式，AI 模型會系統性地分析程式碼庫中可能存在的 bug。


### 21.9 工作流程引擎與持續整合的整合

Claw Code 的工作流程引擎被設計為能夠與現有的 CI/CD 系統協同工作，而不是取代它們。典型的整合模式是：CI 系統（如 GitHub Actions）偵測到程式碼變更後觸發 Claw Code 的一次性模式，Claw Code 分析變更、執行測試、產生報告，然後將結果回報給 CI 系統。

在這種整合模式中，Lane 事件系統扮演著溝通橋樑的角色。CI 系統可以訂閱 Lane 事件來監控工作流程的進度——當事件到達 Green 或 Red 時，CI 系統可以據此決定管線的後續步驟。

task_packet.rs 定義的 TaskPacket 格式為 CI 系統提供了標準化的任務描述方式。CI 系統可以建構 TaskPacket 並透過命令列參數或標準輸入傳遞給 Claw Code，TaskPacket 中的 objective（任務目標）、scope（任務範圍）和 scope_path（範圍路徑）讓 Claw Code 能夠聚焦在相關的程式碼區域。

Worker 機制讓 Claw Code 能夠管理多個並行的任務。在大型的 CI 管線中，可能同時有多個獨立的檢查項目——程式碼風格檢查、單元測試、整合測試、安全掃描等。每個檢查項目可以分配給一個獨立的 Worker，Worker 之間並行執行，互不干擾。WorkerRegistry 追蹤所有 Worker 的狀態，當所有 Worker 都完成後，系統產生一個整合的報告。

### 21.10 綠燈契約在實踐中的應用

green_contract.rs 定義的四級品質閘門在實際開發流程中有著具體的應用場景。

第一級（最低級別）通常要求專案能夠成功編譯。這是最基本的品質要求，確保程式碼至少在語法上是正確的。在開發的早期階段（如初始原型），可能只需要滿足第一級。

第二級通常要求核心測試通過。核心測試是指驗證關鍵功能路徑的測試，通常是測試套件中標記為 critical 或 smoke 的子集。在 Pull Request 開啟時（PrOpened 事件），通常要求至少達到第二級。

第三級通常要求所有測試通過。這包括單元測試、整合測試和端到端測試的完整執行。在準備合併時（MergeReady 事件），通常要求達到第三級。

第四級（最高級別）通常要求所有測試通過且沒有任何 lint 警告。這是最嚴格的品質要求，確保程式碼不僅功能正確，而且符合所有的程式碼品質標準。在最終合併前（ShipPrepared 事件），通常要求達到第四級。

GreenContract 的設定可以根據專案的需求進行調整。在快節奏的專案中，可能在所有階段都使用較低的級別以加速開發迴圈。在關鍵系統的專案中，可能從 PrOpened 就開始要求第三級或第四級。


### 21.11 Lane 事件的觀測與監控

Lane 事件系統不僅驅動了工作流程的自動化邏輯，也提供了豐富的觀測資料。每個 LaneEvent 包含時間戳記、事件名稱、狀態和來源資訊，形成了完整的事件流。

在監控層面，Lane 事件可以被訂閱並轉發到外部的監控系統。例如，可以將所有 Failed 事件發送到告警系統（如 PagerDuty 或 Opsgenie），讓值班工程師能夠及時介入。可以將所有事件發送到日誌聚合系統（如 ELK Stack 或 Datadog），用於長期的趨勢分析。

EventProvenance 結構記錄了事件的來源資訊，讓監控系統能夠區分不同來源的事件。例如，同一個 Lane 中的事件可能來自不同的 Worker，EventProvenance 能夠幫助追蹤每個 Worker 的個別表現。

LaneFailureClass 的十二種分類為自動化的告警路由提供了基礎。不同類別的失敗可能需要不同團隊的介入——編譯錯誤可能需要開發團隊、基礎設施錯誤可能需要運維團隊、安全問題可能需要安全團隊。透過在告警規則中使用 LaneFailureClass 作為路由條件，可以確保告警被發送到正確的團隊。

### 21.12 Worker 的資源管理

Worker 的資源管理是工作流程引擎中一個重要但容易被忽視的面向。每個 Worker 消耗系統資源——記憶體（用於對話歷史和工具狀態）、CPU（用於工具執行）、磁碟（用於工作階段儲存）和 API token（用於 AI 模型的推理）。

WorkerRegistry 提供了資源使用的概覽。管理員可以查詢每個 Worker 的狀態和資源消耗，識別佔用過多資源的 Worker。當系統資源緊張時，可以選擇性地停止低優先級的 Worker 以釋放資源。

Worker 的數量上限也是一個重要的配置項。在資源有限的環境中（如 CI 執行器），同時運行太多 Worker 可能導致效能下降或系統不穩定。合理的上限設定需要考慮可用的 CPU 核心數、記憶體容量和 API 速率限制。

### 19.5 策略引擎的規則優先序

PolicyEngine 在評估多個匹配的規則時，遵循特定的優先序。首先是規則的明確性——更具體的規則優先於更通用的規則。例如，一個針對特定失敗類別的規則優先於一個捕獲所有失敗的通用規則。

其次是動作的嚴格性——較嚴格的動作優先於較寬鬆的動作。例如，如果一個規則要求終止工作流程，而另一個規則要求繼續執行，系統會選擇終止。這種「安全優先」的策略確保了系統在規則衝突時不會做出過於樂觀的決策。

最後是規則的定義順序——在其他條件相同的情況下，後定義的規則覆蓋先定義的規則。這讓使用者能夠透過在設定中添加新規則來覆蓋預設行為。

策略引擎還支援規則的組合——多個條件可以透過 AND 或 OR 邏輯連接。例如，一個規則可以定義為「當測試失敗（條件 1）且重試次數超過 3 次（條件 2）時，終止工作流程」。這種組合邏輯讓策略的定義更加靈活和精確。


### 19.6 事件驅動模型的優勢

Lane 事件驅動模型相比傳統的步驟式 CI/CD 管線有幾個顯著的優勢。

首先是自適應性。在步驟式管線中，每個步驟的行為在管線定義時就已經確定——步驟 A 完成後執行步驟 B，步驟 B 完成後執行步驟 C。如果步驟 B 失敗，管線通常只能選擇重試或終止。而在事件驅動模型中，每個事件都可以觸發不同的行為——Red 事件可以觸發自動復原（而不是簡單地重試），Blocked 事件可以觸發等待然後繼續（而不是終止）。

其次是可觀測性。事件流提供了工作流程的完整歷史記錄，每個事件都帶有精確的時間戳記和來源資訊。這讓事後分析和除錯變得非常方便——可以精確地知道什麼時候發生了什麼、是什麼觸發了什麼行為。

第三是可擴充性。新增一個事件類型（如新的品質閘門）只需要在 LaneEventName 中添加一個新的變體，然後在策略引擎中添加對應的規則。不需要修改核心的事件處理邏輯，因為所有事件都遵循同一個處理模式。

### 20.4 分支管理的自動化策略

在多 Worker 並行工作的場景中，分支管理的自動化是確保程式碼品質和團隊效率的關鍵。Claw Code 的分支管理自動化包含幾個層面。

自動分支建立：當一個新的 Worker 被啟動時，系統可以自動為它建立一個工作分支。分支名稱通常包含任務 ID 和簡短的描述，如 claw/task-123-fix-login-bug。自動建立的分支基於主分支的最新提交。

自動 rebase：StaleBranchPolicy 可以配置為在分支過期時自動執行 rebase。如果主分支在 Worker 開始工作後有了新的提交，自動 rebase 確保 Worker 的修改基於最新的程式碼。如果 rebase 過程中遇到衝突，系統會將事件標記為 Blocked，等待人工介入或 AI 模型的自動衝突解決。

自動清理：完成的工作分支可以被自動刪除，避免分支的積累。清理策略可以基於時間（刪除超過 N 天的已合併分支）或狀態（刪除所有已成功合併的分支）。

### 21.13 任務的生命週期追蹤

TaskRegistry 中的每個 Task 經歷一個明確的生命週期：Created（任務已建立但尚未開始執行）→ Running（任務正在被 Worker 處理）→ Completed（任務成功完成）或 Failed（任務因錯誤而失敗）或 Stopped（任務被使用者手動停止）。

每個狀態轉換都會被記錄，包含轉換的時間戳記和原因。例如，從 Running 到 Failed 的轉換會記錄失敗的錯誤訊息，從 Running 到 Stopped 的轉換會記錄是誰發起了停止操作。

TaskMessage 列表記錄了任務執行過程中的所有重要事件。每個 TaskMessage 包含角色（system、worker、user）、內容和時間戳記。system 角色的訊息通常是狀態變更的通知；worker 角色的訊息是 Worker 的輸出和報告；user 角色的訊息是使用者的介入和指令。

TaskOutput 工具讓使用者或父代理人能夠查看任務的累計輸出。對於長時間運行的任務，輸出可能很長，因此 TaskOutput 支援分頁讀取——指定起始位置和最大長度，只讀取需要的部分。


### 20.5 BranchFreshness 的量化指標

stale_branch.rs 中的 BranchFreshness 結構使用多個量化指標來評估分支的新鮮度。這些指標包括：距離最後一次提交的時間（以小時為單位）、與主分支的偏離提交數量（分支有多少個主分支沒有的提交，以及主分支有多少個分支沒有的提交）、以及分支是否已經過 rebase。

StaleBranchPolicy 使用這些指標來決定行動。一個典型的策略可能是：如果分支的最後提交超過四十八小時，或者主分支在分支建立後有超過二十個新提交，就觸發 Warn 動作；如果超過一週或超過五十個新提交，觸發 Rebase 動作；如果超過兩週或超過一百個新提交，觸發 Block 動作。

BaseCommitState 和 BaseCommitSource 提供了另一個角度的新鮮度評估。BaseCommitState 記錄了 Worker 開始工作時的基底提交是否仍然是主分支的最新提交。如果基底提交已經不是最新的（即主分支有了新的提交），Worker 的修改可能基於過時的程式碼，合併時可能產生衝突。BaseCommitSource 記錄了基底提交的來源——是從主分支取得的，還是從其他分支取得的。

### 21.14 Skill 工具的設計理念

Skill 工具讓使用者能夠定義可重用的操作序列。一個技能（Skill）本質上是一段自然語言的指令，描述了一個特定的任務模式。當 AI 模型透過 Skill 工具呼叫一個技能時，技能的指令會被注入到 AI 的上下文中，指導模型執行特定的操作序列。

與直接在提示詞中描述操作不同，技能的優勢在於可重用性和標準化。一個團隊可以定義一組標準技能——如「程式碼審查技能」、「依賴更新技能」、「安全掃描技能」——然後在不同的專案和場景中重複使用這些技能。技能的指令可以包含特定的步驟（如「先執行測試，然後檢查覆蓋率報告，最後產生修改建議」），確保每次執行都遵循一致的流程。

/skills 斜線命令列出所有已註冊的技能，讓使用者了解當前可用的技能。技能可以來自設定檔中的靜態定義，也可以來自外掛的動態註冊。


### 19.7 復原方案的執行追蹤

recovery_recipes.rs 的復原方案不僅定義了復原步驟，還會追蹤復原的執行過程和結果。RecoveryStep 的每一步執行都會記錄開始時間、結束時間、執行結果（成功或失敗）以及相關的輸出。

這種執行追蹤有兩個重要的用途。首先，它提供了復原過程的完整審計日誌——如果復原成功，日誌記錄了系統是如何自動修復問題的；如果復原失敗，日誌記錄了失敗的具體步驟和原因，幫助人工介入時快速定位問題。

其次，執行追蹤為復原策略的持續改進提供了資料基礎。透過分析復原的成功率和失敗模式，開發團隊可以識別出哪些場景的自動復原最有效、哪些場景需要更好的復原策略、以及哪些場景根本不適合自動復原。

FailureScenario 的七種分類為復原策略的選擇提供了框架。每種失敗場景都有其典型的復原路徑——編譯錯誤通常透過程式碼修正來復原；測試失敗通常透過分析失敗原因和修正邏輯來復原；lint 警告通常透過自動套用修正建議來復原；合併衝突通常透過智能合併策略來復原。

### 21.15 團隊的狀態管理

TeamRegistry 管理的 Team 結構有四種狀態：Created（團隊已建立但尚未開始工作）、Running（團隊中至少有一個任務正在執行）、Completed（團隊中所有任務都已成功完成）和 Deleted（團隊已被刪除）。

團隊的狀態是從其包含的任務狀態推導出來的。如果所有任務都處於 Created 狀態，團隊也是 Created；如果有任何任務處於 Running 狀態，團隊就是 Running；如果所有任務都處於 Completed 狀態，團隊就是 Completed。Failed 任務不會阻止團隊進入 Completed 狀態——只要所有任務都不再處於 Running 狀態，團隊就被視為完成（即使有些任務失敗了）。

團隊的建立和刪除透過 TeamCreate 和 TeamDelete 工具進行。AI 模型可以根據任務的性質和數量決定是否需要建立團隊。對於可以並行處理的多個獨立子任務，建立團隊並為每個子任務分配 Worker 通常比順序執行更高效。


### 19.8 策略引擎的可配置性

PolicyEngine 的規則可以在設定檔中定義，讓使用者能夠根據專案的需求自訂工作流程的行為。一個策略規則的完整定義包含三個部分：名稱（用於日誌和除錯）、條件列表（決定規則何時觸發）和動作（決定觸發後做什麼）。

策略規則支援多種條件類型：EventType 條件匹配特定的 Lane 事件類型（如 Red、Blocked）；FailureClass 條件匹配特定的失敗分類（如 CompileError、TestFailure）；RetryCount 條件匹配重試次數；Duration 條件匹配工作流程的持續時間；WorkerState 條件匹配 Worker 的狀態。

動作類型包括：Continue（繼續正常的工作流程）、Pause（暫停工作流程並等待人工介入）、Recover（觸發自動復原方案）、Notify（向使用者發送通知）、Abort（終止工作流程）、Retry（重試當前步驟）和 Escalate（升級到更高級別的處理）。

一個實際的策略設定範例可能是：「當測試失敗（EventType: Red + FailureClass: TestFailure）且重試次數小於 3（RetryCount < 3）時，觸發自動復原（Recover）；當重試次數達到 3 時，暫停並通知（Pause + Notify）；當工作流程持續超過一小時時，終止（Abort）。」


### 21.16 Sleep 工具在工作流程中的作用

Sleep 工具看似簡單——它只是讓系統等待指定的時間。但在工作流程場景中，它有著重要的用途。

在自動化的 CI 任務中，某些操作之間需要等待一段時間。例如，在修改設定檔後重新啟動服務之前，可能需要等待幾秒鐘讓服務完成當前的請求處理。在執行資料庫遷移後查詢結果之前，可能需要等待遷移完全完成。在部署應用程式後測試端點之前，可能需要等待應用程式完成啟動。

Sleep 工具的實作使用 tokio 的非同步等待——它不會阻塞執行緒，而是讓 tokio 執行時期在等待期間可以處理其他任務。這在多 Worker 場景中特別重要——如果一個 Worker 需要等待，其他 Worker 的執行不會受到影響。

Sleep 工具有一個最大等待時間的限制（通常是五分鐘），防止 AI 模型因為誤判而設定過長的等待時間。如果確實需要更長的等待，AI 可以多次呼叫 Sleep 工具。

### 20.6 工作流程中的 Git 操作

在工作流程引擎的上下文中，Git 操作是核心的操作之一。Worker 需要在正確的分支上工作、提交修改、推送到遠端儲存庫、以及處理合併衝突。

git_context.rs 提供了當前 Git 狀態的上下文資訊。在每個對話回合開始時，系統會更新 Git 上下文——當前分支名稱、最近的提交歷史、暫存區的狀態、工作目錄的修改狀態等。這些資訊被注入到系統提示詞中，讓 AI 模型了解當前的版本控制狀態。

/diff 和 /commit 斜線命令讓使用者（或 AI 模型透過 Bash 工具）能夠在對話中執行 Git 操作。在自動化的工作流程中，Worker 通常會在完成修改後自動建立提交，提交訊息由 AI 模型根據修改的內容自動產生。


### 21.17 工作流程引擎的可觀測性

工作流程引擎的可觀測性是確保其在生產環境中可靠運作的關鍵。可觀測性包含三個維度：日誌（Logs）、指標（Metrics）和追蹤（Traces）。

在日誌維度，Lane 事件系統天然地產生了結構化的事件日誌。每個 LaneEvent 包含事件名稱、狀態、時間戳記和來源，形成了完整的工作流程執行日誌。這些日誌可以被轉發到日誌聚合系統進行集中管理和搜尋。

在指標維度，WorkerRegistry 和 TaskRegistry 提供了即時的狀態統計——活躍的 Worker 數量、執行中的任務數量、已完成和失敗的任務比例等。這些指標可以被暴露為 Prometheus 格式的 metrics，供監控系統收集和視覺化。

在追蹤維度，SessionTracer 為每個工作階段維護了操作追蹤記錄。在工作流程場景中，追蹤記錄跨越了多個 Worker 和多個工具呼叫，形成了一個分散式追蹤。未來可能引入 OpenTelemetry 標準的分散式追蹤支援，讓工作流程的執行路徑能夠被端到端地視覺化。


### 21.18 RemoteTrigger 工具的用途

RemoteTrigger 工具允許 AI 模型觸發遠端操作。這個工具在工作流程引擎中扮演著「外部執行器」的角色——當工作流程需要執行一個不在本地環境中的操作時（如觸發遠端的 CI 管線、呼叫外部的 API、或者向遠端伺服器發送指令），RemoteTrigger 提供了統一的介面。

RemoteTrigger 的實作依賴於 remote.rs 模組提供的遠端通訊能力。它透過 HTTP 請求或 WebSocket 連線與遠端端點通訊，將觸發請求和參數發送過去，然後等待回應。遠端端點的認證和網路配置遵循系統的代理設定和認證設定。

在 CI/CD 整合的場景中，RemoteTrigger 通常用於：觸發 GitHub Actions 或 GitLab CI 的工作流程、呼叫 webhook 端點通知外部系統、或者透過 API 與專案管理工具（如 Jira、Linear）互動。


### 19.9 LaneEventName 的完整列舉

讓我們完整地列舉 LaneEventName 的所有變體，理解工作流程中可能發生的每一種事件。

Started 標記工作流程的開始，通常在 Worker 被建立並接收到提示詞時觸發。Ready 標記工作流程已準備就緒，所有的前置條件（如依賴安裝、環境配置）都已滿足。Running 標記工作流程正在執行核心任務。Green 標記所有測試（或品質檢查）通過。Red 標記至少有一個測試失敗。Blocked 標記工作流程被某個外部條件阻塞（如等待人工審查、等待鎖釋放）。

CommitCreated 標記一個新的 Git 提交被建立。PrOpened 標記一個 Pull Request 被開啟。MergeReady 標記 Pull Request 已通過所有檢查，準備合併。ShipPrepared 標記合併前的最後準備已完成。ShipMerged 標記合併已完成。

Finished 標記工作流程正常結束。Failed 標記工作流程因為不可恢復的錯誤而終止。Recovery 標記系統進入自動復原模式。Retried 標記一個步驟被重試。Escalated 標記問題被升級到更高級別的處理。Cancelled 標記工作流程被使用者取消。

每種事件都可能攜帶額外的上下文資訊（透過 EventState 結構），如相關的檔案路徑、錯誤訊息、重試次數、持續時間等。這些上下文資訊為策略引擎的決策和事後分析提供了豐富的資料。


### 21.19 json.rs 輔助模組

runtime crate 中的 json.rs 模組提供了一系列 JSON 處理的輔助函式，被多個其他模組使用。

merge_json_values 函式實現了前述的深度合併邏輯——對兩個 serde_json::Value 進行遞迴合併。truncate_json_string 函式將 JSON 字串截斷到指定的最大長度，在截斷處添加省略號標記。這個函式在日誌和錯誤訊息中被廣泛使用——當需要顯示一個可能非常長的 JSON 值（如工具呼叫的輸入參數）時，截斷可以避免輸出過於冗長。

sanitize_json_for_display 函式對 JSON 值進行過濾，移除敏感的欄位（如 api_key、token、password 等）。這個函式在遙測事件和日誌記錄中被使用，確保敏感資訊不會被意外地記錄。

extract_text_from_json 函式從複雜的 JSON 結構中提取所有的文字欄位，拼接成一個字串。這個函式在 Bash 驗證中被使用——當 AI 模型的工具呼叫輸入是一個複雜的 JSON 物件時，系統需要從中提取出實際的命令字串進行安全分析。


### 19.10 工作流程引擎與 telemetry 的整合

工作流程引擎與 telemetry crate 深度整合，確保工作流程的每一個狀態轉換都被記錄為遙測事件。

每個 LaneEvent 在觸發時都會同時產生一個 AnalyticsEvent。AnalyticsEvent 的 namespace 設定為 workflow，action 設定為對應的事件名稱（如 lane_started、lane_green、lane_failed）。properties 映射包含事件的詳細上下文——Worker ID、任務 ID、失敗分類、持續時間等。

這種整合讓遙測系統能夠提供工作流程的完整可視性。管理員可以查詢特定時間範圍內的所有工作流程事件，了解系統的整體健康狀態。開發者可以追蹤特定任務的完整事件序列，診斷失敗的原因。產品團隊可以分析工作流程的成功率和平均持續時間，評估 AI 驅動的自動化的效益。


### 21.20 工作流程的可重現性

工作流程的可重現性是企業環境中的一個重要需求。一個工作流程在第一次執行時成功了，在相同的條件下再次執行時也應該成功。

影響可重現性的因素包括：AI 模型的非確定性（相同的輸入可能產生不同的輸出）、外部服務的狀態變化（如 MCP 伺服器的版本更新）、以及時間相關的行為（如基於時間的排程和逾時）。

Claw Code 透過幾種方式來改善可重現性。首先，工作階段的 JSONL 記錄提供了完整的操作歷史，讓開發者能夠追蹤和重現之前的操作序列。其次，設定檔案的版本控制（將 .claw.json 和 .claw/settings.json 提交到 Git）確保了設定的一致性。最後，mock-anthropic-service 在測試環境中提供了確定性的 AI 回應，消除了模型非確定性對測試可重現性的影響。


### 21.21 工作流程引擎與外掛系統的整合

工作流程引擎與外掛系統可以協同工作，讓使用者透過外掛來擴充工作流程的能力。外掛提供的勾子機制在工作流程場景中特別有價值。

例如，一個 CI 整合外掛可以透過 post_tool_use 勾子在每次 Bash 命令執行後檢查命令的退出碼，如果發現測試失敗，自動觸發 Lane 事件系統的 Red 事件。另一個通知外掛可以訂閱 Lane 事件，在特定事件（如 Failed 或 Finished）發生時發送通知到 Slack 或 Teams。

外掛還可以提供自訂的復原方案。recovery_recipes.rs 定義的七種內建復原方案涵蓋了最常見的場景，但特定的專案可能需要特定的復原邏輯——例如，一個需要特殊環境設定的專案可能需要在編譯失敗時執行特定的環境修復腳本。透過外掛提供的工具，這種專案特定的復原邏輯可以被整合到工作流程引擎中。

WorkerRegistry 和 TaskRegistry 的全域存取性讓外掛能夠查詢當前的工作流程狀態——活躍的 Worker 數量、執行中的任務列表、最近的事件歷史等。這些資訊可以被外掛用於做出決策——例如，一個負載均衡外掛可以根據當前的 Worker 數量決定是否接受新的任務請求。


### 21.22 工作流程引擎的設計靈感

Claw Code 工作流程引擎的設計汲取了多個領域的靈感：事件驅動架構（Event-Driven Architecture）的事件總線模式、有限狀態機（Finite State Machine）的狀態轉換模型、以及響應式程式設計（Reactive Programming）的資料流管道。這些設計模式的結合讓工作流程引擎在保持簡潔性的同時具備了強大的表達能力。
