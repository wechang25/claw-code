## 第四章：環境準備與安裝

在正式開始使用 Claw Code 之前，我們需要確保開發環境已經正確地準備就緒。本章將以系統化的方式，引導讀者完成從作業系統確認到最終安裝驗證的整個流程。環境準備雖然看似繁瑣，但它是確保後續所有操作能夠順利進行的關鍵前提。一個正確配置的開發環境不僅能夠避免許多常見的建構錯誤，還能顯著提升日常使用的效率與體驗。因此，我們建議讀者仔細閱讀並完整執行本章中的每一個步驟，即使你認為自己的環境可能已經滿足了大部分需求。

### 4.1 系統需求

Claw Code 作為一個以 Rust 語言編寫的跨平台命令列工具，對作業系統的要求相對寬鬆，但仍然有一些必須滿足的前提條件。在本節中，我們將逐一說明這些系統需求，並提供針對不同平台的具體安裝指引。

首先，讓我們談談支援的作業系統。Claw Code 目前完整支援三種主要的類 Unix 作業系統環境：Linux、macOS 以及 Windows Subsystem for Linux（簡稱 WSL）。在 Linux 平台上，Claw Code 支援所有主流的發行版，包括但不限於 Ubuntu、Debian、Fedora、CentOS、Arch Linux、openSUSE 等。無論你使用的是哪一個發行版，只要能夠安裝 Rust 工具鏈並滿足必要的系統套件需求，就能夠順利地建構與運行 Claw Code。在 macOS 平台上，Claw Code 支援 macOS 十二點零（Monterey）及更新的版本，同時完整支援 Intel 與 Apple Silicon（M1、M2、M3 系列）兩種處理器架構。對於 Windows 使用者，我們強烈建議透過 WSL 2 來運行 Claw Code，因為 WSL 2 提供了完整的 Linux 核心環境，能夠確保所有功能的正常運作。目前 Claw Code 尚未提供原生 Windows 支援，但透過 WSL 2 的使用體驗已經非常接近原生 Linux 環境。

接下來，我們需要安裝 Rust 工具鏈。Rust 工具鏈是建構 Claw Code 的核心依賴項目，其中包括 Rust 編譯器（rustc）、套件管理器與建構工具（Cargo）以及標準函式庫。安裝 Rust 工具鏈的官方推薦方式是使用 rustup 這個工具鏈管理器。rustup 不僅能夠安裝 Rust 工具鏈，還能夠在多個版本之間輕鬆切換，管理不同的目標平台，以及安裝額外的元件。Claw Code 的 Cargo 工作區配置使用的是 Rust 2021 版本（edition），因此你需要確保安裝的 Rust 版本至少為一點五六點零或更新。然而，我們始終建議安裝最新的穩定版本，以獲得最佳的效能、安全性修補以及語言功能支援。在大多數系統上，你只需要在終端機中執行一行簡單的命令就能完成 rustup 的安裝。安裝過程中，rustup 會自動偵測你的作業系統與處理器架構，並下載對應的工具鏈二進位檔案。安裝完成後，你需要重新開啟終端機或手動載入環境變數，以確保 rustc 和 cargo 命令能夠被正確找到。你可以透過執行版本查詢命令來確認安裝是否成功。

除了 Rust 工具鏈本身之外，建構 Claw Code 還需要一些額外的系統套件。這些套件主要是 Rust 編譯過程中所需的 C 語言函式庫及其開發標頭檔。具體而言，你需要安裝以下幾個關鍵的系統套件：首先是 SSL 開發函式庫，在 Debian 或 Ubuntu 系統上對應的套件名稱是 libssl-dev，在 Fedora 或 CentOS 上則是 openssl-devel，在 macOS 上可以透過 Homebrew 安裝 openssl。SSL 函式庫是 Claw Code 進行 HTTPS 通訊時所必需的，因為所有的 API 呼叫都是透過加密的 HTTPS 連線進行的。其次是 pkg-config 工具，它幫助 Cargo 的建構腳本找到系統上已安裝的函式庫路徑。在大多數 Linux 發行版上，pkg-config 都可以透過套件管理器直接安裝。在 macOS 上，如果你已經安裝了 Homebrew，pkg-config 通常已經作為依賴項被自動安裝。此外，你還需要確保系統上安裝了 CA 憑證套件（在 Debian 或 Ubuntu 上是 ca-certificates），以便正確驗證 HTTPS 連線的伺服器憑證。在 macOS 上，CA 憑證是系統內建的，通常不需要額外安裝。

最後，Git 版本控制系統也是必要的前提條件之一。Claw Code 不僅需要 Git 來取得原始碼，在運行時也會使用 Git 來偵測工作區的狀態、追蹤檔案變更以及執行相關的版本控制操作。你需要安裝 Git 版本二點零或更新的版本。在大多數 Linux 發行版上，Git 都可以透過預設的套件管理器直接安裝。在 macOS 上，Git 通常隨 Xcode 命令列工具一起安裝，你也可以透過 Homebrew 安裝更新的版本。安裝完成後，我們建議你進行基本的 Git 設定，包括設定使用者名稱和電子郵件地址，因為這些資訊在後續的操作中可能會被用到。特別需要注意的是，如果你所在的網路環境使用了企業級的防火牆或代理伺服器，你可能還需要額外配置 Git 的代理設定，以確保能夠順利地從遠端儲存庫取得原始碼。關於代理設定的詳細說明，我們將在第六章的第五節中進行深入探討。

### 4.2 原始碼取得與建構

在確認系統環境已經滿足所有需求之後，下一步就是取得 Claw Code 的原始碼並進行建構。本節將詳細說明從原始碼取得到成功建構的完整流程，包括不同建構模式之間的差異以及建構產出物的位置與用途。

取得 Claw Code 原始碼的標準方式是使用 Git 從版本控制儲存庫進行複製。你需要在終端機中切換到你想要存放原始碼的目錄，然後執行 Git 複製命令。複製完成後，你將得到一個包含完整專案結構的目錄。這個目錄的根層級包含了數個重要的檔案與子目錄，其中最關鍵的是 rust 目錄，它包含了整個 Rust 工作區的原始碼。此外，根目錄還包含了安裝腳本、容器檔案、文件檔案以及測試目錄等。我們建議你在複製完成後，先花一些時間瀏覽整個目錄結構，以便對專案的組織方式有一個直觀的了解。

Claw Code 的 Rust 原始碼組織在一個 Cargo 工作區（workspace）中，這個工作區包含了九個獨立的 crate。這種模組化的設計使得每個 crate 都能夠獨立編譯與測試，同時又能透過工作區機制共享依賴項和建構設定。九個 crate 各司其職：rusty-claude-cli 是主要的二進位 crate，負責命令列介面的入口點與整體流程控制；api crate 處理所有的 HTTP 通訊、認證以及串流回應；runtime crate 管理工作階段、設定檔、權限系統以及工具呼叫；commands crate 定義了所有的斜線命令；tools crate 包含了內建工具的規格定義；plugins crate 管理外掛的生命週期與 MCP 協定；telemetry crate 負責遙測資料的收集與回報；compat-harness crate 提供了 OpenAI 相容層的實作；mock-anthropic-service 則是用於測試目的的模擬服務。這種精心設計的 crate 分離策略不僅提高了程式碼的可維護性，還使得開發者能夠只重新編譯有變更的 crate，從而顯著縮短了迭代開發的建構時間。

進行建構時，你需要先切換到 rust 目錄下，然後使用 Cargo 進行建構。Cargo 支援兩種主要的建構模式：Debug 模式和 Release 模式。Debug 模式是預設的建構模式，它會保留完整的除錯資訊、啟用所有的除錯斷言，並且不會進行任何的程式碼最佳化。Debug 模式的建構速度非常快，非常適合開發過程中的快速迭代。然而，由於缺乏程式碼最佳化，Debug 模式產生的二進位檔案體積較大，執行速度也會明顯慢於 Release 模式。Release 模式則恰恰相反，它會啟用完整的程式碼最佳化（包括內聯展開、死碼消除、迴圈展開等），移除除錯資訊，並停用大部分的執行時檢查。Release 模式的建構時間顯著長於 Debug 模式，但產生的二進位檔案體積更小、執行速度更快。對於日常使用而言，我們建議始終使用 Release 模式進行建構，因為 Claw Code 在處理大量文字串流時，Release 模式的效能優勢尤為明顯。

建構完成後，產生的二進位檔案會被放置在特定的目錄中。對於 Debug 模式，二進位檔案位於工作區根目錄下的 target/debug 目錄中；對於 Release 模式，則位於 target/release 目錄中。主要的可執行檔案名稱是 claw（在某些配置中可能是 rusty-claude-cli）。除了主要的二進位檔案外，建構過程還會在同一目錄中產生一些輔助檔案，包括除錯符號檔案、依賴資訊檔案等。這些輔助檔案在大多數情況下不需要特別關注，但在需要進行效能分析或除錯時可能會派上用場。

值得一提的是，Claw Code 的工作區配置中明確禁止了不安全程式碼（unsafe code），並且啟用了 Clippy 的嚴格模式（pedantic）。這意味著在建構過程中，編譯器會執行非常嚴格的程式碼檢查，任何潛在的問題都會被標記為警告或錯誤。如果你在建構過程中遇到了 Clippy 警告，這通常意味著程式碼中存在可以改進的地方。在正常情況下，主分支的程式碼應該總是能夠在沒有任何警告的情況下通過建構。如果你遇到了建構錯誤，最常見的原因是系統套件缺失（特別是 SSL 開發函式庫）或 Rust 工具鏈版本過舊。請回到上一節確認所有的前提條件都已經滿足。

此外，專案根目錄中的安裝腳本提供了一個六步驟的自動化建構與安裝流水線。這個腳本支援多個參數選項，包括指定 Release 或 Debug 建構模式的選項、跳過驗證步驟的選項，以及透過環境變數指定建構設定檔的選項。對於不想手動執行多個命令的使用者來說，安裝腳本是一個非常方便的選擇。它會自動檢測系統環境、安裝必要的依賴項、執行建構、運行測試，並將最終的二進位檔案安裝到系統路徑中。

### 4.3 二進位安裝與 PATH 設定

成功建構 Claw Code 之後，下一步是將二進位檔案安裝到系統路徑中，使得你能夠在任何目錄下直接透過 claw 命令來使用它。本節將介紹幾種不同的安裝方法，並說明各自的優缺點與適用場景。

最簡單直接的安裝方式是在系統路徑中建立一個指向建構產出物的符號連結。這種方式的優點是不需要複製檔案，建構產出物與安裝的二進位檔案始終保持同步。每當你重新建構專案後，符號連結會自動指向最新的二進位檔案，無需重新安裝。在 Linux 和 macOS 系統上，你通常需要在系統的 bin 目錄中建立符號連結。常見的目標目錄包括使用者本地的 bin 目錄或系統全域的 bin 目錄。使用者本地的 bin 目錄不需要管理員權限，因此是個人開發環境中的首選。然而，你需要確保這個目錄已經被加入到 PATH 環境變數中。大多數現代的 Linux 發行版和 macOS 版本都會自動將使用者本地的 bin 目錄加入 PATH，但如果你發現安裝後無法找到 claw 命令，請檢查你的 shell 設定檔（例如 bashrc 或 zshrc 檔案）中是否包含了正確的 PATH 設定。

另一種安裝方式是使用 Cargo 的安裝功能。Cargo install 命令會自動建構專案並將產生的二進位檔案複製到 Cargo 的 bin 目錄中。這個目錄的預設位置通常是使用者家目錄下的 cargo 子目錄中的 bin 目錄。在安裝 Rust 工具鏈時，rustup 通常已經將這個目錄加入了 PATH 環境變數，因此使用 Cargo install 安裝的二進位檔案通常可以立即使用。這種方式的優點是安裝過程完全自動化，不需要手動建立符號連結或設定路徑。缺點是每次更新都需要重新執行安裝命令，而且安裝過程會重新進行完整的建構，可能需要一些時間。

對於需要在多個環境中使用 Claw Code 的使用者，我們建議將環境變數的設定寫入 shell 的設定檔中，以確保每次開啟新的終端機時都能自動載入。除了 PATH 之外，你可能還需要設定一些 Claw Code 特定的環境變數，例如 API 金鑰等。我們將在第五章的第一節中詳細討論這些環境變數的設定。在此階段，你只需要確保 claw 命令能夠在終端機中被正確找到即可。

對於 Windows 使用者而言，雖然我們建議透過 WSL 2 來使用 Claw Code，但如果你確實需要在 PowerShell 環境中配置路徑，過程會稍有不同。PowerShell 使用不同的環境變數設定機制，你需要修改使用者級別的 PATH 環境變數，或者在 PowerShell 的設定檔中添加路徑設定。需要注意的是，PowerShell 的路徑分隔符號是分號而非冒號，這是 Windows 系統與類 Unix 系統之間的一個重要差異。

安裝完成後，我們強烈建議立即進行快速的驗證測試，確保一切正常。你可以嘗試執行 claw 的版本查詢命令，如果看到版本號碼的輸出，就表示安裝已經成功。如果遇到「命令未找到」的錯誤，請仔細檢查 PATH 環境變數的設定，確認二進位檔案的路徑已經被正確包含在其中。

### 4.4 容器化開發環境

對於希望使用隔離環境進行開發或測試的使用者，Claw Code 提供了完整的容器化支援。專案根目錄中包含了一個 Containerfile，定義了標準的容器映像建構流程。本節將詳細介紹如何使用這個 Containerfile 來建立容器化的開發環境，以及在容器環境中使用 Claw Code 時需要注意的事項。

首先，讓我們了解 Containerfile 的內容與結構。Claw Code 的 Containerfile 基於官方的 Rust Bookworm 映像，這是一個基於 Debian Bookworm 的映像，預裝了完整的 Rust 工具鏈。在此基礎映像之上，Containerfile 會安裝三個必要的系統套件：ca-certificates（用於 HTTPS 連線的憑證驗證）、git（用於版本控制操作）以及 libssl-dev 和 pkg-config（用於建構過程中的 SSL 函式庫連結）。這些套件的選擇與我們在系統需求一節中討論的完全一致，因為容器環境同樣需要這些依賴項才能成功建構 Claw Code。Containerfile 的設計遵循了最小化原則，只安裝了絕對必要的套件，以保持映像的體積盡可能小。

使用 Docker 來建構與運行容器是最常見的方式。你需要在專案的根目錄下執行 Docker 的建構命令，指定 Containerfile 作為建構配置。建構過程可能需要一些時間，因為它需要下載基礎映像、安裝系統套件，以及編譯整個 Rust 專案。建構完成後，你就可以使用產生的映像來啟動容器。在啟動容器時，你需要特別注意環境變數的傳遞——特別是 API 金鑰等敏感資訊。Docker 提供了多種傳遞環境變數的方式，包括命令列參數、環境檔案以及 Docker Compose 設定。對於包含敏感資訊的環境變數，我們建議使用環境檔案或 Docker secrets 機制，而非直接在命令列中指定，以避免這些資訊被記錄在 shell 歷史記錄中。

對於偏好使用 Podman 的使用者，操作流程與 Docker 非常相似。Podman 是一個無守護程序的容器引擎，與 Docker 在命令列介面上高度相容，大多數 Docker 命令都可以直接替換為 Podman 命令來使用。Podman 的一個重要優勢是它不需要以 root 權限運行，這在安全性要求較高的企業環境中尤為有用。使用 Podman 建構和運行容器的命令格式與 Docker 幾乎完全相同，只需要將命令中的 docker 替換為 podman 即可。

在容器環境中使用 Claw Code 有幾個需要特別注意的事項。首先是檔案系統的隔離問題。容器預設使用隔離的檔案系統，這意味著容器內部的檔案變更不會反映到宿主機上，反之亦然。如果你需要讓 Claw Code 存取宿主機上的專案檔案，你需要使用掛載（mount）功能將宿主機的目錄掛載到容器內部。其次是網路連線的問題。容器預設使用橋接網路模式，這在大多數情況下能夠正常工作。但如果你的網路環境使用了代理伺服器，你可能需要在容器內部額外配置代理設定。第三是 OAuth 認證流程的特殊處理。Claw Code 的 OAuth 2.0 認證流程需要在本地端口 4545 上啟動一個回調伺服器，在容器環境中，你需要確保這個端口被正確地映射到宿主機上，否則認證回調將無法正常完成。

容器化開發環境的最大優勢在於一致性與可重現性。無論團隊成員使用的是什麼作業系統或什麼版本的系統套件，只要使用相同的 Containerfile，就能夠建立完全一致的開發環境。這不僅消除了「在我的機器上可以運行」這類經典問題，還使得持續整合與持續部署（CI/CD）流水線的設定變得更加簡單。然而，容器化環境也有一些限制，例如效能開銷（特別是在 macOS 上透過虛擬機器運行 Docker 時）以及與宿主機互動的複雜性。讀者應該根據自己的具體需求和使用場景來決定是否採用容器化開發環境。

### 4.5 驗證安裝

完成安裝之後，進行全面的驗證是確保一切正常運作的重要步驟。本節將介紹三種不同層次的驗證方法，從基本的命令列幫助資訊查看，到深入的健康檢查，再到完整的測試套件執行。

第一層驗證是最基本的——確認 claw 命令能夠被正確執行。你可以透過執行幫助命令來查看 Claw Code 的命令列說明。這個輸出不僅能夠確認安裝已經成功，還能讓你快速了解 Claw Code 支援的所有命令列選項與子命令。幫助資訊的輸出通常包含以下幾個部分：程式的簡短描述、可用的子命令列表、全域選項說明，以及各個選項的預設值。仔細閱讀這個輸出，你可以了解到 Claw Code 支援的三種主要運作模式（REPL 模式、一次性提示模式、子命令模式）、常用的命令列參數（如模型選擇、權限模式、輸出格式等），以及各種高級選項（如推理努力程度、工作階段續接、廣泛工作目錄允許等）。這些資訊在後續的使用過程中會經常用到，建議你將幫助輸出作為日常使用的快速參考。

第二層驗證是使用 Claw Code 內建的健康檢查功能。claw doctor 命令會對系統環境進行全面的診斷，檢查所有必要的組件是否正確安裝與配置。doctor 命令會依序執行六項健康檢查：認證健康檢查（auth_health）會驗證 API 金鑰或認證令牌是否已經設定並且有效；設定檔健康檢查（config_health）會檢查設定檔是否存在、格式是否正確，以及各項設定值是否合理；安裝來源健康檢查（install_source_health）會確認二進位檔案的來源與完整性；工作區健康檢查（workspace_health）會檢查當前目錄是否是一個有效的 Git 儲存庫，以及專案設定檔是否存在；沙盒健康檢查（sandbox_health）會驗證沙盒環境的配置狀態；系統健康檢查（system_health）會確認所有必要的系統工具與函式庫是否可用。每項檢查的結果會以三種診斷等級之一呈現：Ok 表示一切正常，Warn 表示存在潛在問題但不影響基本功能，Fail 表示存在嚴重問題需要立即修復。在剛完成安裝的階段，認證健康檢查可能會顯示 Warn 或 Fail，因為我們尚未設定 API 金鑰，這是完全正常的。其他項目都應該顯示 Ok，如果有任何非預期的 Warn 或 Fail，請根據診斷資訊進行相應的修復。

第三層驗證是執行完整的測試套件。這是最徹底的驗證方式，它會運行 Claw Code 的所有單元測試、整合測試以及文件測試。由於測試套件涵蓋了工作區中所有九個 crate 的功能，成功通過所有測試意味著建構環境完全正確，所有的功能都能夠正常運作。測試的執行需要在 rust 目錄下進行，使用 Cargo 的測試命令，並指定工作區範圍。測試過程可能需要幾分鐘的時間，具體取決於你的硬體配置。如果所有測試都通過了，你會看到一個彙總報告，顯示各個 crate 的測試結果。如果有測試失敗，報告會詳細列出失敗的測試名稱以及失敗的原因，你可以根據這些資訊來診斷問題。需要注意的是，某些整合測試可能需要網路連線或特定的環境配置才能通過，如果你在離線環境中運行測試，一些網路相關的測試可能會失敗，這不一定表示安裝有問題。

完成以上三層驗證之後，你就可以確信 Claw Code 已經正確安裝在你的系統上了。接下來，我們將在第五章中引導你完成首次使用的全部流程。

## 第五章：第一次使用 Claw Code

在成功安裝並驗證了 Claw Code 之後，本章將引導你完成首次使用的全部流程。我們將從最基本的 API 金鑰設定開始，然後逐一探索 Claw Code 提供的三種主要運作模式，最後介紹如何在不同的 AI 模型之間進行選擇與切換。本章的目標是讓你能夠在閱讀完畢後，自信地使用 Claw Code 進行日常的 AI 輔助開發工作。

### 5.1 API 金鑰設定

在使用 Claw Code 與 AI 服務進行互動之前，你需要先設定適當的認證憑證。Claw Code 支援多種 AI 服務提供商，每個提供商都有自己的認證機制。本節將逐一介紹每種認證方式的設定方法，以及常見問題的排除步驟。

Anthropic 是 Claw Code 的預設 AI 服務提供商，也是最常用的選擇。要使用 Anthropic 的服務，你需要取得一個 API 金鑰。API 金鑰可以在 Anthropic 的官方開發者平台上申請與管理。取得 API 金鑰後，你需要將它設定為環境變數 ANTHROPIC_API_KEY。這個環境變數的值應該是你的完整 API 金鑰字串。我們強烈建議將這個環境變數的設定寫入你的 shell 設定檔中（例如在檔案末尾添加 export 語句），這樣每次開啟新的終端機時都會自動載入。需要特別注意的是，API 金鑰是敏感資訊，你應該確保它不會被洩露到公開的程式碼儲存庫中。永遠不要將 API 金鑰直接寫入程式碼或設定檔中，也不要在公開的聊天室或論壇中分享你的金鑰。如果你懷疑金鑰已經被洩露，應該立即在 Anthropic 的開發者平台上撤銷該金鑰並產生一個新的。

除了標準的 API 金鑰認證之外，Claw Code 還支援 OAuth 2.0 Bearer Token 認證方式。這種認證方式透過 ANTHROPIC_AUTH_TOKEN 環境變數來設定。Bearer Token 認證在某些企業環境中特別有用，因為它允許透過集中式的身份認證系統來管理存取權限。Claw Code 的 OAuth 2.0 實作使用了 PKCE（Proof Key for Code Exchange）流程，這是一種專為公開客戶端設計的安全認證流程。在 PKCE 流程中，客戶端會產生一個隨機的驗證碼，並在認證請求中發送其雜湊值。當認證伺服器返回授權碼時，客戶端需要提供原始的驗證碼來交換存取令牌。這種機制有效地防止了授權碼被截獲後的濫用。Claw Code 會在本地端口 4545 上啟動一個臨時的回調伺服器來接收認證回調。你可以透過 claw login 命令或 REPL 中的 /login 斜線命令來啟動 OAuth 認證流程。

Claw Code 的認證系統定義了一個名為 AuthSource 的列舉型別，它包含四種可能的狀態：None 表示沒有任何認證憑證；ApiKey 表示只設定了 API 金鑰；BearerToken 表示只設定了 Bearer Token；ApiKeyAndBearer 表示同時設定了 API 金鑰和 Bearer Token。當兩種認證方式同時存在時，Claw Code 會優先使用 Bearer Token，因為它通常代表更高權限的認證。

對於使用 OpenAI 相容服務的使用者，你需要設定 OPENAI_API_KEY 環境變數。OpenAI 相容認證支援所有遵循 OpenAI API 規範的服務提供商，這包括 OpenAI 本身以及眾多的第三方相容服務。xAI 服務的認證則使用 XAI_API_KEY 環境變數，xAI 提供了 Grok 系列的 AI 模型，包括 Grok-3 和 Grok-3 Mini。DashScope 是阿里巴巴提供的 AI 服務平台，使用 DASHSCOPE_API_KEY 環境變數進行認證。DashScope 提供了 Kimi 系列的 AI 模型，其中包括 Kimi K2.5 等高效能模型。每個提供商的 API 金鑰格式可能略有不同，但設定方式都是相同的——透過環境變數來提供。

當你在使用過程中遇到 401 未授權錯誤時，以下是一些常見的排除步驟。首先，確認環境變數是否正確設定——你可以使用 echo 命令來檢查環境變數的值（但請注意不要在共享的終端機或日誌中暴露完整的金鑰）。其次，確認金鑰是否仍然有效——API 金鑰可能會因為過期、被撤銷或超出配額而失效。第三，確認你使用的金鑰與選定的模型所對應的提供商是否匹配——例如，Anthropic 的 API 金鑰不能用於 OpenAI 的模型，反之亦然。第四，檢查網路連線是否正常——特別是在使用代理伺服器的環境中，確保代理設定正確。最後，嘗試使用 claw doctor 命令進行健康檢查，auth_health 檢查項目會提供關於認證狀態的詳細診斷資訊。

### 5.2 互動式 REPL 模式

互動式 REPL（Read-Eval-Print Loop）模式是 Claw Code 的預設運作模式，也是最常用的使用方式。在 REPL 模式中，你可以與 AI 進行持續的對話，發送提示詞、查看回應、使用各種斜線命令，並且全程保持工作階段的上下文。本節將詳細介紹 REPL 模式的各個面向，幫助你充分利用這個強大的互動介面。

啟動 REPL 模式非常簡單——你只需要在終端機中直接執行 claw 命令，不帶任何子命令或提示詞參數即可。啟動後，你會看到一個互動式的命令提示符號，等待你輸入指令或提示詞。Claw Code 的 REPL 介面基於 LiveCli 結構體實作，它提供了豐富的互動功能，包括行編輯、歷史記錄、自動補全等。REPL 的回應渲染使用了 MarkdownStreamState 渲染器，它整合了 syntect（用於語法高亮）、pulldown-cmark（用於 Markdown 解析）以及 crossterm（用於終端機控制）三個函式庫。這意味著 AI 的回應會以美觀的格式呈現在終端機中，程式碼區塊會有語法高亮，標題和清單也會有適當的格式化。

在 REPL 中發送你的第一個提示詞就像在聊天室中發訊息一樣簡單。你只需要輸入你的問題或指令，然後按下 Enter 鍵即可。Claw Code 會將你的提示詞發送到選定的 AI 模型，並以串流的方式即時顯示回應。串流回應意味著你不需要等待整個回應生成完畢才能開始閱讀——文字會隨著 AI 的生成過程逐步出現在終端機中。這種即時回饋的體驗使得與 AI 的互動更加流暢自然。你可以嘗試各種不同類型的提示詞，例如詢問技術問題、請求程式碼生成、要求解釋概念等。每一輪對話都會被自動記錄在工作階段中，AI 能夠參考之前的對話內容來提供更加精確的回應。

REPL 模式的一個重要特色是其豐富的斜線命令系統。斜線命令是以 / 符號開頭的特殊指令，它們提供了各種實用的功能，讓你能夠在不離開 REPL 的情況下管理和控制 Claw Code 的行為。每個斜線命令都有一個完整的規格定義，稱為 SlashCommandSpec，包含了命令名稱、別名、簡短描述、參數提示以及是否支援工作階段續接等資訊。以下是一些最常用的斜線命令的詳細介紹。

/help 命令會顯示所有可用斜線命令的列表及其簡短描述。這是你在 REPL 中最常用的參考命令。/status 命令會顯示當前工作階段的狀態資訊，包括已使用的令牌數量、當前的模型、權限模式等。/model 命令允許你在不退出 REPL 的情況下切換 AI 模型。/permissions 命令顯示當前的權限設定。/cost 命令顯示當前工作階段的 API 使用成本。/compact 命令會觸發工作階段壓縮，減少上下文中的令牌數量。/clear 命令清除對話歷史，開始一個全新的對話。/config 命令顯示或修改設定。/mcp 命令管理 MCP（Model Context Protocol）伺服器的連線。/doctor 命令在 REPL 中執行健康檢查。/login 命令啟動 OAuth 認證流程。/exit 命令退出 REPL。/memory 命令管理長期記憶。/init 命令在當前目錄初始化 Claw Code 專案。/diff 命令顯示工作區中的檔案差異。/version 命令顯示版本資訊。/export 命令將對話歷史匯出為檔案。/session 命令管理工作階段。/plugins 命令管理外掛。/bughunter 命令啟動自動化的錯誤搜尋模式。/commit 命令建立 Git 提交。/pr 命令建立或管理 Pull Request。

退出 REPL 的方式有多種：你可以使用 /exit 斜線命令、輸入 Ctrl+D 組合鍵（代表輸入結束），或者輸入 Ctrl+C 組合鍵（代表中斷）。在退出之前，Claw Code 會自動保存當前的工作階段，你可以在下次啟動時透過續接功能來恢復之前的對話上下文。

### 5.3 一次性提示模式

除了互動式 REPL 模式之外，Claw Code 還支援一次性提示模式，允許你在命令列中直接發送一個提示詞並獲取回應，而不需要進入互動式的 REPL 環境。這種模式特別適合自動化腳本、CI/CD 流水線以及快速的一次性查詢場景。

一次性提示模式可以透過兩種方式啟動。第一種方式是使用 prompt 子命令，後面跟著你的提示詞文字。第二種方式是使用簡寫的 -p 參數，同樣後面跟著提示詞文字。兩種方式的效果完全相同，只是語法略有不同。在簡寫模式下，你甚至可以直接在 claw 命令後面輸入提示詞文字（不帶任何參數前綴），Claw Code 會自動將其識別為一次性提示。一次性提示模式執行完畢後，程式會自動退出，將控制權返回給 shell。

一次性提示模式支援兩種輸出格式：文字格式（text）和 JSON 格式（json）。文字格式是預設的輸出格式，適合人類直接閱讀，AI 的回應會以純文字的形式輸出到標準輸出。JSON 格式則適合機器處理，AI 的回應會被包裝在一個結構化的 JSON 物件中，方便其他程式或腳本進行解析與處理。你可以透過命令列參數來指定輸出格式。在自動化腳本中，JSON 格式通常是更好的選擇，因為它提供了明確的結構，使得回應的解析更加可靠。

一次性提示模式的一個重要特色是支援標準輸入（stdin）的合併。當你透過管道將其他命令的輸出導入 Claw Code 時，Claw Code 會自動將管道輸入的內容與命令列中指定的提示詞進行合併。合併的格式是「提示詞 + 換行 + 換行 + 標準輸入內容」。這個功能使得 Claw Code 能夠輕鬆地與其他命令列工具進行整合。例如，你可以將一個原始碼檔案的內容透過管道傳遞給 Claw Code，並在提示詞中要求 AI 對該程式碼進行審查或解釋。這種管道整合的能力使得 Claw Code 成為了一個強大的命令列 AI 工具，能夠無縫融入現有的 Unix 風格工作流程中。

在腳本整合方面，一次性提示模式提供了極大的靈活性。你可以在 Bash 腳本、Makefile、CI/CD 流水線設定檔中直接呼叫 Claw Code，將 AI 的能力整合到自動化工作流程中。例如，你可以建立一個每日自動執行的腳本，使用 Claw Code 來分析 Git 日誌中的變更並生成程式碼審查摘要。或者，你可以在 CI/CD 流水線中使用 Claw Code 來自動分析測試失敗的原因並提供修復建議。一次性提示模式的非互動特性使得它非常適合這些自動化場景，因為它不需要人工介入就能完成整個查詢流程。

### 5.4 子命令模式

Claw Code 除了提供 REPL 模式和一次性提示模式之外，還支援一系列獨立的子命令，用於執行各種管理和診斷任務。這些子命令不需要與 AI 進行互動，它們直接在本地執行特定的操作。本節將介紹 Claw Code 中最重要的幾個子命令。

doctor 子命令是我們在安裝驗證階段已經初步接觸過的健康檢查工具。在實際使用過程中，doctor 命令是診斷問題的首選工具。它會系統性地檢查六個方面的健康狀態：認證健康、設定檔健康、安裝來源健康、工作區健康、沙盒健康以及系統健康。每個檢查項目都會返回一個包含診斷等級（Ok、Warn 或 Fail）和詳細說明的結果。當你在使用過程中遇到任何異常時，第一步應該是執行 claw doctor 命令來獲取系統的整體健康狀態。doctor 命令的輸出會清楚地指出問題所在，並在可能的情況下提供修復建議。

status 子命令顯示 Claw Code 的當前狀態資訊，包括已載入的設定、活動的工作階段、當前選定的模型以及認證狀態等。這個命令在你需要快速了解 Claw Code 的運行狀態時非常有用。它不會修改任何設定或狀態，只是純粹的資訊查詢。

sandbox 子命令用於管理沙盒環境。沙盒是一種隔離的執行環境，它限制了 AI 代理能夠存取的檔案系統範圍和執行的操作類型。在處理不信任的程式碼或在安全性要求較高的環境中，沙盒功能能夠提供額外的保護層。sandbox 子命令允許你查看、啟用或停用沙盒設定。

init 子命令用於在當前目錄中初始化一個新的 Claw Code 專案。我們將在第六章的第一節中對這個命令進行深入的討論。簡單來說，init 命令會在當前目錄中建立必要的設定檔和目錄結構，使得 Claw Code 能夠在該目錄中正常運作。

state 子命令顯示 Claw Code 的內部狀態資訊，這主要用於除錯目的。它會輸出比 status 命令更詳細的內部資料結構，包括設定檔的解析結果、工作階段的中繼資料等。一般使用者通常不需要使用這個命令，但在遇到難以診斷的問題時，state 命令的輸出可以提供額外的線索。

config 子命令用於查看和管理 Claw Code 的設定。它可以顯示當前的有效設定（包括所有層級的設定合併結果），也可以顯示特定設定項目的值和來源。diff 子命令顯示工作區中的檔案差異，這在使用 Claw Code 進行程式碼修改後特別有用。export 子命令允許你將對話歷史匯出為特定格式的檔案。version 子命令顯示 Claw Code 的版本資訊，包括建構日期和 Git 提交雜湊值。

### 5.5 模型選擇與切換

Claw Code 支援多種 AI 模型，每個模型都有不同的特性、效能以及成本。正確地選擇和使用模型對於獲得最佳的使用體驗至關重要。本節將詳細介紹 Claw Code 的模型管理機制，包括內建模型別名、自定義別名、提供商自動偵測以及各種指定模型的方式。

為了方便使用，Claw Code 為最常用的模型定義了一組內建的短別名。這些別名讓你不需要記住冗長的完整模型名稱，只需要輸入簡短的縮寫即可。目前定義的內建別名包括：opus 對應到 claude-opus-4-6，這是 Anthropic 最強大的推理模型；sonnet 對應到 claude-sonnet-4-6，它在效能與成本之間取得了良好的平衡；haiku 對應到 claude-haiku-4-5-20251213，這是最快速且成本最低的 Claude 模型；grok 和 grok-3 都對應到 grok-3，這是 xAI 的旗艦模型；grok-mini 對應到 grok-3-mini，它是 Grok 系列中更輕量的選擇；kimi 對應到 kimi-k2.5，這是阿里巴巴 DashScope 平台上的高效能模型。Claw Code 的預設模型是 claude-opus-4-6（即 opus 別名），如果你沒有明確指定要使用的模型，Claw Code 將會自動使用這個預設模型。

除了內建別名之外，你還可以在設定檔中定義自己的自定義模型別名。自定義別名允許你為任何支援的模型建立自己偏好的短名稱。例如，如果你的團隊有一個特定的命名慣例，或者你經常使用的模型名稱特別冗長，自定義別名就能夠大大提高你的使用效率。自定義別名的設定位於專案設定檔的 aliases 區段中，它是一個簡單的鍵值對映射，其中鍵是你定義的別名，值是對應的完整模型名稱。

Claw Code 使用了一個智慧的提供商自動偵測機制來確定應該使用哪個 AI 服務提供商。這個機制基於模型名稱的前綴來判斷：以 claude 開頭的模型名稱會自動路由到 Anthropic 提供商；以 grok 開頭的模型名稱會路由到 xAI 提供商；以 gpt 開頭的模型名稱會路由到 OpenAI 提供商。如果模型名稱不匹配任何已知的前綴模式，系統會進一步檢查已設定的環境變數來推斷提供商。例如，如果只設定了 XAI_API_KEY 而沒有設定其他金鑰，系統會假定使用 xAI 提供商。如果無法透過以上兩種方式確定提供商，系統會預設使用 Anthropic 作為回退選項。

每個模型都有其特定的令牌限制，這些限制定義了模型在單次互動中能夠處理的最大文字量。令牌限制分為兩個維度：輸出令牌限制和上下文令牌限制。輸出令牌限制規定了模型在單次回應中能夠生成的最大令牌數量，而上下文令牌限制則規定了模型能夠處理的輸入與輸出令牌的總和。目前各模型的令牌限制如下：opus 模型的輸出限制為三萬二千個令牌，上下文限制為二十萬個令牌；sonnet 模型的輸出限制為六萬四千個令牌，上下文限制為二十萬個令牌；grok-3 模型的輸出限制為六萬四千個令牌，上下文限制為十三萬一千個令牌；kimi 模型的輸出限制為一萬六千個令牌，但上下文限制高達二十五萬六千個令牌。了解這些限制對於有效地使用模型非常重要。當你的對話上下文接近令牌限制時，Claw Code 會自動觸發壓縮機制來減少令牌使用量，但如果你能夠提前規劃令牌的使用，就能避免不必要的壓縮操作，從而獲得更好的對話品質。

在指定要使用的模型時，Claw Code 遵循一個明確的優先順序，稱為 ModelSource 優先順序：命令列參數（Flag）優先於環境變數（Env），環境變數優先於設定檔（Config），設定檔優先於預設值（Default）。這意味著你可以在設定檔中設定一個常用的模型作為預設值，在需要時透過環境變數或命令列參數來臨時覆蓋。在 REPL 模式中，你還可以使用 /model 斜線命令來即時切換模型，而不需要退出並重新啟動。命令列中使用 --model 參數可以指定你想要使用的模型名稱或別名。

選擇模型時，你應該考慮以下幾個因素：任務的複雜程度、回應速度的要求、成本預算以及所需的上下文窗口大小。對於需要深度推理和複雜分析的任務，opus 模型通常是最佳選擇，因為它具有最強大的推理能力。對於日常的程式碼生成和問答任務，sonnet 模型提供了良好的效能與成本平衡。對於簡單的查詢和快速的程式碼補全，haiku 模型的速度優勢使其成為首選。如果你需要處理非常長的文件或大量的程式碼上下文，kimi 模型的超大上下文窗口（二十五萬六千個令牌）將會非常有用。在團隊環境中，我們建議在專案的設定檔中統一設定模型選擇，以確保所有團隊成員使用一致的配置。

## 第六章：專案初始化與設定

完成了第五章中的首次使用體驗之後，本章將深入探討 Claw Code 的專案初始化與設定機制。一個正確配置的專案不僅能夠提升 AI 輔助開發的效率，還能確保團隊成員之間的設定一致性，以及在安全性和權限控制方面的合規性。本章將涵蓋從專案初始化到會話管理的各個方面，幫助你建立一個完善的 Claw Code 工作環境。

### 6.1 claw init 深度解析

claw init 命令是開始使用 Claw Code 進行專案開發時的第一步。這個命令會在當前目錄中建立所有必要的設定檔和目錄結構，為 Claw Code 的正常運作奠定基礎。本節將深入解析 init 命令的執行流程、產生的檔案結構以及各個設定檔的用途與內容。

當你在一個專案目錄中執行 claw init 命令時，系統會依序執行以下步驟。首先，它會檢查當前目錄的狀態，確認是否已經存在先前的初始化結果。如果偵測到目錄中已經存在 Claw Code 的設定檔，init 命令會根據情況選擇更新或跳過這些檔案，而不會盲目地覆蓋已有的設定。這種智慧的行為由 InitStatus 列舉型別來表示，它包含三種可能的狀態：Created 表示檔案是新建立的；Updated 表示檔案已存在但被更新了；Skipped 表示檔案已存在且不需要任何變更。

init 命令會建立和修改以下幾個關鍵的檔案與目錄。首先是 .claw.json 設定檔，這是 Claw Code 的專案級設定檔案，它包含了所有與專案相關的設定項目。這個 JSON 格式的檔案會被建立在專案的根目錄中，並且應該被加入到版本控制系統中，以便團隊成員能夠共享相同的專案設定。.claw.json 設定檔包含了多個設定區段，包括模型設定（model）、模型別名（aliases）、權限設定（permissions）、鉤子設定（hooks）、外掛設定（plugins）、MCP 伺服器設定（mcp，其中包含伺服器的命令、參數、環境變數、是否停用等資訊）、OAuth 設定（oauth）、沙盒設定（sandbox）以及提供商回退設定（providerFallbacks）。初始建立的設定檔會使用合理的預設值，你可以在之後根據專案的具體需求進行修改。

其次是 .claw/ 目錄，這是 Claw Code 用於儲存運行時資料的本地目錄。這個目錄通常不應該被加入到版本控制系統中，因為它包含了使用者特定的資料，例如工作階段記錄和本地覆蓋設定。.claw/ 目錄下的結構包括 sessions/ 子目錄（用於儲存工作階段的 JSONL 檔案）以及 settings.local.json（用於儲存本地覆蓋設定）。init 命令還會自動更新專案的 .gitignore 檔案，將 .claw/ 目錄加入到忽略清單中，以防止這些本地資料被意外地提交到版本控制系統中。

第三個重要的檔案是 CLAUDE.md，這是一個 AI 指導檔案，它為 AI 提供了關於專案的背景資訊、編碼規範、技術棧說明以及其他有助於 AI 生成高品質回應的上下文資訊。CLAUDE.md 檔案的內容會被自動包含在發送給 AI 的系統提示中，使得 AI 能夠更好地理解專案的特點和要求。這個檔案應該被加入到版本控制系統中，並隨著專案的演進而持續更新。一個良好維護的 CLAUDE.md 檔案能夠顯著提升 AI 輔助開發的品質，因為它確保了 AI 始終擁有最新的專案上下文。

init 命令的設計體現了 Claw Code 的一個重要原則：「合理的預設值，靈活的自定義」。開箱即用的預設設定已經能夠滿足大多數使用場景的需求，但同時也為高級使用者提供了充分的自定義空間。我們建議在執行 init 命令之後，花一些時間審閱自動生成的設定檔，了解每個設定項目的用途，然後根據你的具體需求進行調整。

### 6.2 設定檔體系

Claw Code 採用了一個精心設計的五層設定合併體系，這個體系確保了設定的靈活性與可管理性。理解這個體系的工作方式是正確配置 Claw Code 的關鍵。本節將詳細說明每一層設定的來源、優先順序以及適用場景。

五層設定的合併順序從低優先順序到高優先順序依次為：編譯預設值（compiled defaults）、使用者全域設定（user global settings）、專案設定（project settings）、本地覆蓋設定（local override settings）以及命令列參數（CLI flags）。在這個合併過程中，高優先順序的設定會覆蓋低優先順序的同名設定。這意味著命令列參數具有最高的優先順序，它會覆蓋所有其他來源的設定；而編譯預設值具有最低的優先順序，只在沒有其他設定來源提供對應設定項目時才會生效。

編譯預設值是直接寫入 Claw Code 原始碼中的設定值，它們定義了所有設定項目的初始預設值。這些預設值是經過精心選擇的，能夠在大多數使用場景中提供合理的行為。你通常不需要關心編譯預設值的具體內容，除非你需要了解某個設定項目在沒有被明確指定時的預設行為。

使用者全域設定位於使用者家目錄下的設定目錄中，具體路徑通常是 ~/.config/claw/settings.json。這個設定檔適合存放與特定專案無關的個人偏好設定，例如你偏好的預設模型、終端機顯示偏好等。全域設定會應用到你使用 Claw Code 的所有專案中，除非被更高優先順序的設定所覆蓋。如果你在多個專案中使用 Claw Code，全域設定是統一管理通用偏好的理想位置。需要注意的是，全域設定檔不會被 claw init 命令自動建立，你需要手動建立它。

專案設定位於專案根目錄中的 .claw.json 檔案中。這是最常用的設定層級，它包含了與特定專案相關的所有設定。專案設定應該被加入到版本控制系統中，以便團隊成員能夠共享相同的設定。典型的專案設定包括模型選擇、自定義模型別名、權限規則、MCP 伺服器配置等。設定檔的 ConfigSource 體系標識了三個明確的來源等級：User 對應使用者全域設定，Project 對應專案設定，Local 對應本地覆蓋設定。

本地覆蓋設定位於 .claw/settings.local.json 檔案中。這個設定檔的用途是存放不應該被提交到版本控制系統中的設定，例如個人的 API 金鑰（雖然我們更推薦使用環境變數）、針對特定開發環境的路徑設定等。本地覆蓋設定的優先順序高於專案設定，這使得開發者能夠在不修改共享設定檔的情況下，根據自己的需求進行個性化調整。

命令列參數具有最高的優先順序，它們會覆蓋所有其他層級的設定。這種設計使得你能夠在啟動 Claw Code 時臨時調整任何設定，而不需要修改任何設定檔。例如，你可以透過 --model 參數臨時切換到不同的模型，或透過 --dangerously-skip-permissions 參數臨時跳過權限檢查。命令列參數的臨時性特點使其非常適合一次性的設定調整或測試目的。

RuntimeFeatureConfig 結構體是 Claw Code 在運行時使用的統一設定物件，它包含了所有的功能設定，包括鉤子（hooks）、外掛（plugins）、MCP 設定、OAuth 設定、模型設定、模型別名（aliases）、權限模式（permission_mode）、權限規則（permission_rules）、沙盒設定（sandbox）、提供商回退設定（provider_fallbacks）以及信任根目錄（trusted_roots）。五層設定的合併結果最終會被填充到這個結構體中，Claw Code 的各個組件在運行時都會從這個結構體中讀取設定值。

當你在設定過程中遇到問題時，可以使用 claw config 子命令或 REPL 中的 /config 斜線命令來查看當前的有效設定。這個命令會顯示每個設定項目的最終值以及它來自哪個設定層級，這對於診斷設定合併相關的問題非常有幫助。此外，claw doctor 命令中的 config_health 檢查也會驗證設定檔的格式和內容是否正確。

### 6.3 權限模式設定

安全性是 Claw Code 設計中的一個核心考量。作為一個能夠代理執行各種操作的 AI 工具，權限控制機制對於防止意外或惡意的操作至關重要。Claw Code 提供了一個精細的權限管理系統，允許使用者根據自己的安全需求和信任程度來配置 AI 代理的行為權限。本節將詳細介紹 Claw Code 的權限模式體系以及權限規則的配置方法。

Claw Code 定義了五種權限模式，每種模式代表了不同的安全等級和功能限制。ReadOnly 模式是最嚴格的模式，在此模式下，AI 只能讀取檔案和資訊，不能進行任何的寫入操作。這個模式適合在你只需要 AI 來分析和解釋程式碼，但不希望它修改任何檔案時使用。WorkspaceWrite 模式允許 AI 在工作區目錄中進行寫入操作，但不能存取工作區以外的檔案系統。這是大多數日常使用場景的推薦模式，因為它在功能性和安全性之間取得了良好的平衡。DangerFullAccess 模式（也可透過 --dangerously-skip-permissions 命令列參數啟用）完全移除了所有的權限限制，AI 可以執行任何操作。這個模式只應該在你完全信任 AI 的行為並且了解潛在風險的情況下使用。Prompt 模式表示在每次需要執行敏感操作時，都會提示使用者進行確認。Allow 模式則是一種更細粒度的控制方式，它基於具體的權限規則來決定是否允許特定的操作。

Claw Code 的權限規則系統使用 PermissionPolicy 結構體來定義精細的存取控制策略。PermissionPolicy 包含三組規則：allow_rules 定義了明確允許的操作；deny_rules 定義了明確禁止的操作；ask_rules 定義了需要使用者確認的操作。當 AI 嘗試執行一個操作時，系統會按照特定的順序檢查這些規則：首先檢查 deny_rules，如果匹配則直接拒絕；然後檢查 allow_rules，如果匹配則直接允許；最後檢查 ask_rules，如果匹配則提示使用者確認；如果沒有匹配任何規則，則根據當前的權限模式來決定預設行為。

權限規則可以在專案設定檔（.claw.json）中的 permissions 區段中定義，也可以透過命令列參數在啟動時指定。在團隊環境中，我們建議在專案設定檔中定義統一的權限規則，以確保所有團隊成員使用一致的安全策略。你可以根據專案的具體需求來自定義規則。例如，你可能希望允許 AI 在特定的目錄中建立和修改檔案，但禁止它存取包含敏感資訊的設定檔。或者，你可能希望允許 AI 執行特定的 shell 命令（如測試和建構命令），但禁止它執行刪除操作。

命令列中的 --dangerously-skip-permissions 參數是一個全域的權限覆蓋開關，它會繞過所有的權限檢查。這個參數的名稱刻意包含了「dangerously」（危險地）這個詞，以提醒使用者這是一個具有潛在風險的操作。在使用這個參數時，你應該完全了解 AI 可能執行的所有操作，並確保工作環境中沒有你不想被修改的重要檔案。此外，--allow-broad-cwd 參數允許 AI 在更廣泛的工作目錄範圍內操作，但仍然受到其他權限規則的約束。

--reasoning-effort 參數雖然不直接與權限相關，但它影響了 AI 在處理請求時的推理深度。這個參數支援三個等級：low（低）、medium（中）和 high（高）。更高的推理努力等級通常會產生更加深思熟慮的回應，但也會消耗更多的令牌和時間。在涉及安全相關的操作時，我們建議使用 high 等級，以確保 AI 能夠充分考慮操作的潛在影響。

### 6.4 工作階段管理

工作階段（Session）是 Claw Code 中用於維護對話上下文和狀態的核心概念。每一次與 AI 的互動都在一個工作階段的框架內進行，工作階段記錄了完整的對話歷史、系統狀態以及中繼資料。本節將深入介紹 Claw Code 的工作階段管理機制，包括工作階段的儲存格式、續接功能、壓縮機制以及旋轉策略。

每個工作階段都以 JSONL（JSON Lines）格式儲存在 .claw/sessions/ 目錄中，檔案名稱使用工作階段的唯一識別碼（session_id）。JSONL 格式是一種每行一個 JSON 物件的文字格式，它具有幾個重要的優點：首先，它支援增量寫入，新的對話訊息可以直接追加到檔案末尾，而不需要重新序列化整個檔案；其次，它易於用標準的文字處理工具進行分析和處理；第三，即使檔案在寫入過程中被中斷，已寫入的部分仍然是有效的。工作階段檔案的目前版本號為 1，每條記錄包含了以下欄位：version（版本號）、session_id（工作階段唯一識別碼）、created_at_ms（建立時間戳，毫秒精度）、updated_at_ms（最後更新時間戳）、messages（對話訊息列表）、compaction（壓縮記錄）、fork（分叉記錄）、workspace_root（工作區根目錄）、prompt_history（提示詞歷史）、last_health_check_ms（最後健康檢查時間戳）以及 model（使用的模型名稱）。

工作階段續接（resume）功能允許你在中斷後恢復之前的對話上下文。Claw Code 提供了三種續接方式：使用 --resume latest 參數會自動找到並續接最近的一個工作階段，這是最常用的續接方式；使用 --resume 後面跟著工作階段的檔案路徑，可以續接指定路徑的工作階段檔案；使用 --resume 後面跟著工作階段的識別碼，則會根據識別碼在 sessions 目錄中尋找對應的工作階段。續接功能在很多場景中都非常實用，例如當你的終端機意外關閉時、當你需要在不同的時間段繼續之前的工作時，或者當你想要基於某個歷史工作階段進行分支探索時。

工作階段壓縮（compaction）機制是 Claw Code 用於管理令牌使用量的重要功能。隨著對話的進行，工作階段中的訊息數量和令牌總量會持續增長。當令牌數量超過特定的閾值時（預設為一萬個令牌），系統會自動觸發壓縮操作。壓縮的過程如下：系統會保留最近的四條訊息不動，然後將之前的所有訊息交給 AI 生成一個簡潔的摘要。這個摘要會替代被壓縮的訊息，從而顯著減少令牌的使用量。壓縮的結果記錄在 SessionCompaction 結構體中，包含壓縮次數（count）、被移除的訊息數量（removed_message_count）以及生成的摘要文字（summary）。你也可以在 REPL 中使用 /compact 斜線命令手動觸發壓縮操作。需要注意的是，壓縮是一個有損操作——被壓縮的訊息的細節可能在摘要中被省略。因此，如果你需要精確地引用之前對話中的具體內容，最好在壓縮發生之前就完成相關的操作。

工作階段旋轉（rotation）是另一個重要的管理機制。當一個工作階段的 JSONL 檔案體積超過二百五十六 KB 時，系統會自動進行旋轉。旋轉的過程是將當前的工作階段檔案重命名為備份檔案，然後建立一個新的工作階段檔案。系統最多保留三個備份檔案，超過限制的最舊備份會被自動刪除。這種旋轉機制確保了磁碟空間不會被無限增長的工作階段檔案所耗盡，同時又保留了足夠的歷史記錄用於回溯和分析。

在實際使用中，工作階段管理通常是自動進行的，你不需要手動介入。但了解這些機制的工作原理可以幫助你更好地理解 Claw Code 的行為，並在遇到問題時進行有效的診斷。例如，如果你發現 AI 似乎「忘記」了之前對話中的某些內容，這可能是因為壓縮操作將那些內容濃縮成了摘要。在這種情況下，你可以透過查看工作階段的 JSONL 檔案來確認壓縮是否發生，以及摘要的內容是否充分保留了必要的資訊。

### 6.5 HTTP 代理設定

在企業網路環境中，直接的網際網路存取通常受到限制，所有的外部通訊都需要透過代理伺服器進行。由於 Claw Code 需要與外部的 AI 服務 API 進行通訊，正確配置 HTTP 代理是在這類環境中使用 Claw Code 的必要步驟。本節將詳細介紹 Claw Code 的代理配置機制以及在企業環境中的最佳實踐。

Claw Code 的代理配置透過 ProxyConfig 結構體來管理，這個結構體包含了以下幾個關鍵欄位：http_proxy 指定用於 HTTP 請求的代理伺服器地址；https_proxy 指定用於 HTTPS 請求的代理伺服器地址（由於 AI API 通常使用 HTTPS，這個設定在大多數情況下是更重要的）；no_proxy 定義了不需要透過代理存取的主機或網域清單；proxy_url 則是一個統一的代理 URL 設定，當 http_proxy 和 https_proxy 未分別指定時使用。ProxyConfig 提供了一個 from_env() 方法，它會自動從系統環境變數中讀取代理設定。對應的環境變數名稱遵循業界標準：HTTP_PROXY（或小寫的 http_proxy）用於 HTTP 代理，HTTPS_PROXY（或小寫的 https_proxy）用於 HTTPS 代理，NO_PROXY（或小寫的 no_proxy）用於代理排除清單。

設定代理的最簡單方式是透過環境變數。你只需要在你的 shell 設定檔中匯出對應的環境變數，指定你的代理伺服器的地址和端口號即可。代理伺服器的 URL 格式通常包括協定前綴、主機名和端口號。如果代理伺服器需要認證，你可能還需要在 URL 中包含使用者名稱和密碼（格式為 protocol://username:password@host:port），但這種方式會在環境變數中暴露密碼，在安全性要求較高的環境中可能不是最佳選擇。

NO_PROXY 環境變數用於定義不需要透過代理存取的目標清單。這個清單是以逗號分隔的主機名、網域名或 IP 位址列表。常見的排除項目包括本機地址（localhost 和 127.0.0.1）以及內部網路的網域名。正確配置 NO_PROXY 清單對於避免不必要的代理路由非常重要——如果你的某些服務部署在內部網路中，將它們加入排除清單可以避免代理伺服器成為通訊的瓶頸。此外，由於 Claw Code 的 OAuth 認證回調使用本地端口 4545，確保 localhost 被加入到 NO_PROXY 清單中是非常重要的，否則認證回調可能會失敗。

ProxyConfig 的 build_http_client() 方法會根據配置建立一個正確設定了代理的 HTTP 客戶端。這個方法會自動處理代理設定的各種細節，包括代理認證、SSL 證書驗證等。在大多數情況下，你只需要設定好環境變數，Claw Code 就能自動地使用代理進行所有的外部通訊。

在企業環境中配置代理時，有幾個常見的注意事項需要特別關注。首先，許多企業代理伺服器使用自簽名的 SSL 證書或企業內部的 CA 證書。在這種情況下，你可能需要將企業的 CA 證書添加到系統的信任根憑證庫中，否則 HTTPS 連線可能會因為證書驗證失敗而被拒絕。其次，某些企業代理會對 HTTPS 流量進行中間人檢查（MITM inspection），這可能會干擾 Claw Code 與 AI API 之間的加密通訊。如果你遇到了無法解釋的連線錯誤，可以與你的網路管理員確認是否存在這種情況。第三，在使用代理伺服器時，API 請求的延遲可能會增加。如果你發現 Claw Code 的回應速度顯著下降，可以嘗試使用 claw doctor 命令的網路相關檢查來診斷問題。最後，如果你的環境中有多個代理伺服器（例如生產環境和開發環境使用不同的代理），你可以使用 Claw Code 的本地覆蓋設定來為不同的專案配置不同的代理。

在某些特殊情況下，你可能需要完全繞過代理直接進行連線。這通常在你使用 VPN 連線到外部網路時會發生。在這種情況下，你可以臨時取消代理環境變數的設定，或者將目標 API 伺服器的網域加入到 NO_PROXY 清單中。但請注意，繞過企業代理可能違反公司的網路安全政策，在做出這個決定之前，建議先與你的網路安全團隊進行溝通。

透過正確的代理配置，即使在受限的企業網路環境中，你也能夠順暢地使用 Claw Code 與外部 AI 服務進行通訊。代理配置是一項一次性的設定工作，完成後通常不需要頻繁修改。如果你在配置過程中遇到了任何問題，claw doctor 命令的系統健康檢查會提供有用的診斷資訊，幫助你快速定位和解決問題。
