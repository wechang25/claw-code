# 第八部分：測試架構、遙測系統與未來展望

作為本書的最後一部分，我們將探討 Claw Code 確保品質的測試架構、提供可觀測性的遙測系統、以及這個專案的未來發展方向。一個優秀的軟體系統不僅要有好的功能設計，還需要完善的測試覆蓋來保障正確性，以及全面的遙測來支援運維和最佳化。

## 第二十二章：測試架構

### 22.1 mock-anthropic-service

mock-anthropic-service crate 是 Claw Code 測試架構的核心元件。它實現了一個完整的 Anthropic API 模擬服務，能夠在不需要真實 API 金鑰和網路連線的情況下，模擬各種 AI 回應場景。

這個模擬服務內建了十個測試場景，每個場景對應一種特定的使用案例。StreamingText 場景模擬基本的串流文字回應，驗證 SSE 解析和增量渲染的正確性。ReadFileRoundtrip 場景模擬一次完整的讀檔往返——AI 模型請求讀取一個檔案，系統執行讀取操作並將結果回傳給模型，模型基於檔案內容生成回應。GrepChunkAssembly 場景模擬 grep 搜尋結果的分塊組裝。WriteFileAllowed 和 WriteFileDenied 場景分別模擬寫檔操作在不同權限模式下的行為。MultiToolTurnRoundtrip 場景模擬一個涉及多個工具呼叫的複雜回合。BashStdoutRoundtrip 場景模擬 Bash 命令的執行和輸出收集。BashPermissionPromptApproved 和 BashPermissionPromptDenied 場景分別模擬 Bash 權限請求被核准和拒絕的情況。PluginToolRoundtrip 場景模擬外掛工具的往返呼叫。

每個測試場景都預先定義了完整的 SSE 事件序列，包括 message_start、content_block_start、content_block_delta、content_block_stop、message_delta 和 message_stop 等事件。模擬服務在收到 API 請求後，會根據請求中的特定標記（如系統提示詞中的關鍵字或工具結果的內容）選擇對應的場景，然後按照預定義的順序推送 SSE 事件。

### 22.2 泛型測試策略

Claw Code 的泛型 ConversationRuntime<C, T> 設計使得核心對話邏輯可以被完整地單元測試。在測試中，C 被替換為 mock-anthropic-service 提供的模擬客戶端，T 被替換為預設回應的虛擬工具執行器。這樣，測試可以驗證對話引擎的所有核心行為——多輪對話管理、工具呼叫串接、壓縮觸發、錯誤處理等——而完全不依賴外部服務。

這種測試策略的優勢是多方面的。首先，測試是確定性的——模擬服務的回應是預先定義的，不存在因為模型行為的隨機性而導致的測試不穩定。其次，測試是快速的——沒有網路延遲，沒有 API 速率限制。最後，測試是全面的——可以模擬各種邊緣情況和錯誤場景，包括那些在真實環境中很難觸發的情況。

### 22.3 整合測試策略

除了單元測試之外，Claw Code 還採用了多層次的整合測試策略。在 crate 層面，每個 crate 都有自己的測試模組，驗證 crate 內部各模組之間的協作。在工作區層面，tests 目錄包含跨 crate 的整合測試，驗證不同層之間的互動。

Claw Code 的 CI 管線包含三個主要的驗證步驟：cargo fmt 確保程式碼格式的一致性，cargo clippy（配合 pedantic 等級和 deny warnings 旗標）確保程式碼品質，cargo test --workspace 執行工作區中所有 crate 的測試。這三個步驟必須全部通過，程式碼才能被合併。

## 第二十三章：遙測系統

### 23.1 事件追蹤

telemetry crate 定義了五種遙測事件類型，涵蓋了系統運行時期的關鍵活動。HttpRequestStarted 記錄每一個 HTTP 請求的發起，包含請求的 URL、方法和時間戳記。HttpRequestSucceeded 記錄成功完成的請求，包含回應狀態碼和延遲。HttpRequestFailed 記錄失敗的請求，包含錯誤描述。Analytics 是通用的分析事件，包含命名空間、動作和自訂屬性。SessionTrace 是工作階段追蹤記錄，用於記錄工作階段中的重要操作。

SessionTracer 是工作階段追蹤的核心元件。它為每個工作階段維護一個遞增的序列號（使用 AtomicU64 保證執行緒安全），每個追蹤記錄都包含工作階段 ID、序列號、操作名稱、毫秒級時間戳記以及自訂的屬性映射。

### 23.2 Sink 架構

遙測事件透過 Sink（接收器）機制進行處理。Claw Code 提供了兩種 Sink 實作。MemoryTelemetrySink 將所有事件儲存在記憶體中，主要用於測試——測試可以在執行後檢查 Sink 中收集的事件，驗證遙測的正確性。JsonlTelemetrySink 將事件序列化為 JSONL 格式並追加寫入檔案，用於生產環境的遙測資料收集。

Sink 介面的設計允許使用者實現自定義的 Sink——例如，將遙測事件發送到 Prometheus、Grafana、Datadog 等外部監控平台。

### 23.3 Token 用量追蹤與成本估算

usage.rs 模組提供了精確的 token 用量追蹤和成本估算功能。UsageTracker 在每次 API 呼叫後更新累計用量，包括輸入 token、輸出 token、快取創建 token 和快取讀取 token 四個維度。

ModelPricing 結構定義了每種模型的定價表，包含每百萬 token 的輸入成本、輸出成本、快取創建成本和快取讀取成本。系統內建了主要模型的定價資訊：Claude Opus 的輸入成本為每百萬 token 十五美元，輸出成本為每百萬 token 七十五美元；Claude Sonnet 的輸入成本為每百萬 token 三美元，輸出成本為每百萬 token 十五美元；Claude Haiku 的輸入成本為每百萬 token 零點二五美元，輸出成本為每百萬 token 一點二五美元。

UsageCostEstimate 結構提供了更細緻的成本分解，將總成本拆分為輸入成本、輸出成本、快取創建成本和快取讀取成本四個部分。使用者可以透過 /cost 斜線命令在 REPL 中查看當前工作階段的累計成本，幫助控制 API 支出。

## 第二十四章：未來展望

### 24.1 持續演進的架構

Claw Code 的架構被設計為支援持續演進。Cargo Workspace 的模組化結構使得新增 crate 或模組不會影響現有的功能。trait-based 的多態設計使得新增提供商、新增工具或新增傳輸方式只需要實現對應的 trait，而不需要修改核心邏輯。全域 Registry 模式使得新增資源類型（如新類型的 Worker 或新的排程機制）是自然的擴充。

### 24.2 多模型協作

隨著 AI 模型的多樣化和專業化，未來的 AI 代理人框架需要支援多模型協作——不同的任務使用不同的模型。ProviderFallbackConfig 已經為這種場景提供了基礎設施，允許定義主要模型和回退模型。未來的擴充可能包括：根據任務類型自動選擇最適合的模型、在同一個工作流程中混用不同提供商的模型、以及基於成本和延遲的動態模型路由。

### 24.3 安全性的持續加固

安全性是一個永無止境的追求。Claw Code 的多層安全防禦模型提供了堅實的基礎，但隨著 AI 模型能力的增強和使用場景的多樣化，安全模型也需要持續演進。可能的發展方向包括：更精細的檔案系統沙箱（基於 seccomp 或 AppArmor）、更智能的 Bash 指令分析（基於抽象語法樹而非關鍵字匹配）、以及跨 Worker 的安全策略傳播機制。

### 24.4 生態系統建設

MCP 協定的引入為 Claw Code 打開了生態系統建設的大門。隨著越來越多的 MCP 伺服器被開發和共享，Claw Code 的使用者將能夠輕鬆地獲取各種專業化的工具能力——從資料庫管理到雲端部署、從專案管理到安全掃描。外掛系統的進一步成熟也將鼓勵社群貢獻，形成一個活躍的外掛生態。

### 24.5 與開發工具鏈的深度整合

LSP 整合已經展示了 Claw Code 與程式語言工具鏈深度整合的潛力。未來的發展可能包括：與更多語言的 LSP 伺服器的原生整合、與 DAP（Debug Adapter Protocol）的整合以支援除錯能力、與 CI/CD 平台（如 GitHub Actions、GitLab CI）的更深度整合、以及與程式碼審查工具的整合。

### 22.4 權限系統的測試策略

權限系統的測試是一個特別具有挑戰性的領域。由於權限系統涉及多個層次的互動（權限模式、權限規則、勾子覆蓋、工具強制執行），需要設計精心的測試用例來覆蓋各種組合場景。

mock-anthropic-service 的 BashPermissionPromptApproved 和 BashPermissionPromptDenied 兩個場景專門用於測試權限提示流程。在 Approved 場景中，模擬服務產生一個需要權限確認的 bash 工具呼叫，測試驗證系統正確地顯示了確認提示，並在「使用者」核准後成功執行了命令。在 Denied 場景中，測試驗證系統在「使用者」拒絕後正確地回傳了權限拒絕的錯誤訊息給 AI 模型。

PermissionPolicy 的測試需要覆蓋所有五種模式和三種規則列表之間的組合。例如：在 WorkspaceWrite 模式下，allow 清單中的 bash 工具是否被允許？在 ReadOnly 模式下，deny 清單中的 read_file 工具是否被拒絕（deny 優先於任何模式）？在 Prompt 模式下，ask 清單中的工具是否觸發了使用者確認提示？

PermissionEnforcer 的測試需要驗證每個工具的 required_permission 屬性是否正確設定。例如，所有的讀取工具（read_file、glob_search、grep_search）都應該只需要 ReadOnly 權限，而所有的寫入工具（write_file、edit_file、bash）都應該需要 WorkspaceWrite 權限。

### 22.5 沙箱的測試方法

沙箱功能的測試受限於測試環境——大多數 CI 環境不支援 Linux namespace 操作，因為它們本身已經在容器中運行。因此，沙箱的測試策略分為兩個層面。

第一個層面是邏輯測試，不需要實際的 namespace 支援。這包括：sandbox.rs 中的偵測邏輯（在不同的環境條件下是否正確判斷沙箱的可用性）、build_linux_sandbox_command 函數的命令建構邏輯（是否正確地將使用者命令包裝在 unshare 命令中）、以及沙箱設定的解析和驗證邏輯。

第二個層面是整合測試，需要在支援 namespace 的環境中執行。這些測試通常在專門的測試伺服器或虛擬機中運行，驗證沙箱的實際隔離效果——在 PID namespace 中啟動的程序是否無法看到外部程序、在 NET namespace 中啟動的程序是否無法存取網路、在限制了檔案系統的沙箱中啟動的程序是否無法存取工作區之外的檔案。

### 23.4 遙測資料的隱私保護

遙測系統在收集操作資料時需要特別注意隱私保護。Claw Code 的遙測設計遵循了幾個重要的隱私原則。

首先是最小收集原則——系統只收集對運維和除錯有用的資訊，不收集使用者的對話內容、API 金鑰、或其他敏感資料。SessionTrace 記錄的是操作的名稱和時間戳記，而不是操作的具體內容。Analytics 事件包含的屬性也是經過篩選的聚合資訊。

其次是本地存儲原則——遙測資料預設儲存在本地的 JSONL 檔案中，不會自動上傳到任何外部服務。如果使用者希望將遙測資料發送到外部監控平台，需要明確地配置 Sink。

最後是可控原則——使用者可以隨時透過設定停用遙測功能，或者刪除已收集的遙測檔案。系統不會因為遙測功能被停用而降低其他功能的可用性。

### 24.6 compat-harness 與上游對齊

compat-harness crate 在 Claw Code 的品質保證中扮演著獨特的角色。它從上游 TypeScript 原始碼中提取工具清單、斜線命令清單以及啟動配置清單，然後產生 ExtractedManifest 供 Rust 端進行功能對等性檢查。

這種 parity 檢查（功能對等性檢查）確保了 Claw Code 的 Rust 實作不會遺漏上游 TypeScript 版本中已有的功能。每當上游新增一個工具或一個命令時，parity 檢查會偵測到差異並產生報告，提醒開發團隊需要在 Rust 端實作對應的功能。

ExtractedManifest 結構包含三個主要的清單：工具清單（列出所有上游定義的工具名稱和參數）、命令清單（列出所有上游定義的斜線命令和別名）、以及啟動清單（列出上游的啟動配置項目）。比較邏輯會將這些清單與 Rust 端的實際清單進行逐項比對，標記出缺失、多餘或不一致的項目。

### 24.7 持續整合的品質閘門

Claw Code 的 CI 管線被設計為一個嚴格的品質閘門，確保每一次程式碼變更都不會降低系統的品質標準。管線包含以下主要步驟。

cargo fmt --check 驗證所有原始碼檔案都遵循統一的格式化規則。Rust 的官方格式化工具 rustfmt 確保了程式碼風格的一致性，消除了團隊成員之間關於程式碼格式的爭議。

cargo clippy --workspace --all-targets -- -D warnings 執行靜態分析。由於工作區層級啟用了 pedantic 等級的 clippy 檢查，而且所有警告被當作錯誤處理（-D warnings），任何不符合最佳實踐的程式碼都會導致 CI 失敗。

cargo test --workspace 執行工作區中所有 crate 的測試。這包括單元測試、整合測試以及文件測試。mock-anthropic-service 在這個步驟中被大量使用，模擬各種 AI 回應場景來驗證核心邏輯的正確性。

文件一致性檢查驗證生成的文件與實際的程式碼行為是否一致。這個步驟使用 compat-harness 進行功能對等性檢查，並驗證各種自動生成的文件（如工具參考文件）是否為最新版本。

### 23.5 ClientIdentity 與 AnthropicRequestProfile

telemetry crate 還定義了 ClientIdentity 和 AnthropicRequestProfile 結構，用於在 API 請求中標識 Claw Code 客戶端。

ClientIdentity 包含三個欄位：app_name（應用程式名稱，固定為 claw-code）、app_version（應用程式版本，從建構時期元資料取得）和 runtime（執行時期資訊，包含 Rust 版本和作業系統資訊）。這些資訊被包含在每次 API 請求的標頭中，幫助 AI 提供商追蹤不同客戶端的使用情況。

AnthropicRequestProfile 結構定義了 Anthropic API 請求的額外配置：anthropic_version 指定使用的 API 版本、client_identity 包含前述的客戶端身份資訊、betas 列出要啟用的 beta 功能（如提示詞快取 prompt-caching-scope-2026-01-05）、extra_body 包含要附加到請求正文中的額外欄位。

### 23.6 遙測與效能最佳化

遙測資料不僅用於監控和審計，還可以用於效能最佳化。透過分析 HttpRequestStarted 和 HttpRequestSucceeded 事件中的時間戳記，可以計算每次 API 呼叫的延遲。長期的延遲統計可以幫助使用者識別效能瓶頸——是 API 伺服器的回應時間太長，還是本地的工具執行時間太長，又或者是 MCP 伺服器的處理速度太慢。

UsageTracker 的累計 token 用量資料也提供了最佳化的方向。如果輸入 token 佔比過高，可能意味著系統提示詞太長或工具定義太多，可以透過精簡提示詞或減少工具數量來降低成本。如果快取讀取 token 的比例太低，可能意味著提示詞快取沒有被有效利用，需要檢查快取配置。

### 22.6 端到端測試的設計

除了單元測試和模組級整合測試之外，Claw Code 還需要端到端測試來驗證整個系統的協作是否正確。端到端測試模擬使用者的完整使用流程——從輸入提示詞到接收 AI 回應，包括中間的工具呼叫和權限檢查。

端到端測試的搭建使用 mock-anthropic-service 作為 AI 提供商的替身。測試框架建構一個完整的 ConversationRuntime，配置模擬客戶端和真實的工具執行器（但限制在測試專用的臨時目錄中），然後模擬一系列的對話回合。每個回合後，測試驗證工作階段的狀態是否符合預期——訊息的數量和內容、工具呼叫的結果、token 用量的計算等。

端到端測試特別關注以下場景：多輪對話中上下文的正確維護、工具呼叫鏈（一個工具的結果觸發另一個工具的呼叫）的正確串接、壓縮觸發後工作階段的狀態是否正確、工作階段的序列化和反序列化是否保持資料完整性。

### 24.10 效能最佳化的方向

Claw Code 作為一個以 Rust 語言實作的系統，天然地具有良好的效能特性——零成本抽象、無垃圾回收、高效的記憶體管理。然而，在實際使用中，效能瓶頸往往不在本地計算，而在 API 通訊的延遲上。

幾個可能的效能最佳化方向包括：工具呼叫的並行化——當 AI 模型在一次回應中發出多個獨立的工具呼叫時，這些呼叫可以並行執行而不是順序執行。提示詞的壓縮最佳化——更智能的壓縮策略可以在保留更多有用上下文的同時減少 token 消耗。SSE 解析的零拷貝最佳化——目前的 SSE 解析器會為每個事件建立新的字串，零拷貝的實作可以減少記憶體分配。工作階段載入的懶加載——對於大型的歷史工作階段，可以只載入最近的訊息而不是全部訊息。

### 24.12 Claw Code 的教學價值

除了作為實用的開發工具之外，Claw Code 的原始碼本身也具有重要的教學價值。它展示了多種 Rust 語言的進階用法和軟體工程的最佳實踐。

模組化設計：九個 crate 的分層架構展示了如何在 Rust 的 Cargo Workspace 中組織大型專案。嚴格的依賴方向、最小的公開介面、以及清晰的職責邊界——這些原則適用於任何大型 Rust 專案的設計。

### 22.7 持續模糊測試的可能性

模糊測試（Fuzzing）是一種自動化的測試技術，透過產生大量的隨機或半隨機輸入來發現程式中的錯誤。Claw Code 中有幾個模組特別適合模糊測試。

SSE 解析器（sse.rs）處理來自外部的不可信資料——AI 提供商回傳的 SSE 事件流。模糊測試可以產生各種畸形的 SSE 資料，驗證解析器是否能夠正確地處理而不會崩潰或產生安全漏洞。

JSON-RPC 解析（mcp_stdio.rs）處理來自 MCP 伺服器的 JSON-RPC 回應。模糊測試可以產生各種不符合規格的 JSON-RPC 訊息，驗證系統是否能夠優雅地處理錯誤。

設定檔解析（config.rs）處理使用者提供的 JSON 設定。模糊測試可以產生各種極端的設定值（如非常長的字串、深層嵌套的物件、非常大的數字），驗證解析器的健壯性。

bash_validation.rs 的命令意圖分類是另一個重要的模糊測試目標。模糊測試可以產生各種奇怪的 Shell 命令字串，驗證分類器是否能夠正確地處理而不會遺漏潛在的危險命令。

### 24.15 Rust 語言選擇的長期影響

Claw Code 選擇 Rust 作為實作語言，這個決策的影響遠不止於效能和安全性。

在可維護性方面，Rust 的型別系統和所有權模型強制要求開發者在編譯時期就處理好資源管理、錯誤處理和併發安全。這使得 Claw Code 的程式碼在重構時更加安全——編譯器會捕獲大多數因為重構引入的錯誤。unsafe_code = forbid 的設定更進一步，確保了整個程式碼庫的記憶體安全。

在可移植性方面，Rust 編譯為原生的機器碼，不需要語言執行時期。Claw Code 的二進位檔案可以被部署到任何支援的平台上，不需要安裝 Rust 或任何其他依賴。這對於 CI/CD 環境特別有價值——只需要複製一個二進位檔案就能在任何 Linux 機器上運行。

在生態系統方面，Rust 的 crate 生態系統為 Claw Code 提供了豐富的高品質函式庫。tokio 提供了成熟的非同步執行時期，reqwest 提供了強大的 HTTP 客戶端，serde 提供了零開銷的序列化框架，crossterm 提供了跨平台的終端控制。這些函式庫的穩定性和效能直接提升了 Claw Code 的品質。

在社群方面，Rust 社群以嚴謹的程式碼品質標準和活躍的開源文化著稱。Claw Code 繼承了這些文化特質——clippy::pedantic 的程式碼風格要求、完善的文件規範、以及開放的貢獻流程。


### 22.8 回歸測試的策略

回歸測試確保新的程式碼變更不會破壞已有的功能。Claw Code 的回歸測試策略包含幾個層面。

在 crate 層面，每個 crate 的測試模組包含覆蓋其核心功能的測試用例。這些測試在每次程式碼變更後都會被 CI 管線執行。如果一個變更導致某個測試失敗，CI 會立即報告失敗，阻止變更被合併。

在整合層面，tests 目錄包含跨 crate 的測試。這些測試驗證不同 crate 之間的介面和互動是否正確。例如，一個測試可能驗證：當 api crate 回傳一個特定的錯誤時，runtime crate 是否正確地處理了這個錯誤，並且 rusty-claude-cli 是否向使用者顯示了適當的錯誤訊息。

在 parity 層面，compat-harness 的功能對等性檢查確保 Rust 實作不會遺漏上游 TypeScript 版本的功能。每次上游有新的功能或工具被添加時，parity 檢查會偵測到差異並提醒開發團隊。

回歸測試的一個重要原則是：每個被報告和修復的 bug 都應該有一個對應的測試用例。這個測試用例先驗證 bug 的存在（在修復前測試會失敗），然後在修復後驗證 bug 已經被解決。這確保了同一個 bug 不會在未來的變更中重新出現。

### 23.8 遙測與開發者體驗的關聯

遙測資料對於改善開發者體驗有著直接的價值。透過分析遙測資料，開發團隊可以識別使用者的痛點和最佳化機會。

例如，如果遙測資料顯示大量的工具呼叫因為權限被拒絕而失敗，可能意味著預設的權限模式對於某些常見的使用場景太過限制。開發團隊可以根據這些資料調整預設設定或改進權限提示的使用者體驗。

如果遙測資料顯示特定類型的 API 錯誤頻繁發生，開發團隊可以針對性地改進錯誤處理邏輯——例如，增加自動重試的次數、改進錯誤訊息的清晰度、或者添加特定的恢復策略。

如果遙測資料顯示工作階段的壓縮觸發非常頻繁，可能意味著預設的壓縮閾值太低，或者系統提示詞太長佔用了太多的 token 預算。開發團隊可以據此調整預設的壓縮設定或最佳化系統提示詞的長度。

這種資料驅動的改進循環——收集遙測 → 分析數據 → 識別問題 → 實施改進 → 驗證效果——是持續改善開發者體驗的關鍵方法論。

### 24.17 技術債務的管理

任何長期發展的軟體專案都會累積技術債務。Claw Code 的架構設計本身就是為了最小化技術債務而設計的——嚴格的分層架構防止了隨意的跨層依賴、trait-based 的多態設計確保了擴充的可預測性、全域 Registry 的 OnceLock 模式避免了複雜的生命週期管理。

然而，某些類型的技術債務是不可避免的。隨著功能的增加，runtime crate 已經成長到三十五個以上的子模組，未來可能需要進一步的模組拆分。全域 Registry 模式雖然簡化了資源管理，但增加了全域狀態，使得某些測試場景變得複雜。compat-harness 的功能對等性檢查依賴於上游 TypeScript 原始碼的結構穩定性，上游的大規模重構可能需要 compat-harness 的相應更新。

管理技術債務的關鍵是持續的小規模重構——在每次功能開發時，如果發現了可以改進的地方，就同時進行重構。Claw Code 的 CI 管線（特別是 clippy::pedantic 的嚴格檢查）為安全的重構提供了信心——如果重構引入了問題，CI 會立即報告。


### 22.9 效能基準測試

除了功能測試之外，效能基準測試也是 Claw Code 品質保證的重要組成部分。基準測試驗證了關鍵操作的效能不會因為程式碼變更而退化。

可能的基準測試目標包括：SSE 解析的吞吐量（每秒能解析多少個 SSE 事件）、JSONL 工作階段的載入速度（每秒能載入多少行 JSON）、設定合併的速度（合併五層設定的平均耗時）、Bash 驗證的速度（每秒能分類多少個 Shell 命令）。

Rust 的 criterion 基準測試框架為效能測試提供了統計學上嚴格的分析——它不只報告單次運行的耗時，而是透過多次運行和統計分析來計算置信區間。這確保了效能差異是真實的（統計顯著的），而不是隨機波動。

在 CI 管線中，效能基準可以被設定為在每次程式碼變更時自動運行，與基線（通常是主分支的最新版本）進行比較。如果發現顯著的效能退化，CI 會發出警告，提醒開發者檢查是否引入了效能問題。

### 22.10 測試的文化與實踐

Claw Code 專案的測試文化不僅體現在具體的測試策略上，更體現在開發團隊的日常實踐中。

「測試先行」（Test-First）是推薦的開發方式——在實作新功能之前，先編寫測試用例來定義功能的預期行為。這種方式確保了每個新功能都有對應的測試覆蓋，也讓開發者在實作過程中有一個明確的目標。

「紅-綠-重構」（Red-Green-Refactor）循環是測試先行方式的具體操作步驟：首先編寫一個會失敗的測試（紅色），然後編寫最少的程式碼讓測試通過（綠色），最後重構程式碼以改善結構和品質（重構）。CI 管線在每個步驟都提供快速的反饋，確保重構不會引入問題。

測試的可讀性也是重要的考量。每個測試用例的名稱應該清晰地描述它測試的是什麼——例如 test_permission_denies_bash_in_readonly_mode 比 test_permission_1 更有資訊量。測試的結構應該遵循 Arrange-Act-Assert 模式——先設定測試環境（Arrange），然後執行被測試的操作（Act），最後驗證結果（Assert）。

### 22.11 測試環境的隔離

測試環境的隔離對於確保測試的可靠性和可重複性至關重要。Claw Code 的測試使用了幾種隔離技術。

臨時目錄隔離：每個需要檔案操作的測試都會建立一個獨立的臨時目錄（使用 tempdir crate），所有的檔案讀寫操作都在這個臨時目錄中進行。測試結束後，臨時目錄會被自動清理。這確保了不同測試之間的檔案操作互不干擾。

全域狀態隔離：由於 Claw Code 使用了多個全域 Registry（TaskRegistry、TeamRegistry 等），測試需要確保每個測試開始時全域狀態是乾淨的。每個 Registry 都提供了 reset 或 clear 方法，測試框架在每個測試開始前呼叫這些方法來重置全域狀態。

環境變數隔離：某些測試需要設定特定的環境變數（如 ANTHROPIC_API_KEY 或 CLAW_SANDBOX_ENABLED）。由於環境變數是程序級的全域狀態，並行的測試可能互相干擾。解決方案是使用 serial_test crate 標記需要修改環境變數的測試為序列執行，確保它們不會並行運行。
