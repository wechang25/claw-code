# 第六部分：MCP 與外部整合

Model Context Protocol（MCP，模型上下文協定）是 Claw Code 中最具前瞻性的子系統之一。它代表了一種根本性的架構理念：AI 代理人的能力不應該被侷限在工具框架內建的功能中，而應該能夠透過標準化的協定，與任意數量的外部服務進行通訊，動態地獲取新的工具和資源。MCP 的存在使得 Claw Code 從一個功能固定的工具框架，進化為一個具有無限擴充能力的代理人平台。

本部分將深入剖析 MCP 子系統的架構設計、傳輸層抽象、生命週期管理以及外部整合的最佳實踐。

---

## 第十六章：MCP 協定架構

### 16.1 MCP 的設計動機

在 Claw Code 的早期設計中，所有的工具能力都是透過內建工具提供的。如果需要新的能力——例如存取特定的資料庫、呼叫特定的 API、整合特定的開發工具——就需要修改 Claw Code 的原始碼，新增一個內建工具。這種方式的問題顯而易見：首先，每個新工具都增加了核心程式碼的複雜度和維護負擔；其次，使用者需要等待新版本發布才能獲得新的工具能力；最重要的是，不同的使用者和團隊有著千差萬別的工具需求，不可能將所有需求都內建到核心系統中。

MCP 協定的引入徹底改變了這種局面。MCP 定義了一個標準化的通訊介面，任何實現了 MCP 伺服器端的外部程序都可以向 Claw Code 提供工具和資源。Claw Code 作為 MCP 客戶端，在啟動時與配置的 MCP 伺服器建立連線，發現它們提供的工具和資源，然後將這些外部工具無縫地整合到工具分派系統中。從 AI 模型的角度來看，MCP 工具和內建工具之間沒有任何區別——它們都出現在工具定義列表中，都可以透過相同的 tool_use 機制來呼叫。

### 16.2 六種傳輸方式

MCP 協定的一個核心設計決策是傳輸層的抽象化。mcp_client.rs 定義了 McpClientTransport 列舉型別，支援六種不同的傳輸方式，每種方式適用於不同的部署場景。

Stdio 傳輸是最常用的方式。在這種模式下，Claw Code 啟動一個 MCP 伺服器作為子程序，透過子程序的標準輸入（stdin）和標準輸出（stdout）進行 JSON-RPC 通訊。這種方式的優點是簡單、可靠，不需要網路配置，適合本地開發環境。使用者只需要在設定中指定伺服器的命令和參數，Claw Code 就會自動管理子程序的啟動和關閉。

SSE（Server-Sent Events）傳輸適用於遠端 MCP 伺服器。在這種模式下，Claw Code 透過 HTTP SSE 連線接收伺服器推送的事件，並透過 HTTP POST 請求發送命令。這種方式利用了 HTTP 的廣泛支援和穿透防火牆的能力，適合企業環境中的遠端工具伺服器。

HTTP 傳輸是最簡單的遠端通訊方式，使用標準的 HTTP 請求-回應模式。WebSocket 傳輸提供了全雙工的即時通訊能力。SDK 傳輸是保留的未來擴充點。ManagedProxy 傳輸透過一個託管的代理服務轉發通訊，適用於需要集中管理和監控 MCP 連線的場景。

### 16.3 JSON-RPC 通訊協定

所有 MCP 通訊都建構在 JSON-RPC 2.0 協定之上。JSON-RPC 是一種輕量級的遠端程序呼叫協定，使用 JSON 作為資料格式。每個請求包含四個欄位：jsonrpc（固定為字串 2.0）、id（請求的唯一標識符）、method（方法名稱）和 params（可選的參數物件）。每個回應也包含四個欄位：jsonrpc、id（與請求對應）、result（成功時的結果物件）和 error（失敗時的錯誤物件，包含 code、message 和可選的 data）。

MCP 協定定義了五個核心的 JSON-RPC 方法：initialize 用於初始化握手，客戶端向伺服器宣告自己的能力並獲取伺服器的能力聲明；tools/list 用於發現伺服器提供的所有工具；tools/call 用於執行特定的工具並傳遞輸入參數；resources/list 用於發現伺服器提供的所有資源；resources/read 用於讀取特定資源的內容。

### 16.4 工具命名規範

MCP 工具在 Claw Code 的工具系統中使用特定的命名格式：mcp__<server_name>__<tool_name>。例如，如果一個名為 github 的 MCP 伺服器提供了一個名為 search_repos 的工具，那麼在 Claw Code 中它的完整名稱就是 mcp__github__search_repos。這種雙下劃線分隔的命名格式確保了 MCP 工具名稱不會與內建工具名稱衝突，同時也讓系統能夠快速地從工具名稱中提取出伺服器名稱和原始工具名稱。

## 第十七章：MCP 生命週期管理

### 17.1 十一階段狀態機

mcp_lifecycle_hardened.rs 模組定義了一個精密的十一階段生命週期狀態機，管理每個 MCP 伺服器從啟動到關閉的完整過程。這個狀態機的「hardened」（加固）設計理念意味著每個階段的轉換都被嚴格驗證，任何異常都會被正確地處理和報告。

十一個階段依序為：ConfigLoad（從設定檔讀取 MCP 伺服器設定）、ServerRegistration（將伺服器規格註冊到 McpServerManager）、SpawnConnect（啟動子程序或建立遠端連線）、InitializeHandshake（發送 initialize JSON-RPC 請求並等待回應）、ToolDiscovery（發送 tools/list 請求取得伺服器提供的工具清單）、ResourceDiscovery（發送 resources/list 請求取得伺服器提供的資源清單）、Ready（伺服器完全就緒，可以接受工具呼叫）、Invocation（正在執行工具呼叫）、ErrorSurfacing（處理執行時期錯誤）、Shutdown（正在關閉伺服器）和 Cleanup（最終的資源清理）。

在正常的啟動流程中，狀態機從 ConfigLoad 開始，依序經過每個階段，最終到達 Ready 狀態。在 Ready 狀態下，伺服器可以接受工具呼叫（進入 Invocation 狀態），呼叫完成後回到 Ready。如果在任何階段發生錯誤，狀態機會根據錯誤的嚴重程度決定是進入 ErrorSurfacing（嘗試復原）還是直接進入 Shutdown（放棄連線）。

### 17.2 降級模式

在多伺服器的場景中，可能只有部分伺服器成功啟動，而其他伺服器因為各種原因（程序啟動失敗、連線被拒、握手逾時等）而無法就緒。Claw Code 採用了降級模式的設計——即使部分伺服器失敗，系統仍然可以使用成功啟動的伺服器所提供的工具。

McpDegradedReport 結構記錄了降級狀態的詳細資訊：healthy_servers 列出了所有成功就緒的伺服器名稱，failed_servers 列出了所有失敗的伺服器資訊（包括伺服器名稱、失敗的階段和錯誤描述）。系統在啟動時會將降級報告呈現給使用者，讓使用者了解哪些 MCP 工具可用、哪些不可用。

### 17.3 錯誤分類與復原

MCP 子系統定義了七種錯誤類別：ConfigParse（設定解析錯誤）、SpawnFailure（程序啟動失敗）、ConnectionRefused（連線被拒）、HandshakeTimeout（握手逾時）、ToolDiscoveryEmpty（沒有發現任何工具）、InvocationError（工具呼叫執行錯誤）和 TransportError（傳輸層錯誤）。

不同類型的錯誤有不同的復原策略。SpawnFailure 和 ConnectionRefused 通常意味著 MCP 伺服器程式不存在或未正確安裝，系統會記錄錯誤並將伺服器標記為失敗。HandshakeTimeout 可能是暫時性的網路問題，系統可能會嘗試重新連線。InvocationError 通常只影響單次工具呼叫，不會影響伺服器的整體可用性。TransportError 可能需要重新建立連線。

## 第十八章：外部整合實踐

### 18.1 MCP 伺服器設定

在 Claw Code 的設定檔（如 .claw.json 或 .claw/settings.json）中，MCP 伺服器透過 mcpServers 區段進行配置。每個伺服器需要一個唯一的名稱作為鍵，配置值指定傳輸方式和連線參數。

對於 Stdio 傳輸的伺服器，配置需要指定 type 為 stdio，以及 command（要執行的命令）、args（命令參數列表）和可選的 env（環境變數）。系統還支援 tool_call_timeout_ms 參數，設定工具呼叫的逾時時間（預設三萬毫秒）。

對於 SSE 傳輸的伺服器，配置需要指定 type 為 sse，以及 url（伺服器的 SSE 端點 URL）和可選的 headers（自訂 HTTP 標頭，常用於認證）。

對於 WebSocket 傳輸的伺服器，配置需要指定 type 為 ws，以及 url（WebSocket 端點 URL）。

### 18.2 LSP 整合

除了 MCP 之外，Claw Code 還透過 LSP（Language Server Protocol）與程式語言工具鏈進行整合。LspRegistry 管理活躍的 LSP 連線，LSP 工具支援七種操作：diagnostics 提供語法和語意錯誤的即時偵測；hover 提供符號的型別資訊和文件說明；definition 跳轉到符號的定義位置；references 查找符號的所有參考位置；completion 提供程式碼自動完成建議；symbols 列出檔案或工作區中的所有符號；format 進行程式碼格式化。

LSP 整合讓 AI 模型能夠利用語言伺服器的精確分析能力，而不是僅僅依賴自身對程式碼的理解。例如，當 AI 需要重命名一個函數時，它可以先使用 LSP 的 references 操作找到所有參考位置，確保修改的完整性。

### 18.3 外掛系統

plugins crate 提供了另一種外部整合機制。與 MCP 的標準化協定不同，外掛系統使用基於檔案系統的約定——每個外掛是一個包含特定目錄結構的資料夾。

外掛的根目錄包含一個 plugin.json 清單檔，定義了外掛的元資料（ID、名稱、版本、描述）、類型（Builtin 内建、Bundled 隨附、External 外部）、提供的工具和勾子。src 子目錄包含初始化腳本（init.sh）和關閉腳本（shutdown.sh），tools 子目錄包含工具的 Shell 腳本實作。hooks 子目錄包含勾子腳本：pre_tool_use.sh 在任何工具執行前被呼叫，post_tool_use.sh 在工具成功執行後被呼叫。

外掛的生命週期由 plugin_lifecycle.rs 管理，定義了八種狀態：Unconfigured（未設定）、Validated（已驗證）、Starting（啟動中）、Healthy（健康）、Degraded（降級）、Failed（失敗）、ShuttingDown（關閉中）和 Stopped（已停止）。

### 18.4 MCP 伺服器開發指南

開發自訂 MCP 伺服器是擴充 Claw Code 能力的最強大方式。一個 MCP 伺服器可以用任何程式語言實作，只要它遵循 JSON-RPC 2.0 通訊協定和 MCP 的方法規範。

最簡單的 MCP 伺服器實作方式是使用 Stdio 傳輸。伺服器程序從標準輸入讀取 JSON-RPC 請求，處理後將回應寫入標準輸出。以 Node.js 為例，一個基本的 MCP 伺服器需要處理以下方法：initialize 方法回覆伺服器的能力聲明（包含伺服器名稱、版本和支援的功能）；tools/list 方法回覆伺服器提供的工具清單（每個工具包含名稱、描述和輸入 Schema）；tools/call 方法接收工具名稱和輸入參數，執行對應的邏輯，回覆工具結果。

工具結果（McpToolCallResult）可以包含多種類型的內容（McpToolCallContent）：Text（純文字）、Json（JSON 物件）、Image（Base64 編碼的圖片）或 Resource（MCP 資源的參考）。這種多類型的結果格式使得 MCP 工具能夠回傳豐富的資訊給 AI 模型。

resources/list 方法回覆伺服器提供的資源清單。McpResource 包含 URI（唯一資源標識符）、名稱、可選的描述和 MIME 類型。resources/read 方法接收資源 URI 並回覆資源的內容。MCP 資源是一種讓 AI 模型能夠瀏覽和讀取外部資料的機制——例如，一個資料庫 MCP 伺服器可能將每張表定義為一個資源，讓 AI 模型能夠查看表結構和範例資料。

### 18.5 MCP 效能考量

MCP 通訊的效能直接影響工具呼叫的延遲和整體的使用者體驗。對於 Stdio 傳輸，效能主要受限於子程序的啟動時間和 JSON 序列化/反序列化的開銷。為了最小化啟動延遲，Claw Code 在系統初始化時就啟動所有配置的 MCP 伺服器子程序，而不是在第一次使用時才啟動。子程序一旦啟動就保持運行，避免了重複的啟動開銷。

對於遠端傳輸（SSE、HTTP、WebSocket），效能主要受限於網路延遲。tool_call_timeout_ms 參數允許使用者為每個伺服器設定不同的逾時時間，以適應不同的網路環境。對於需要長時間處理的工具呼叫（如複雜的資料庫查詢或大規模的搜尋操作），可以適當增加逾時時間。

JSON-RPC 的批次處理是一個潛在的效能最佳化方向。JSON-RPC 2.0 規範支援批次請求——在一個 JSON 陣列中包含多個請求，伺服器處理後在一個 JSON 陣列中包含所有回應。如果 AI 模型在一次回應中產生了多個工具呼叫，這些呼叫理論上可以被批次發送到同一個 MCP 伺服器，減少通訊往返次數。

### 18.6 McpToolRegistry 的工作機制

McpToolRegistry 是 MCP 子系統與 Claw Code 工具系統之間的橋接層。當 MCP 伺服器完成 ToolDiscovery 和 ResourceDiscovery 階段後，McpToolRegistry 會收集所有伺服器提供的工具和資源，將它們轉換為統一的內部格式，並註冊到全域的工具清單中。

對於每個 MCP 工具，McpToolRegistry 會建立一個對應的工具定義（ToolDefinition），包含使用命名規範格式化的名稱（mcp__<server>__<tool>）、工具描述和輸入 Schema。這個工具定義會被包含在每次 API 請求的工具清單中，讓 AI 模型知道它可以使用這些外部工具。

當 AI 模型透過 tool_use 機制呼叫一個 MCP 工具時，execute_tool 函數會識別出 mcp__ 前綴，從工具名稱中提取伺服器名稱和原始工具名稱，然後透過 McpToolRegistry 找到對應的 MCP 伺服器連線，發送 tools/call JSON-RPC 請求，等待回應，最後將結果轉換為 ToolResult 格式回傳給 ConversationRuntime。

McpToolRegistry 還處理工具可用性的動態變化。如果一個 MCP 伺服器在運行過程中崩潰或失去連線，McpToolRegistry 會將該伺服器的所有工具標記為不可用。後續對這些工具的呼叫會立即回傳錯誤，而不是等待逾時。如果伺服器重新上線，McpToolRegistry 可以重新發現其工具並恢復可用狀態。


### 18.7 MCP 與安全的交叉考量

MCP 伺服器引入了一個重要的安全考量：外部提供的工具不在 Claw Code 的直接控制範圍內。一個惡意或有 bug 的 MCP 伺服器可能回傳錯誤的資訊、嘗試注入惡意指令到 AI 的上下文中，或者在工具呼叫時執行不安全的操作。

Claw Code 透過幾種機制來緩解這些風險。首先，MCP 工具呼叫受到與內建工具相同的權限檢查——PermissionEnforcer 會檢查每個 MCP 工具的權限需求是否被當前模式滿足。其次，MCP 伺服器的設定只能來自於使用者明確配置的設定檔，系統不會自動發現或連線到未配置的伺服器。最後，tool_call_timeout_ms 參數防止了惡意伺服器透過長時間不回應來消耗系統資源。

然而，MCP 安全仍然是一個活躍的研究領域。未來可能的增強包括：MCP 伺服器的簽章驗證（確保伺服器程式沒有被竄改）、MCP 工具呼叫的速率限制（防止異常頻繁的工具呼叫）、以及 MCP 回應的內容過濾（偵測可能的注入攻擊）。

### 18.8 LSP 與 MCP 的整合潛力

LSP 和 MCP 在技術上有許多相似之處——它們都是基於 JSON-RPC 的客戶端-伺服器協定，都透過 Stdio 傳輸進行通訊，都支援能力發現機制。這種相似性暗示了未來可能的整合方向：將 LSP 伺服器包裝為 MCP 伺服器，或者在 MCP 協定中引入 LSP 風格的語言智能能力。

目前，LspRegistry 和 McpToolRegistry 是獨立運作的。LSP 整合透過專門的 LSP 工具提供七種語言操作，而 MCP 整合透過通用的 MCP 工具機制提供任意的外部工具。然而，在語意層面，它們的目標是一致的——擴充 AI 代理人理解和操作程式碼的能力。

未來的一個可能方向是統一的語言智能 MCP 伺服器——一個 MCP 伺服器同時提供 LSP 風格的語言操作和自訂的程式碼分析工具。這種統一的方式可以簡化設定和管理，同時讓 AI 模型能夠透過一致的介面存取所有的程式碼智能功能。

### 18.9 外掛與 MCP 的對比

外掛系統和 MCP 子系統都提供了擴充 Claw Code 能力的機制，但它們的設計哲學和適用場景有所不同。

外掛系統使用基於檔案系統的約定（plugin.json 清單檔、Shell 腳本實作），適合簡單的工具擴充和勾子機制。外掛的開發門檻較低——只需要寫幾個 Shell 腳本就能建立一個功能完整的外掛。外掛的勾子機制（pre_tool_use、post_tool_use）提供了 MCP 沒有的能力——在任何工具執行前後介入。

MCP 子系統使用標準化的 JSON-RPC 協定，適合複雜的工具伺服器和跨語言整合。MCP 伺服器可以用任何程式語言實作，可以存取任何外部資源（資料庫、API、雲端服務等），可以維護狀態（如持久的資料庫連線）。MCP 的資源機制（resources/list、resources/read）提供了外掛系統沒有的能力——結構化的資料瀏覽。

在選擇使用哪種擴充機制時，一般的建議是：如果需求是簡單的腳本化工具或勾子，使用外掛系統；如果需求是複雜的服務整合或需要持久狀態，使用 MCP 伺服器。兩種機制可以同時使用，外掛提供的勾子也能夠作用於 MCP 工具的呼叫。


### 16.4 MCP 協定版本與相容性

Claw Code 的 MCP 實作遵循 Protocol v2024-11-05 版本規格。版本相容性在 MCP 通訊中是一個重要的考量——客戶端和伺服器需要能夠就雙方都支援的協定版本達成一致。

在 initialize 握手過程中，客戶端和伺服器交換各自支援的協定版本資訊。如果雙方的版本不相容（例如伺服器要求的最低版本高於客戶端支援的最高版本），握手會失敗，伺服器會被標記為不可用。

版本協商的設計允許向前和向後相容。較新版本的 MCP 協定可能引入新的方法或擴充現有方法的功能，但必須保持對舊版本核心功能的支援。這確保了不同版本的客戶端和伺服器能夠協同工作，雖然可能無法利用某些新功能。

### 17.4 Stdio 傳輸的程序管理

mcp_stdio.rs 模組實現了 Stdio 傳輸的完整程序管理功能。McpStdioProcess 結構維護了子程序的參考，包括程序 ID、stdin 寫入器和 stdout 讀取器。McpServerManager 統一管理所有 Stdio 傳輸的子程序。

子程序的啟動使用 tokio 的非同步程序管理功能。spawn_mcp_stdio_process 函數根據設定中的 command 和 args 建構命令，設定 stdin 為管道模式（pipe）以便寫入，設定 stdout 為管道模式以便讀取，設定 stderr 為管道模式以便收集錯誤資訊。env 參數中指定的環境變數會被傳遞給子程序，與系統的環境變數合併。

JSON-RPC 的請求-回應配對使用 ID 機制。每個請求都攜帶一個唯一的 ID（通常是遞增的整數），伺服器的回應包含相同的 ID。這使得客戶端能夠將回應與對應的請求配對，即使回應的順序與請求的順序不同。

子程序的生命週期管理包括優雅關閉和強制終止。在正常關閉時，系統會先嘗試關閉 stdin（向伺服器發送 EOF 信號），等待伺服器自行退出。如果伺服器在合理的時間內沒有退出，系統會發送 SIGTERM 信號。如果 SIGTERM 也無效，系統會發送 SIGKILL 強制終止。

### 17.5 遠端傳輸的認證機制

對於遠端傳輸（SSE、HTTP 和 WebSocket），認證是一個重要的考量。MCP 伺服器的設定支援 headers 參數，允許使用者指定自訂的 HTTP 標頭。最常見的用途是傳遞認證資訊——例如，Authorization: Bearer <token> 標頭。

McpClientAuth 結構封裝了 MCP 伺服器的認證資訊。它支援多種認證方式：Bearer Token（最常見，適用於大多數 API 閘道）、Basic Auth（使用者名稱和密碼的 Base64 編碼）和自訂標頭（適用於使用非標準認證方案的伺服器）。

在 SSE 傳輸中，認證標頭在建立初始 HTTP 連線時被包含。一旦 SSE 連線建立，後續的事件推送不需要額外的認證。但如果連線斷開需要重新連線，認證標頭會被再次包含。

在 WebSocket 傳輸中，認證標頭在 WebSocket 握手的 HTTP Upgrade 請求中被包含。握手成功後，後續的 WebSocket 幀不包含 HTTP 標頭。如果需要在 WebSocket 通訊中進行認證刷新，需要透過 WebSocket 訊息來進行。


### 18.10 MCP 生態系統的願景

MCP 協定的引入為 Claw Code 打開了一個廣闘的生態系統空間。隨著越來越多的 MCP 伺服器被開發和共享，使用者將能夠輕鬆地獲取各種專業化的工具能力。

在開發工具領域，可能的 MCP 伺服器包括：資料庫存取伺服器（讓 AI 能夠查詢和修改資料庫）、雲端部署伺服器（讓 AI 能夠部署應用程式到 AWS、GCP 或 Azure）、專案管理伺服器（讓 AI 能夠更新 Jira、Linear 或 GitHub Issues 中的任務）、安全掃描伺服器（讓 AI 能夠執行程式碼安全分析）。

在知識管理領域，可能的 MCP 伺服器包括：文件搜尋伺服器（讓 AI 能夠搜尋企業知識庫）、API 文件伺服器（讓 AI 能夠查詢特定框架或庫的文件）、程式碼範例伺服器（讓 AI 能夠搜尋和引用程式碼範例）。

在協作領域，可能的 MCP 伺服器包括：聊天整合伺服器（讓 AI 能夠在 Slack 或 Teams 中發送訊息）、郵件伺服器（讓 AI 能夠發送通知郵件）、版本控制伺服器（提供更高階的 Git 操作，如複雜的合併和 rebase 策略）。

這些 MCP 伺服器可以由企業內部開發（針對特定的內部系統），也可以由社群開發並開源共享。隨著生態系統的成長，MCP 有望成為 AI 工具整合的通用標準。


### 16.5 MCP 資源的概念模型

MCP 資源（Resource）是 MCP 協定中除了工具之外的另一個核心概念。如果說工具是 MCP 伺服器提供的「操作能力」，那麼資源就是 MCP 伺服器提供的「資料存取」。

每個 McpResource 有四個屬性：uri 是資源的唯一識別符，使用 URI 格式（如 db://users/schema 或 file:///docs/README.md）；name 是人類可讀的資源名稱；description 是可選的資源描述；mime_type 是可選的 MIME 類型，指示資源內容的格式。

AI 模型可以透過 ListMcpResources 工具瀏覽所有 MCP 伺服器提供的資源列表，然後透過 ReadMcpResource 工具讀取特定資源的內容。這種瀏覽-讀取的互動模式讓 AI 模型能夠探索未知的資料結構——例如，面對一個資料庫 MCP 伺服器，AI 可以先列出所有表（資源），然後讀取特定表的結構和範例資料，最後根據理解到的結構來構造查詢。

資源機制在某些場景下比工具更加高效。如果 AI 需要存取一組靜態的或很少變化的資料（如 API 文件、設定模板、參考資料），將這些資料作為資源提供可以避免每次存取都進行一次完整的工具呼叫。

### 17.6 MCP 伺服器的健康監控

在 MCP 伺服器長時間運行的場景中，健康監控是確保系統穩定性的重要機制。Claw Code 透過幾種方式監控 MCP 伺服器的健康狀態。

對於 Stdio 傳輸的伺服器，系統監控子程序的存活狀態。如果子程序意外退出（退出碼非零），系統會偵測到並將伺服器標記為失敗。退出碼和標準錯誤的內容會被記錄，幫助診斷失敗原因。

對於遠端傳輸的伺服器（SSE、HTTP、WebSocket），系統透過定期的心跳機制檢查連線的存活性。如果心跳請求在指定時間內沒有收到回應，系統會認為連線已斷開，嘗試重新連線。

plugin_lifecycle.rs 中定義的 ServerHealth 結構提供了伺服器健康狀態的量化評估。健康評估考慮多個因素：最近的工具呼叫成功率、平均回應延遲、連續失敗次數等。當健康評估降低到警戒閾值以下時，系統會發出警告。

### 18.11 MCP 設定的最佳實踐

基於實際使用經驗，以下是 MCP 設定的一些最佳實踐建議。

對於本地開發環境，建議使用 Stdio 傳輸。Stdio 的優點是不需要網路配置、啟動簡單、除錯方便（可以直接查看子程序的 stderr 輸出）。將 MCP 伺服器的命令和參數配置在專案的 .claw/settings.json 中，讓團隊成員共享同一套 MCP 配置。

對於團隊共享的 MCP 伺服器，建議使用 SSE 或 HTTP 傳輸。遠端傳輸讓多個團隊成員可以共享同一個 MCP 伺服器實例，避免每個人都需要在本地運行伺服器。將伺服器的 URL 配置在專案設定中，將認證資訊（如 Bearer Token）配置在 .claw/settings.local.json 中。

對於生產環境的自動化場景，建議設定合理的逾時時間。tool_call_timeout_ms 的預設值（三萬毫秒）對於大多數工具呼叫來說足夠了，但對於需要長時間處理的操作（如大型資料庫查詢或複雜的 API 呼叫），可能需要增加到六萬毫秒甚至更長。

始終在設定中為每個 MCP 伺服器提供有意義的名稱。伺服器名稱會出現在工具名稱中（mcp__<name>__<tool>），也會出現在日誌和錯誤訊息中。一個好的命名（如 github、database、docs）比通用的命名（如 server1、my-mcp）更有助於理解和除錯。


### 18.12 McpServerConfig 的完整結構

讓我們詳細了解 McpServerConfig 的每一個變體和它們的配置參數。

Stdio 變體是最常用的：command 指定要執行的命令（如 node、python、npx 等）；args 是命令的參數列表（如 server.js 或 --port 3000）；env 是一個鍵值映射，指定要傳遞給子程序的環境變數；tool_call_timeout_ms 設定工具呼叫的逾時時間。

Sse 變體用於遠端 SSE 伺服器：url 指定 SSE 端點的 URL（如 https://api.example.com/mcp/events）；headers 是一個鍵值映射，指定要包含在 HTTP 請求中的自訂標頭（最常用於認證）。

Http 變體用於標準的 HTTP 請求-回應模式：url 指定 HTTP 端點的 URL；headers 同樣是自訂標頭映射。與 SSE 不同的是，Http 模式不支援伺服器推送——每次通訊都是獨立的請求-回應。

Ws（WebSocket）變體用於全雙工的即時通訊：url 指定 WebSocket 端點的 URL（使用 wss:// 或 ws:// 協定）。WebSocket 的優勢是雙向通訊——伺服器可以主動向客戶端推送訊息，適合需要即時通知的場景。

Sdk 變體目前是保留的擴充點，尚未有完整的實作。

ManagedProxy 變體用於透過代理服務轉發 MCP 通訊。這在企業環境中特別有用——所有 MCP 連線都透過一個中央代理進行，便於監控、審計和存取控制。

ScopedMcpServerConfig 包裝了 McpServerConfig，添加了作用域資訊。作用域指定了這個伺服器設定來自哪個設定層級（全域、使用者、專案或本地），在設定合併時用於確定優先序。


### 17.7 MCP 連線的重試與復原

在長時間運行的場景中，MCP 連線可能因為各種原因而中斷——MCP 伺服器崩潰並重新啟動、網路暫時中斷、系統資源不足導致子程序被終止。Claw Code 需要能夠優雅地處理這些中斷並嘗試恢復連線。

對於 Stdio 傳輸，連線中斷意味著子程序已經退出。系統偵測到子程序退出後，會根據退出碼判斷是正常退出還是異常退出。如果是異常退出，系統可以嘗試重新啟動子程序。重啟後，系統需要重新執行完整的握手和發現流程（initialize → tools/list → resources/list），因為新的子程序沒有之前的狀態。

對於遠端傳輸，連線中斷可能是暫時的（如網路波動）或永久的（如伺服器下線）。系統會使用指數退避的重試策略——第一次重試等待一秒、第二次等待兩秒、第四次等待八秒，以此類推。如果連續的重試都失敗，系統會將伺服器標記為不可用，但會在後續的對話回合中繼續嘗試重新連線，以應對伺服器最終恢復的情況。

重試過程對使用者是透明的。在重試期間，對不可用伺服器的工具呼叫會回傳清晰的錯誤訊息（如「MCP 伺服器 github 目前不可用，正在嘗試重新連線」），讓 AI 模型能夠選擇替代的方法來完成任務。


### 16.6 MCP 與 Agent 工具的協同

Agent 工具（啟動子代理人）和 MCP 工具可以協同使用，產生強大的組合效果。一個常見的模式是：主代理人使用 Agent 工具啟動一個子代理人，子代理人專門負責使用特定的 MCP 伺服器完成特定的任務。

例如，假設配置了一個 database MCP 伺服器（提供資料庫查詢功能）和一個 docs MCP 伺服器（提供 API 文件查詢功能）。主代理人收到「修復使用者查詢的效能問題」這個任務後，可以：啟動子代理人 A 使用 database MCP 伺服器分析慢查詢日誌、啟動子代理人 B 使用 docs MCP 伺服器查閱資料庫最佳化的文件、然後根據兩個子代理人的報告制定修復方案。

這種模式的優勢是任務分解和並行處理——子代理人 A 和 B 可以同時工作，各自專注於自己的任務，不會互相干擾。主代理人負責整合結果和制定策略，形成了一種「經理-工程師」的協作模式。

MCP 工具還可以與 LSP 工具協同使用。例如，AI 可以先使用 LSP 的 references 操作找到一個函數的所有參考位置，然後使用特定的 MCP 工具（如 refactoring MCP 伺服器）來執行自動化的重命名重構。


### 18.13 MCP 生態系統的演進

MCP 協定仍然是一個相對年輕的標準，其規格和生態系統都在快速演進中。Protocol v2024-11-05 版本定義了核心的功能集，但未來的版本可能會引入新的功能。

可能的協定擴充方向包括：批次工具呼叫（在單一請求中包含多個工具呼叫，減少通訊往返）、工具結果串流（讓長時間運行的工具能夠逐步回報結果，而不是等到完全完成）、伺服器推送通知（讓伺服器能夠主動通知客戶端某些事件的發生）、以及工具的版本化（讓伺服器能夠同時提供同一個工具的多個版本，支援漸進式的介面遷移）。

在生態系統層面，MCP 伺服器的分發和管理機制也在發展中。目前，MCP 伺服器的安裝和配置是手動的——使用者需要自行安裝伺服器程式（如透過 npm install 或 pip install），然後手動配置設定檔案。未來可能會出現 MCP 伺服器的集中式登記處（類似 npm registry 或 Docker Hub），讓使用者能夠一鍵安裝和配置 MCP 伺服器。

Claw Code 的 MCP 實作被設計為易於跟隨協定的演進。McpClientTransport 的列舉設計允許新增傳輸方式而不影響現有的實作；JsonRpcMessage 的通用結構支援新的方法而不需要修改核心的通訊邏輯；McpLifecyclePhase 的狀態機可以擴充新的階段。


### 18.14 從 MCP 到通用代理人協定

展望更遠的未來，MCP 可能演進為一個更通用的「代理人協定」——不僅僅是工具呼叫和資源存取，還包括代理人之間的直接通訊、任務委派和結果共享。

在這樣的願景中，Claw Code 不僅是一個 MCP 客戶端，也是一個 MCP 伺服器——它可以將自己的工具能力暴露給其他的 AI 代理人系統。例如，一個專注於產品管理的 AI 代理人可能透過 MCP 協定向 Claw Code 委派程式碼修改任務，而不需要了解 Claw Code 的內部工作方式。

這種代理人間的協作開啟了一個令人興奮的可能性：一個由多個專業化 AI 代理人組成的「虛擬開發團隊」。產品經理代理人負責需求分析和優先級排序，架構師代理人負責系統設計，開發者代理人（如 Claw Code）負責程式碼實作，測試代理人負責品質保證，運維代理人負責部署和監控。每個代理人透過標準化的協定進行通訊，形成一個高效的自動化開發流水線。


### 16.7 MCP 的規模化挑戰

隨著配置的 MCP 伺服器數量增加，系統面臨幾個規模化的挑戰。

首先是工具定義的 token 消耗。每個 MCP 工具都需要在 API 請求中包含其定義（名稱、描述和輸入 Schema），這些定義消耗輸入 token。如果配置了大量的 MCP 伺服器，每個提供十到二十個工具，工具定義的 token 消耗可能變得顯著。一種可能的最佳化是只在 API 請求中包含最相關的工具定義——根據當前的對話上下文和使用者的最近操作，動態地選擇要包含的工具子集。

其次是啟動時間。每個 MCP 伺服器都需要經歷完整的生命週期啟動流程——從程序啟動到握手到工具發現。如果配置了十個以上的 MCP 伺服器，啟動時間可能變得明顯。一種最佳化是並行啟動多個伺服器——Claw Code 已經支援這種方式，使用 tokio 的並發任務同時驅動多個伺服器的狀態機。

第三是工具名稱衝突。不同的 MCP 伺服器可能提供同名的工具——例如，兩個伺服器都提供 search 工具。MCP 的命名規範（mcp__<server>__<tool>）透過伺服器名稱前綴避免了衝突，但過長的工具名稱可能影響 AI 模型的使用效率。


### 17.8 MCP 伺服器的日誌收集

對於 Stdio 傳輸的 MCP 伺服器，日誌收集是一個重要的運維需求。MCP 的 JSON-RPC 通訊透過 stdin/stdout 進行，那麼伺服器的日誌應該輸出到哪裡？

答案是 stderr。MCP 的 Stdio 傳輸約定中，stdout 專門用於 JSON-RPC 通訊，stderr 用於日誌和除錯資訊。Claw Code 會收集子程序的 stderr 輸出，在伺服器出錯時將其包含在錯誤報告中。

在正常運行時，stderr 的輸出通常不會顯示給使用者（除非使用者使用 /mcp 命令查看伺服器的詳細狀態）。但在除錯模式下（可以透過環境變數 CLAW_MCP_DEBUG=1 啟用），所有 MCP 伺服器的 stderr 輸出都會被即時顯示在終端中，幫助開發者診斷通訊問題。

日誌的旋轉也需要考慮。長時間運行的 MCP 伺服器可能產生大量的日誌輸出，如果不進行控制可能消耗大量記憶體。Claw Code 對每個伺服器的 stderr 緩衝區有大小限制，超過限制時舊的日誌會被丟棄。


### 18.15 mcp_server.rs 的本地 MCP 伺服器

除了作為 MCP 客戶端之外，Claw Code 還實現了一個本地的 MCP 伺服器（mcp_server.rs）。這個伺服器遵循 Protocol v2024-11-05 版本規格，可以將 Claw Code 的內建工具暴露給其他的 MCP 客戶端。

本地 MCP 伺服器的存在讓 Claw Code 能夠被整合到更大的 AI 代理人生態系統中。例如，一個使用其他框架建構的 AI 代理人可以透過 MCP 協定呼叫 Claw Code 的 Bash 工具或檔案操作工具，利用 Claw Code 的安全模型和沙箱隔離功能，而不需要直接整合 Claw Code 的程式碼。

本地 MCP 伺服器支援所有六種傳輸方式，但最常見的部署方式是 Stdio——其他的 AI 代理人框架將 Claw Code 作為子程序啟動，透過 stdin/stdout 進行 JSON-RPC 通訊。


### 18.16 ScopedMcpServerConfig 的作用域語意

ScopedMcpServerConfig 中的 scope 欄位記錄了設定的來源層級，這個資訊在多個場景中被使用。

在設定顯示中（如 /mcp 和 /config 命令的輸出），scope 資訊讓使用者能夠了解每個 MCP 伺服器的設定來自哪裡。例如，如果一個伺服器的設定來自專案層級，使用者知道修改 .claw.json 就能改變這個設定；如果來自全域層級，則需要修改 ~/.claw.json。

在除錯場景中，scope 資訊幫助診斷設定合併的問題。如果使用者發現某個 MCP 伺服器的設定與預期不同，scope 資訊能夠幫助定位是哪一層的設定覆蓋了預期的值。

在安全審計中，scope 資訊提供了設定來源的追蹤。安全團隊可以驗證特定的 MCP 伺服器設定是否來自受控的來源（如專案設定），而不是來自可能被使用者任意修改的來源（如本地覆蓋）。


### 18.17 MCP 的標準化意義

MCP 協定的標準化對於整個 AI 工具生態系統有著深遠的意義。在 MCP 出現之前，每個 AI 代理人框架都有自己專屬的工具整合方式——LangChain 使用 Python 的裝飾器、AutoGPT 使用 JSON 配置檔、Aider 使用命令列介面。這種碎片化使得工具開發者需要為每個框架建立獨立的整合，大大增加了開發和維護的成本。

MCP 的出現為這個問題提供了一個優雅的解決方案——定義一個通用的工具整合協定，讓工具開發者只需要實作一次 MCP 伺服器，就能被所有支援 MCP 的 AI 代理人框架使用。這種「寫一次，到處用」的理念與 Web 標準的精神一脈相承。

Claw Code 是 MCP 協定的早期採用者之一，它的 MCP 實作為協定的驗證和改進提供了寶貴的實踐經驗。隨著更多的框架採用 MCP，一個統一的 AI 工具生態系統正在逐步形成。
